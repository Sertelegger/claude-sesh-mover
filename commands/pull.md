---
name: pull
description: Pull a project's thread from the cross-machine hub into this machine
---

You are running the sesh-mover pull command. Follow these steps:

1. Check hub configuration first:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" hub status
   ```
   - If `hubPath` is `null`, tell the user no hub is configured yet and point them at `/sesh-mover:hub-init`. Stop.
   - If `reachable` is false, surface the `warnings` and stop.

2. Determine the project path:
   - Normal case (this project already exists locally — you're pulling an update or a thread from another machine into it): use cwd as `--project-path`, no `--target-path` needed.
   - Bootstrap case (this project doesn't exist on this machine at all yet — first time pulling it here): ask the user for the destination directory (AskUserQuestion or free text) and pass it as `--target-path <dir>` **in addition to** `--project-path` (still cwd, or wherever the user is running the command from — it drives hub project identity/linking, while `--target-path` is where the session files and workspace snapshot actually land). Don't conflate the two flags; they can point at different places.

3. Run without a thread selector first, to discover what's available:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" pull --project-path "<cwd>" --source-config-dir "<config-dir>" [--project-id <id>]
   ```
   (only include `--project-id` if the user is deliberately linking to a specific hub project that isn't linked locally yet)

4. Parse the result and branch:
   - `reason: "unlinked"`: same shape as push — present `linkCandidates` as a pick-list, but point the user at `/sesh-mover:push` to link or create the hub project first (pull can also link directly via `--project-id`; offer to re-run step 3 with `--project-id <picked>` if the user prefers not to switch commands).
   - `reason: "lock-busy"`: wait a few seconds and retry the same invocation once; if still busy, stop and report it.
   - `pickRequired: true`: present `threads` as a numbered list — slug, latest machine name, `lastActiveAt`, `messageCount`, and whether `pullNeeded` is true. Ask the user which thread to pull (AskUserQuestion), or offer "pull whichever most needs updating" which maps to `--latest` instead of `--thread <id>`.
   - Any other `success: false` (no `reason` field): report `error`/`suggestion` and stop.

5. Run the real pull with the chosen thread, always with `--on-divergence skip`:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" pull --project-path "<cwd>" --source-config-dir "<config-dir>" --thread "<id>" --on-divergence skip [--target-path "<dir>"] [--project-id <id>]
   ```
   (substitute `--latest` for `--thread "<id>"` if that's what the user picked)

   `--on-divergence skip` is inert on an ordinary pull — it only does anything when the thread was extended on **both** machines from the same point, which is the one situation where the right answer is the user's to give. Skipping applies and records nothing, so step 6's divergence branch can put the real choice in front of them and then re-run. Without it the default (`fragment`) would already have imported the hub's branch as a second session, and adopting it afterwards is no longer possible: the bundle is recorded as received, so the re-run reports "already up to date".

6. Parse the result and branch:
   - `reason: "not-yet-synced"`: tell the user the hub folder's sync client (OneDrive/Dropbox/Syncthing/etc.) hasn't finished copying these files to this machine yet. List the `missing` files, wait a moment, and offer to retry the same invocation.
   - `success: false` with an error mentioning the workspace target already has content: this happens specifically when you passed an explicit `--target-path` that isn't empty. Nothing was written. Use AskUserQuestion to confirm with the user **before** re-running with `--force-workspace` appended — never add it automatically — and label the options for what the flag actually does: "overwrite files of the same name in that directory" / "cancel". It is **not** a merge and never becomes one: this error only happens when no shared generation was found, which is the exact condition that makes a 3-way merge impossible, and `--force-workspace` skips the merge even when one is available. Files the payload does not contain are left alone; files it does contain replace yours.
   - **`unfetchableBundles` present (a result field — branch on it, never on the warning text):** part of this thread is held by a machine whose bundle list this pull did not read. A pull fetches the bundle list of exactly **one** machine, and each machine's index lists only the bundles *it* pushed — so a conversation continued on two other machines arrives here in halves. Report each entry (`machineName` or `machineId`, and how many `bundleIds` it holds), say the entries in those bundles are not on this machine, and say nothing is lost — every bundle is still on the hub. **Offer no flag, no re-run and no `hub reindex`:** there is no `--from-machine`, `--thread` and `--target-path` resolve to the same single source, and `hub reindex` only rebuilds *this* machine's index from *its own* bundles. Assembling a thread whose history is split across machines is a later release; say that plainly rather than inventing a way around it. This branch also **overrides the reassurance in every branch below**: however many sessions were imported or appended, do not tell the user this machine now holds the whole conversation, and do not present `whereis`'s "current" as meaning it does.
   - **Workspace payload — branch on the RESULT FIELDS, never on the warning text.** A warning can name `--force-workspace` in *both* directions now, so its presence alone tells you nothing:
     - `workspaceMerge` present: the payload **was applied**, as a 3-way merge against the last generation this machine shared with the sender. Report what it decided from the report's own arrays — `conflicted` files have `<<<<<<< local` markers in them and the user must resolve those by hand; `sidecars` are `*.theirs-*` files left beside binaries and unmergeable files (tell them to delete those once reconciled, or they get pushed back to the hub); `localDeleted` files were **withheld**, and the accompanying warning explains why and names both remedies. Do **not** describe this pull as "skipped".
     - `workspaceMerge` absent and `workspaceUnpacked` non-null: the payload was unpacked wholesale (an empty project directory, or `--force-workspace`).
     - `workspaceRefused` non-empty (can accompany either of the two branches above): the payload carried paths that can **never** be applied — `.git` or `.claude-sesh-mover` at some depth, in some casing. Nothing from them was written, and a directory entry stands for everything under it. Report the paths and say what the risk was: `.claude-sesh-mover/hubinclude` decides what this machine's *next* push uploads, so a payload writing it could have redirected that. Do **not** accuse the sender — a sesh-mover older than this guard, on a case-insensitive filesystem, legitimately shipped a `.GIT` store — say only that a current sesh-mover never puts those in a bundle, so it came from an older version, was damaged in transit, or wasn't produced by sesh-mover. Nothing needs re-running.
     - `workspaceMerge.skipped` entries with reason `payload-internals` are the same thing on the merge path; `locally-excluded` means the incoming copy matched *this* machine's `.claude-sesh-mover/hubignore` (and isn't named back by its `hubinclude`), so it was deliberately not applied and the local file at that path was left alone. That is a rule on this machine, not a fault: the remedy is to edit `hubignore` (or `hubinclude`) and re-pull a later payload, or to take the hub's copy wholesale with `--force-workspace`, which does not honor that veto.
     - `workspaceDeclaredMissing: true`: the bundle's manifest **declared** a workspace payload that the bundle does not actually contain, so there was nothing to apply and this project's files were left untouched (sessions still imported normally). This is field-identical to the skip below apart from this flag — check it *first*, because that skip's remedies cannot deliver a payload that was never in the bundle. **Offer neither `--force-workspace` nor `--target-path`, and no re-run:** the bundle is recorded as received by the end of this pull. Say the other machine's project files did not arrive and that a fresh push from that machine is the fix. Don't accuse the sender — every sesh-mover before 0.6.0 wrote exactly this bundle whenever a snapshot happened to carry no files (an empty project, or a `hubignore` broad enough to drop the whole tree); a damaged or hand-made bundle says the same thing.
     - both absent and `workspaceDeclaredMissing` not set, with a warning naming `--force-workspace`: this is the genuine skip — the project directory already has content and no shared generation was available to merge against, so the workspace payload was **not** applied (sessions still imported normally). Offer `--target-path <fresh-dir>` **first**: it unpacks elsewhere and destroys nothing. Only offer `--force-workspace` after using AskUserQuestion to confirm, and say plainly that it unpacks the hub's copy over the current directory, overwriting any file of the same name — it is not a merge. Never add it automatically. **Present either as an attempt, not a guarantee, and say what decides it:** this pull imported the thread's sessions and recorded its bundles, so a repeat can come back "already up to date" or "the latest copy of this thread is already local" without ever reaching the payload. (`--target-path <fresh-dir>` reads its received-bundle bookkeeping from the fresh directory, which has none, so it clears that check — but both still have to clear thread resolution, which this pull's own import may have just tipped toward this machine.) If a re-run is refused, nothing is lost: the payload is still in the bundle on the hub, and both flags apply to the next payload that machine pushes. **Say that this repeats until one payload is applied:** a skip records no generation (recording one for files that were never written is what would make a later merge treat the whole payload as deleted), so the next payload from that machine finds nothing to merge against either and skips identically. It is not a transient first-contact case — it is the standing state for this pair of machines, and every workspace bundle pushed before 0.6.0 lands here on its first 0.6.0 pull because it declares no ancestor at all. One deliberate application (either flag, on any later pull) establishes the shared generation and the merge takes over from then on.
   - **Carried uncommitted work — branch on `carryApplied`, never on the warning text.** A git project's bundle can carry the other machine's *uncommitted* changes (a `git diff HEAD` patch plus untracked files). `carryAvailable` describes what was carried; `carryApplied` says what became of it. On every decline `carryApplied.savedCommands` says whether the saved `README.md` actually holds the commands to finish by hand — it is `false` for the two that withhold them on purpose (`unsafe-payload`, and an `apply-failed` whose patch could not be parsed), so don't send the user there looking for commands:
     - `carryApplied.applied` is `true`: the working tree here **was changed** — `filesChanged` files from the patch, `untrackedCopied` files copied. Say that they are uncommitted here too (`git status` shows them) and that `git checkout -- .` undoes the patch half. Report `collisions` (your file was kept, theirs written beside it as `*.incoming-*` — tell the user to delete those once reconciled, or a later push carries them), `blocked` (nothing was written near those paths), and `refused` (see the security bullet below).
     - `carryApplied.applied` is `false` with `reason: "not-requested"`: `--apply-carry` was not passed, so nothing touched the tree. The payload is **saved** at `carryApplied.savedTo` with a `README.md` holding the exact commands. **Do not offer to re-run the pull with `--apply-carry`** — this pull has already recorded the bundle as received, so the re-run answers "already up to date". The two real options are: apply it by hand from `savedTo` (its README is written for that, and the flags in it matter — `apply.whitespace=fix` alone will silently strip whitespace the patch adds), or pass `--apply-carry` on a *future* pull. Mention that the saved copy can simply be deleted if it isn't wanted; sesh-mover keeps only the most recent few.
     - `carryApplied.applied` is `false` with `reason: "wrong-base"`, `"dirty-tree"`, `"in-progress"`, `"not-git"`, `"no-git"` or `"apply-failed"`: the guards refused it and the payload was saved at `savedTo` instead. Relay `detail` — it names the actual state (the commit this machine is on versus the one the changes were taken against, uncommitted changes of the user's own, a rebase in progress). These are the user's to resolve (commit or stash, check out the base commit, finish the rebase) and then apply from `savedTo`; again, **never** by re-running the pull. Two of these are about *this* machine rather than the user's workflow, and `detail` carries git's own words for them: a `not-git`/`no-git` whose detail is a git error (an unparseable `.git/config`, `safe.directory` ownership, no git on `PATH`) is a local setup problem to fix first — it is **not** a judgement on the payload. And an `apply-failed` whose detail says the patch *could not be parsed* means the bundle is damaged or truncated rather than the tree being in the wrong state: the saved README gives no apply command for it, and the fix is a fresh push from the other machine, not anything local.
     - `carryApplied.applied` is `false` with `reason: "unsafe-payload"`: the patch tried to write plugin or VCS internals (`.claude-sesh-mover/hubinclude` decides what this machine's *next* push uploads; the project-scope `config.json` decides where the hub is) or to create a symbolic link. It was refused **whole**, not partly applied, and saved for inspection. Same rule as `workspaceRefused`: report it without accusing the sender, and tell the user to read the saved copy before doing anything with it.
     - `carryApplied.savedTo` is `null` on any of those: even the saved copy could not be written. Say plainly that the only remaining copy is inside the bundle on the hub (the warning names the file) and that it must be extracted by hand.
     - `carryAvailable` present but `carryApplied` **absent entirely**: the bundle's manifest declared carried changes that the bundle does not actually contain, so there was nothing to apply and nothing to save. Nothing touched the tree. Report it as a damaged or non-sesh-mover bundle (the warning says so) and say that the sender's uncommitted work did not arrive — re-pushing from that machine is the fix. Do not describe this as a decline, and do not look for `savedTo`: there is no payload on this machine at all.
     - Because this decision cannot be revisited for a given bundle, it is worth **asking before step 5** whenever the user is pulling into a git project and expects work-in-progress from the other machine — passing `--apply-carry` on the step-5 invocation is the only way the changes land in the tree directly.
   - `success: true` with a non-empty `appended` array: the continuation was **spliced onto the end of a session this machine already had** (`appended[i].baseSessionId`), adding `entriesAppended` entries. Report it as "your existing session now continues" and point at `claude --resume <baseSessionId>` — that session really does hold the whole conversation, so the separate-session caveat below does **not** apply to it. Note that appended sessions are not listed in `importedSessions` (nothing new was created); a single pull can both append one thread's continuation and import other bundles, so check both fields.
     **Check `divergence` before using this wording.** An adoption also reports through `appended` (same shape, same `baseSessionId`), but it was a *replacement*, not a continuation: the session's own tail was cut off at the shared anchor and the hub's branch put in its place. If `divergence.resolution` is `"adopt-hub"`, report it as the adoption branch below describes and never as "your existing session now continues" — that session no longer contains the entries the user wrote locally; the preserved session does.
   - `success: true` with a `divergence` object: the thread was extended on **both** sides of a common point (`divergence.anchorUuid`) — your local session `divergence.localSessionId` added `localEntriesSinceAnchor` entries, the hub's copy added `hubEntriesSinceAnchor`. Neither continues the other, so this is a genuine fork and there is no safe automatic answer. With the step-5 invocation `divergence.resolution` is `"skip"`, meaning **nothing has happened yet**. Present the fork (both entry counts, `localLastActiveAt` vs `hubLastActiveAt`) and ask with AskUserQuestion, spelling out the consequences **before** they pick:
     - **Keep both** (`--on-divergence fragment`) — your session is left exactly as it is and the hub's branch is imported as a separate session. Nothing is lost, but the conversation stays split across two transcripts and neither one holds both halves.
     - **Adopt the hub's branch** (`--on-divergence adopt-hub`, only offer this when `divergence.adoptAvailable` is `true`) — your session `localSessionId` is rewritten to be the shared history plus the hub's branch, and your local branch is preserved **in full** (shared history + your entries) as a brand-new session that is registered and resumable. Two consequences to state explicitly: (1) the preserved session has no thread mapping, so the **next push publishes it as its own thread** on the hub; (2) adoption **truncates** `localSessionId` — if a Claude Code session is open on it, its next message chains onto the hub's branch instead of the user's own. The preserved copy is the transcript only: side files (subagent transcripts, tool-result blobs, file-history backups) stay attached to `localSessionId`, so mention that if the user asks what the preserved session is missing.
       **Liveness:** compare `divergence.localLastActiveAt` to now. If it is within the last 5 minutes the CLI will **refuse** the adoption, so present the option as "written Ns ago — exit any Claude Code session on that transcript first, then re-run with `--on-divergence adopt-hub --force-append`" rather than as a plain choice. Only add `--force-append` after the user has confirmed that session is closed; here it means "I accept the truncate", not the live-base override it means on a plain append. A refusal applies and records **nothing** (it comes back as `resolution: "skip"`), so it is a round trip, not a dead end: the forced re-run still reaches the adoption, and `--on-divergence fragment` is still reachable too.
     - **Decide later** (re-run nothing) — the skip already leaves the hub bundle unapplied and unrecorded, so the same pull can be run again at any time with either answer.

     Then re-run the exact step-5 command with the user's `--on-divergence <mode>`, using `--thread "<id>"` (not `--latest`) so the follow-up cannot resolve to a different thread. When `divergence.adoptAvailable` is `false`, adopt-hub is not on the table: the shared anchor isn't in the local session at all (compacted or unrelated history), so there is no point to splice at — offer only "keep both" and "decide later", and say why. In that case `localEntriesSinceAnchor` is `0` because there is nothing to measure from, **not** because the local session is empty or unchanged; don't present it as a count. On the re-run, `divergence.resolution` reports what actually happened: `"adopt-hub"` with `preservedSessionId` set means the adoption succeeded (report both `claude --resume <localSessionId>` for the adopted thread and `claude --resume <preservedSessionId>` for their own branch); `"fragment"` when the user asked for `adopt-hub` means it was refused or failed and the accompanying warning says why — the local session was left untouched in that case.
   - `success: true` with a warning about a continuation that "could not be appended" or was "not spliced": the splice was refused and the content arrived as a separate session instead (handled by the next bullet). Three causes, each relayed differently: (a) a base modified in the last 5 minutes, i.e. it looks like a live Claude Code session — **do not offer `--force-append` here.** The content has already been imported and this bundle recorded, so a re-run answers "already up to date" and never reaches the splice; the flag only helps on a pull that still has the bundle to apply. Say what happened (nothing local was touched, the messages are in a separate session) and give the preventive advice instead: close the Claude Code session writing to that transcript before pulling, and future continuations of the thread splice in; (b) a chain mismatch — the local session isn't the entry this continuation follows, so there is nothing to do and `--force-append` will **not** help (it never skips the chain guard); (c) a failed integrity check — the bundle's content doesn't match its manifest hash, so it was refused rather than welded into an existing transcript. For (c), tell the user the hub file is likely damaged or still syncing, that the imported separate session may be incomplete, and that re-pushing from the source machine is the fix. `--force-append` is not a remedy for **any** of the three here — its one live use is the divergence flow in the bullet above, where a refusal records nothing and the re-run genuinely reaches the adoption.
   - `success: true`, `localSessionId` is a string and `appended` is absent/empty: report `importedSessions`/`skippedSessions` and tell the user the session is registered and resumable with `claude --resume <localSessionId>`.
     **Honesty requirement (always include this when reporting a resumable pulled session that was NOT appended):** the pulled session is a **separate, new session** on this machine — never claim the full original conversation now lives inside it. If it continues earlier work, its first entry is a synthetic continuation header explaining where the prior messages live (on the originating machine, or in another local session id if this machine already had them). The result JSON does not tell you whether this pull was a full session or a continuation, so state it conditionally ("if this continues earlier work, you'll see a header at the top explaining where the earlier messages are"). Optionally, to tailor the message precisely: read the first line of the new session's JSONL (`<configDir>/projects/<encoded-project-path>/<localSessionId>.jsonl`) and check whether its message content starts with `[sesh-mover continuation]` — if yes, it's a continuation and you can describe the header definitively; if no, it's a full transcript.
   - `success: true`, `localSessionId` is `null`: the pulled content already existed locally, but sesh-mover couldn't identify which existing session it corresponds to (a bookkeeping edge case, explained further in the accompanying warning). There is nothing new to resume in this case — say so plainly, and mention that a future push from this machine will re-establish the thread mapping.
   - If `workspaceUnpacked` is non-null, report its `path` and `fileCount`.
   - Any other `success: false` you haven't handled above (e.g. "no thread found", "already local", "already up to date"): report `error`/`suggestion` and stop — these are plain mistakes (bad thread id, nothing new to pull), not conditions to retry automatically. **One exception in kind:** an "already up to date with the source machine" whose `error` goes on to say the thread **could not be pulled whole** is the split-history condition above, reached on a thread this machine already holds its half of. It is not a mistake and there is nothing to retry — relay it as the same limitation, and mention that `whereis` reports it per thread as `unfetchableBundles`.

7. Report a final summary: thread pulled, sessions imported/skipped/appended, workspace outcome, and the resumable session id (or, if `null`, why there isn't one). If a divergence was resolved, say which way and name every session the user can now resume.

**Invocation:** `${CLAUDE_PLUGIN_ROOT}` is set by Claude Code inside plugin command execution — use it as-is in the bash invocations above; do not search the plugin cache. The flag set documented in this file (in both the main invocations and the conditional branches — `--project-id` for linking, `--target-path` for the bootstrap/relocate case, `--force-workspace` for the confirmed-merge retry, `--apply-carry` for applying carried uncommitted work into the working tree, `--latest` as the `--thread` alternative, `--force-append` for the confirmed live-base retry, `--on-divergence <fragment|adopt-hub|skip>` for the fork flow above, and `--no-append` to opt out of splicing entirely) is authoritative — do not run the CLI with `--help` or with no arguments to discover its surface. `pull` also accepts `--progress` (NDJSON progress events on stderr) — it's oriented at humans running the CLI directly; don't pass it from this command flow.
