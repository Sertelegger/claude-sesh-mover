---
name: pull
description: Pull a project's thread from the cross-machine hub into this machine
---

You are running the sesh-mover pull command. Follow these steps:

1. Check hub configuration first:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" hub status
   ```
   - If `hubPath` is `null`, tell the user no hub is configured yet and point them at `/sesh-mover:hub-init`. Stop.
   - If `reachable` is false, surface the `warnings` and stop.

2. Determine the project path:
   - Normal case (this project already exists locally — you're pulling an update or a thread from another machine into it): use cwd as `--project-path`, no `--target-path` needed.
   - Bootstrap case (this project doesn't exist on this machine at all yet — first time pulling it here): ask the user for the destination directory (AskUserQuestion or free text) and pass it as `--target-path <dir>` **in addition to** `--project-path` (still cwd, or wherever the user is running the command from — it drives hub project identity/linking, while `--target-path` is where the session files and workspace snapshot actually land). Don't conflate the two flags; they can point at different places.

   **`--target-path` links the directory it points at.** A pull plants `.sesh-mover-project.json` in the target, and being linked to a hub project is the consent gate for the default-on SessionEnd auto-push — so a directory used purely to *look* at a payload becomes one that uploads itself (and, for a git project, its uncommitted work) at the end of the next Claude Code session run there. That is what you want for the bootstrap case above and what you almost certainly do not want for a throwaway inspection directory. Whenever you suggest `--target-path <fresh-dir>` as a way to see something without touching this project, say so in the same breath and tell the user that deleting the `.sesh-mover-project.json` file inside that fresh directory un-links it again — that one root dotfile is the whole gate, not the `.sesh-mover/` directory beside it.

3. Run without a thread selector first, to discover what's available:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" pull --project-path "<cwd>" --source-config-dir "<config-dir>" [--project-id <id>]
   ```
   (only include `--project-id` if the user is deliberately linking to a specific hub project that isn't linked locally yet)

4. Parse the result and branch:
   - `reason: "unlinked"`: same shape as push — present `linkCandidates` as a pick-list, but point the user at `/sesh-mover:push` to link or create the hub project first (pull can also link directly via `--project-id`; offer to re-run step 3 with `--project-id <picked>` if the user prefers not to switch commands).
   - `reason: "no-such-project"`: the `--project-id` you passed names no project on this hub (`requestedProjectId` echoes it back). Nothing was pulled and nothing was written or linked. Present `linkCandidates` as a pick-list and re-run step 3 with a corrected `--project-id`; an empty `linkCandidates` means this hub has no projects yet, so the other machine has to push first.
   - `reason: "hub-unreachable"`: the configured `hub.path` could not be read at all. `hubState` says which — `"no-directory"` (nothing there: an unmounted share, a synced folder that hasn't appeared on this machine yet, or a typo in `hub.path`), `"not-a-hub"` (a directory is there but it carries no `hub.json`, so it was never `hub init`-ed or points at the wrong folder), or `"unresponsive"` (mounted but hung — a filesystem call against it timed out; `hub.path` is almost certainly right, so offer to reconnect or force-unmount the filesystem rather than to edit config; it takes the hub I/O timeout to detect and exits by signal rather than with a status code, so read the complete JSON body and don't report it as a crash). **Nothing was written and nothing was linked** — this is checked before any hub write, so re-running is always safe. Don't offer `linkCandidates` here: the hub couldn't be listed, so an empty candidate list means nothing. Ask the user to mount/connect the share or check `hub.path` (`configure --show`), then offer to re-run the same invocation. The result deliberately does **not** echo the path back.
   - `reason: "lock-busy"`: wait a few seconds and retry the same invocation once; if still busy, stop and report it.
   - `reason: "project-retired"`: a machine has retired this project on the hub. **Nothing was pulled, nothing local changed, and no link was written** — the refusal happens before any of that. What to say next depends entirely on `retiredByThisMachine`:
     - `true` — the user retired it from this machine. Offer `/sesh-mover:hub-retire --undo` to take the assertion back, or a one-off `--ignore-retirement` on this same pull. Mention `deleteEligibleAt`: that is when `/sesh-mover:hub-delete` here stops refusing.
     - `false` — another machine did, named in `retiredByMachineName` (`retiredByMachineId` when the hub has no record of its name), with any `retirementReason` it recorded. **Do not offer `--undo`**: retraction is asymmetric, and only the asserting machine can withdraw a tombstone. What this user can do is (a) nothing — their own sessions are untouched, since retirement only affects the shared hub copy; (b) re-run this pull with `--ignore-retirement` if they still need work that is on the hub, and say plainly that `deleteEligibleAt` is the deadline after which that machine may delete it for good; (c) `/sesh-mover:hub-unlink` if they are done with this project here, which also disarms its session-end auto-push.
   - `pickRequired: true`: present `threads` as a numbered list — slug, latest machine name, `lastActiveAt`, `messageCount`, and whether `pullNeeded` is true. Ask the user which thread to pull (AskUserQuestion), or offer "pull whichever most needs updating" which maps to `--latest` instead of `--thread <id>`.
   - Any other `success: false` (no `reason` field): report `error`/`suggestion` and stop.

5. Run the real pull with the chosen thread, always with `--on-divergence skip`:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" pull --project-path "<cwd>" --source-config-dir "<config-dir>" --thread "<id>" --on-divergence skip [--target-path "<dir>"] [--project-id <id>]
   ```
   (substitute `--latest` for `--thread "<id>"` if that's what the user picked)

   `--on-divergence skip` is inert on an ordinary pull — it only does anything when the thread was extended on **both** machines from the same point, which is the one situation where the right answer is the user's to give. Skipping applies and records nothing, so step 6's divergence branch can put the real choice in front of them and then re-run. Without it the default (`fragment`) would already have imported the hub's branch as a second session, and adopting it afterwards is no longer possible: the bundle is recorded as received, so the re-run reports "already up to date".

6. Parse the result and branch:
   - `reason: "not-yet-synced"`: tell the user the hub folder's sync client (OneDrive/Dropbox/Syncthing/etc.) hasn't finished copying these files to this machine yet. List the `missing` files, wait a moment, and offer to retry the same invocation.
   - `success: false` with an error mentioning the workspace target already has content: this happens specifically when you passed an explicit `--target-path` that isn't empty. Nothing was written. Use AskUserQuestion to confirm with the user **before** re-running with `--force-workspace` appended — never add it automatically — and label the options for what the flag actually does: "overwrite files of the same name in that directory" / "cancel". It is **not** a merge and never becomes one: this error only happens when no shared generation was found, which is the exact condition that makes a 3-way merge impossible, and `--force-workspace` skips the merge even when one is available. Files the payload does not contain are left alone; files it does contain replace yours.
   - **Chain-assembly disclosures — branch on the RESULT FIELDS, never on the warning text.** A pull **assembles** a thread across every machine's bundle list, following the entry each bundle records itself as continuing from, so a conversation continued on two other machines arrives here whole rather than in halves. What assembly still could not deliver, it names — and each condition is its own field with its own answer, so report the one that is present instead of a generic "part of this thread is missing". Every field below is absent on an ordinary pull, and each is emitted together with the warning that explains it:
     - `unfetchableBundles`: which **machines** hold bundles this pull did not fetch (`machineName` or `machineId`, and how many `bundleIds` each holds). It normally rides alongside one of the condition fields below; in the rare case where the walk could not account for those bundles at all, it appears alone and the honest report is exactly that — those machines list bundles the assembled chain does not reach, and this pull cannot say why.
     - `chainGaps`: a bundle's recorded link (`anchorEntryUuid`) names an entry no bundle on the hub carries — something between two bundles is genuinely missing. The chain was applied up to that point and stopped there; it never resumes past a gap, because the resulting transcript would be non-contiguous and the splice guard would refuse it anyway. `strandedBundleIds` is what that one gap holds back. A fresh push from the machine that still holds the missing piece is the fix.
     - `parkedBranches`: the thread forks on the hub and this pull followed one side (`followedBundleId`). The other branch was left untouched and is still on the hub. This is **not** the local-vs-hub `divergence` below — that one is about the user's own transcript and has a policy flag; this one is two branches on the hub and has neither.
     - `unplaceableBundles`: bundles that belong to no chain. `preAssembly: true` means pushed **before** this release recorded chain links, so the link was never written — that bundle is **not missing**, it is sitting right there, and the machine still holding that session re-links it the next time it pushes. Never report one as a gap. `preAssembly: false` means an index declaring a continuation of nothing, which no sesh-mover push can produce: report it as a damaged or hand-edited index, and do not accuse anyone.
     - `unwalkedRoots`: the thread has more than one independent starting point and this pull walked one of them. That is **ordinary, not damage** — a session that was compacted, truncated or rolled back is re-pushed whole under the same thread id — and two starting points can never be joined into one history, because a compaction rewrites the very entry uuids a link would need.
     - `advertisedUnshipped`: a machine's index advertises a thread head it never pushed. That work is not on the hub at all, so no pull of any kind reaches it; it arrives once that machine pushes, which its SessionEnd auto-push does by default. This field appears only on a pull that applied nothing, where it is frequently the whole answer to "why did this do nothing".

     **Offer no flag and no `hub reindex` for any of them:** there is no `--from-machine`, `--thread` and `--target-path` resolve to the same single source, and `hub reindex` only rebuilds *this* machine's index from *its own* bundles. What changes any of these outcomes is on the hub — a bundle pushed, a link recorded — never an argument to this command, so do not offer a re-run as a remedy. Say plainly that nothing is lost: every bundle stays on the hub. This branch also **overrides the reassurance in every branch below**: however many sessions were imported or appended, do not tell the user this machine now holds the whole conversation, and do not present `whereis`'s "current" as meaning it does.
   - **`success: true` with `nothingToApply: { reason }`:** this pull worked the thread's history out, found one of the conditions above, and correctly applied nothing. `importedSessions`/`skippedSessions`/`appended` are empty and `localSessionId` is `null` because nothing landed, not because anything failed. There is **no `error` and nothing to retry** — relay `reason` as the answer, add whichever condition field is set, and do not present it as a failure.
   - **Workspace payload — branch on the RESULT FIELDS, never on the warning text.** A warning can name `--force-workspace` in *both* directions now, so its presence alone tells you nothing:
     - `workspaceMerge` present: the payload **was applied**, as a 3-way merge against the last generation this machine shared with the sender. Report what it decided from the report's own arrays — `conflicted` files have `<<<<<<< local` markers in them and the user must resolve those by hand; `sidecars` are `*.theirs-*` files left beside binaries and unmergeable files (tell them to delete those once reconciled, or they get pushed back to the hub); `localDeleted` files were **withheld**, and the accompanying warning explains why and names both remedies. Do **not** describe this pull as "skipped".
     - `workspaceMerge` absent and `workspaceUnpacked` non-null: the payload was unpacked wholesale (an empty project directory, or `--force-workspace`).
     - `workspaceRefused` non-empty (can accompany either of the two branches above): the payload carried paths that can **never** be applied — `.git`, or a path sesh-mover owns (`.sesh-mover/`, `.sesh-mover-include`, `.sesh-mover-ignore`, `.sesh-mover-project.json`), at some depth, in some casing. Nothing from them was written, and a directory entry stands for everything under it. Report the paths and say what the risk was: `.sesh-mover-include` decides what this machine's *next* push uploads, so a payload writing it could have redirected that. Do **not** accuse the sender — a sesh-mover older than this guard, on a case-insensitive filesystem, legitimately shipped a `.GIT` store — say only that a current sesh-mover never puts those in a bundle, so it came from an older version, was damaged in transit, or wasn't produced by sesh-mover. That is a rule on this machine, not a fault: the remedy is to edit `.sesh-mover-ignore` (or `.sesh-mover-include`) and re-pull a later payload, or to take the hub's copy wholesale with `--force-workspace`, which does not honor that veto.

This is field-identical to the skip below apart from this flag — check it *first*, because that skip's remedies cannot deliver a payload that was never in the bundle. **Offer neither `--force-workspace` nor `--target-path`, and no re-run:** the bundle is recorded as received by the end of this pull. Say the other machine's project files did not arrive and that a fresh push from that machine is the fix. Don't accuse the sender — every sesh-mover before 0.6.0 wrote exactly this bundle whenever a snapshot happened to carry no files (an empty project, or a `.sesh-mover-ignore` broad enough to drop the whole tree); a damaged or hand-made bundle says the same thing.

Ordering them the other way round reads as "try the safe one first, then the other if it doesn't work", and the safe one cannot work for this directory at all. **Present either as an attempt, not a guarantee, and say what decides it:** this pull imported the thread's sessions and recorded its bundles, so a repeat can come back "already up to date" without ever reaching the payload. If a re-run is refused, nothing is lost: the payload is still in the bundle on the hub, and both flags apply to the next payload that machine pushes. **Say that this repeats until one payload is applied *here*:** a skip records no generation (recording one for files that were never written is what would make a later merge treat the whole payload as deleted), so the next payload from that machine finds nothing to merge against either and skips identically.    - **Carried uncommitted work — branch on `carryApplied`, never on the warning text.** A git project's bundle can carry the other machine's *uncommitted* changes (a `git diff HEAD` patch plus untracked files). `carryAvailable` describes what was carried; `carryApplied` says what became of it. On every decline `carryApplied.savedCommands` says whether the saved `README.md` actually holds the commands to finish by hand — it is `false` for the two that withhold them on purpose (`unsafe-payload`, and an `apply-failed` whose patch could not be parsed), so don't send the user there looking for commands:

Say that they are uncommitted here too (`git status` shows them) and that `git checkout -- .` undoes the patch half. Report `collisions` (your file was kept, theirs written beside it as `*.incoming-*` — tell the user to delete those once reconciled, or a later push carries them), `blocked` (nothing was written near those paths), and `refused` (see the security bullet below).
     - `carryApplied.applied` is `false` with `reason: "not-requested"`: `--apply-carry` was not passed, so nothing touched the tree. The payload is **saved** at `carryApplied.savedTo` with a `README.md` holding the exact commands. **Do not offer to re-run the pull with `--apply-carry`** — this pull has already recorded the bundle as received, so the re-run answers "already up to date". The two real options are: apply it by hand from `savedTo` (its README is written for that, and the flags in it matter — `apply.whitespace=fix` alone will silently strip whitespace the patch adds), or pass `--apply-carry` on a *future* pull. Mention that the saved copy can simply be deleted if it isn't wanted; sesh-mover keeps only the most recent few.
     - `carryApplied.applied` is `false` with `reason: "wrong-base"`, `"dirty-tree"`, `"in-progress"`, `"not-git"`, `"no-git"` or `"apply-failed"`: the guards refused it and the payload was saved at `savedTo` instead. Relay `detail` — it names the actual state (the commit this machine is on versus the one the changes were taken against, uncommitted changes of the user's own, a rebase in progress). These are the user's to resolve (commit or stash, check out the base commit, finish the rebase) and then apply from `savedTo`; again, **never** by re-running the pull. Two of these are about *this* machine rather than the user's workflow, and `detail` carries git's own words for them: a `not-git`/`no-git` whose detail is a git error (an unparseable `.git/config`, `safe.directory` ownership, no git on `PATH`) is a local setup problem to fix first — it is **not** a judgement on the payload. And an `apply-failed` whose detail says the patch *could not be parsed* means the bundle is damaged or truncated rather than the tree being in the wrong state: the saved README gives no apply command for it, and the fix is a fresh push from the other machine, not anything local.

It was refused **whole**, not partly applied, and saved for inspection. Same rule as `workspaceRefused`: report it without accusing the sender, and tell the user to read the saved copy before doing anything with it.
     - `carryApplied.savedTo` is `null` on any of those: even the saved copy could not be written. Say plainly that the only remaining copy is inside the bundle on the hub (the warning names the file) and that it must be extracted by hand.
     - `carryAvailable` present but `carryApplied` **absent entirely**: the bundle's manifest declared carried changes that the bundle does not actually contain, so there was nothing to apply and nothing to save. Nothing touched the tree. Report it as a damaged or non-sesh-mover bundle (the warning says so) and say that the sender's uncommitted work did not arrive — re-pushing from that machine is the fix. Do not describe this as a decline, and do not look for `savedTo`: there is no payload on this machine at all.

All four are absent when no bundle carried a memory or plans layer.

     - **Adopt the hub's branch** (`--on-divergence adopt-hub`, only offer this when `divergence.adoptAvailable` is `true`) — your session `localSessionId` is rewritten to be the shared history plus the hub's branch, and your local branch is preserved **in full** (shared history + your entries) as a brand-new session that is registered and resumable. Two consequences to state explicitly: (1) the preserved session has no thread mapping, so the **next push publishes it as its own thread** on the hub; (2) adoption **truncates** `localSessionId` — if a Claude Code session is open on it, its next message chains onto the hub's branch instead of the user's own. The preserved copy is the transcript only: side files (subagent transcripts, tool-result blobs, file-history backups) stay attached to `localSessionId`, so mention that if the user asks what the preserved session is missing.
       **Liveness:** compare `divergence.localLastActiveAt` to now. Only add `--force-append` after the user has confirmed that session is closed; here it means "I accept the truncate", not the live-base override it means on a plain append. A refusal applies and records **nothing for the diverged bundle or any later one** — it comes back as `resolution: "skip"` and it stops the chain there, leaving every later bundle unfetched (a warning says how many). So it is a round trip, not a dead end: the forced re-run reaches the adoption. It is *not* a guarantee that the pull was a no-op — bundles earlier in the same chain may already have been applied and recorded, so check `appended`/`importedSessions` as above before describing it that way.
     - **Decide later** (re-run nothing) — the skip leaves the diverged bundle and everything behind it unapplied and unrecorded, so the same pull can be run again at any time with either answer. It does not undo what earlier bundles of the chain already landed.

     Then re-run the exact step-5 command with the user's `--on-divergence <mode>`, using `--thread "<id>"` (not `--latest`) so the follow-up cannot resolve to a different thread. When `divergence.adoptAvailable` is `false`, adopt-hub is not on the table: the shared anchor isn't in the local session at all (compacted or unrelated history), so there is no point to splice at — offer only "keep both" and "decide later", and say why. In that case `localEntriesSinceAnchor` is `0` because there is nothing to measure from, **not** because the local session is empty or unchanged; don't present it as a count. On the re-run, `divergence.resolution` reports what actually happened: `"adopt-hub"` with `preservedSessionId` set means the adoption succeeded (report both `claude --resume <localSessionId>` for the adopted thread and `claude --resume <preservedSessionId>` for their own branch); `"fragment"` when the user asked for `adopt-hub` means it was refused or failed and the accompanying warning says why — the local session was left untouched in that case.
   - `success: true` with a warning about a continuation that "could not be appended" or was "not spliced": the splice was refused and the content arrived as a separate session instead (handled by the next bullet). Three causes, each relayed differently: (a) a base modified in the last 5 minutes — **do not offer `--force-append` as a re-run of this pull.** The content has already been imported and this bundle recorded, so a re-run answers "already up to date" and never reaches the splice. Two things to get right when relaying it. First, **do not report this as a live Claude Code session**: the guard cannot tell one from sesh-mover's own earlier pull, whose import stamps that transcript's mtime just the same (the self-write exemption only covers the pull doing the asking), so a pull a few minutes after another one lands here with nothing running anywhere. Say the age and both possibilities, exactly as the warning does. Second, `--force-append` is foreclosed for *this* bundle, not for the thread: passing it on the **next** pull of the same thread does splice that pull's continuation. So give the preventive advice first (close any Claude Code session writing to that transcript before pulling) and offer `--force-append` only as a flag for a later pull, never as a retry of this one; (b) a chain mismatch — the local session isn't the entry this continuation follows, so there is nothing to do and `--force-append` will **not** help (it never skips the chain guard); (c) a failed integrity check — the bundle's content doesn't match its manifest hash, so it was refused rather than welded into an existing transcript. For (c), tell the user the hub file is likely damaged or still syncing, that the imported separate session may be incomplete, and that re-pushing from the source machine is the fix. `--force-append` is not a remedy for **any** of the three here — its one live use is the divergence flow in the bullet above, where a refusal records nothing and the re-run genuinely reaches the adoption.
   - `success: true`, `localSessionId` is a string and `appended` is absent/empty: report `importedSessions`/`skippedSessions` and tell the user the session is registered and resumable with `claude --resume <localSessionId>`.
     **Honesty requirement (always include this when reporting a resumable pulled session that was NOT appended):** the pulled session is a **separate, new session** on this machine — never claim the full original conversation now lives inside it. If it continues earlier work, its first entry is a synthetic continuation header explaining where the prior messages live (on the originating machine, or in another local session id if this machine already had them). The result JSON does not tell you whether this pull was a full session or a continuation, so state it conditionally ("if this continues earlier work, you'll see a header at the top explaining where the earlier messages are"). Optionally, to tailor the message precisely: read the first line of the new session's JSONL (`<configDir>/projects/<encoded-project-path>/<localSessionId>.jsonl`) and check whether its message content starts with `[sesh-mover continuation]` — if yes, it's a continuation and you can describe the header definitively; if no, it's a full transcript.
   - `success: true`, `localSessionId` is `null`: the pulled content already existed locally, but sesh-mover couldn't identify which existing session it corresponds to (a bookkeeping edge case, explained further in the accompanying warning). There is nothing new to resume in this case — say so plainly, and mention that a future push from this machine will re-establish the thread mapping.
   - If `workspaceUnpacked` is non-null, report its `path` and `fileCount`.
   - Any other `success: false` you haven't handled above (e.g. "no thread found", "already local", "already up to date"): report `error`/`suggestion` and stop — these are plain mistakes (bad thread id, nothing new to pull), not conditions to retry automatically. **One exception in kind:** an error whose text goes on to say a thread **could not be pulled whole** (or "not whole here") is the residual chain-assembly case — another machine lists bundles the assembled chain does not reach, and the walk could not work out why, so there is no condition field to go with it. It is not a mistake and there is nothing to retry; relay it as it stands, say nothing is lost, and mention that `whereis` reports it per thread as `unfetchableBundles`. When the walk *could* name the condition the same situation comes back as `success: true` with `nothingToApply` instead — that is the branch above, not this one.

7. **Offer to merge the conflicting memories** — only if `memoryConflicts` is non-empty and every entry you act on has a `parkedAs`. This step is yours, not the CLI's: `dist/cli.js` does pure filesystem work and never calls a model, so the semantic merge happens here, in the session the user is already paying for, where its cost is visible and it can be confirmed before it happens.

   **When there is nobody to confirm — do nothing.** The SessionEnd/SessionStart hooks drive `hub pull` with no user attached, and so does a scripted CLI run. What the CLI already did (yours kept, theirs parked, both indexed) is a **complete and correct outcome**, not a fallback that failed. Never merge without asking.

   The procedure is the one `/sesh-mover:import` step 11 documents and it is authoritative there — follow it rather than a paraphrase. In outline: size the conflicts in bytes and say the number before offering; offer per file (plus "All of them" / "None, leave them parked"); read both texts and classify every contradiction as `superseded` / `both-true-scoped` / `unresolved`; **any `unresolved` blocks the write** and is shown to the user instead of being decided; show the full proposed text and get an explicit yes; and on acceptance write the merged text to `<memoryDir>/<filename>`, save the **pre-merge local** text as `<memoryDir>/<stem>.pre-merge.md`, delete `<memoryDir>/<parkedAs>`, and remove only the `MEMORY.md` pointer line whose target was `<parkedAs>`.

   One thing differs here and it is worth saying to the user: on a pull the incoming text is still in the bundle **on the hub**, which deletes nothing, so the sender's copy is never at risk. The local pre-merge text is still the half that exists in exactly one place.

8. Report a final summary: thread pulled, sessions imported/skipped/appended, workspace outcome, the memory/plans outcome, and the resumable session id (or, if `null`, why there isn't one). If a divergence was resolved, say which way and name every session the user can now resume.

**Exit codes:** keep branching on the parsed JSON, not on `$?` — every branch above is decided from the body, and the codes only classify what the body already says. `0` a pull that applied something. `1` a bad invocation (`--on-divergence bogus`) or an unexpected failure. `2` a refusal that applied nothing: `unlinked`, `no-such-project`, `project-retired`, "already up to date"/"nothing to pull" — **and the pick-required listing, which is `success: true` and still exits `2`**, because it pulled nothing and is waiting to be told which thread. `3` not ready: `hub-unreachable`, `lock-busy`, `not-yet-synced`, the class where the same invocation is expected to work once the share is mounted, the lock is released, or the sync finishes. See "Exit Codes" in the skill doc for the full four-class table.

**Invocation:** `${CLAUDE_PLUGIN_ROOT}` is set by Claude Code inside plugin command execution — use it as-is in the bash invocations above; do not search the plugin cache. The flag set documented in this file (in both the main invocations and the conditional branches — `--project-id` for linking, `--target-path` for the bootstrap/relocate case, `--force-workspace` for taking the hub's copy over the current directory — an overwrite, never a merge, and the only flag that ends a repeating workspace skip *here*, `--apply-carry` for applying carried uncommitted work into the working tree, `--latest` as the `--thread` alternative, `--force-append` for the divergence flow's confirmed-truncate adoption, and — scoped to a *later* pull of the same thread, never as a retry of the one that just declined — for overriding the plain append's liveness guard (see the liveness bullets above), `--on-divergence <fragment|adopt-hub|skip>` for the fork flow above, `--ignore-retirement` for the `project-retired` branch only — an explicit, one-off override of a gate somebody else put up, so never pass it pre-emptively — and `--no-append` to opt out of splicing entirely) is authoritative — do not run the CLI with `--help` or with no arguments to discover its surface. `pull` also accepts `--progress` (NDJSON progress events on stderr) — it's oriented at humans running the CLI directly; don't pass it from this command flow.
