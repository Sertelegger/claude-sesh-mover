---
name: import
description: Import a previously exported Claude Code session
---

You are running the sesh-mover import command. Follow these steps:

1. List available exports:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" browse --storage all --json
   ```

2. If no exports found, use AskUserQuestion to offer:
   - "Specify a file path" — ask the user for the path to an export directory or archive
   - "Cancel"
   Do NOT give a verbose explanation of where you searched unless the user asks.

3. If exports exist, present the list with: date, name, summary, source platform, source project path, session count. Format as a numbered table.

   These values come from each bundle's own `manifest.json` — for `.tar.gz`/`.tar.zst` archives just as for directory exports — so they describe the machine the bundle was *exported from*, not this one. That's what lets the user tell two archives apart without unpacking them, so always show source platform and source project path in the picker, not just the file name.

   **Degraded entries.** An entry with `metadataAvailable: false` has `null` for `exportedAt` / `sourcePlatform` / `sourceProjectPath` / `sessionCount` — its metadata could not be read, which is not the same as "the bundle has none". List it with its name and the `metadataError` in place of those columns rather than blank or zero values, and still offer it as a selectable option — but say it will likely fail until the cause is fixed. Import unpacks the real bundle and will work if the archive is intact *and readable on this machine*: a `.tar.zst` whose metadata could not be read for lack of `zstd` will fail to import for exactly the same reason, so offer the install below before the user selects it.

   **The zstd case.** A degraded entry whose **name ends in `.tar.zst`** is this case: `.tar.zst` bundles can only be read where the `zstd` binary is installed. Key off the name, not off the wording of `metadataError` — that field carries a free-text detail string that is not guaranteed to contain the word "zstd" (it usually will, and when it does it corroborates the name). Offer to install it rather than leaving the row unexplained:
   - macOS: `brew install zstd`
   - Debian/Ubuntu/WSL: `sudo apt-get install -y zstd`

   After a successful install, re-run step 1 so the picker shows the archive's real platform, path, date, and session count. zstd is also required to *import* a `.tar.zst` bundle, so this install is worth offering before the user picks one.

4. Use AskUserQuestion to let the user pick which export to import. Always include an extra option:
   - Each found export as a selectable option (name + summary)
   - "Specify a different file path" — for exports not in the standard locations

5. If the chosen export contains multiple sessions, use AskUserQuestion to ask:
   - "Import all sessions" (recommended)
   - "Pick specific sessions" — then present individual sessions as selectable options

   For an entry with `metadataAvailable: false`, `sessions` is `[]` — that means "unknown", not "empty". Skip this question and let the step 6 dry-run report what the bundle actually contains.

6. Run a dry-run first:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" import --from "<path>" [--session-id <ids>] --target-project-path "<cwd>" --target-config-dir "<config-dir>" --dry-run
   ```
   Start with no payload flags. The dry run still walks and counts a `workspace/` payload the bundle carries and still reports the `carry/` it declares, so the write set tells the user what is on offer without anyone having consented to it yet; step 8 is where the flags get added and the dry run gets re-run.

7. Present the dry-run results: version adaptations, any warnings, the path rewrites in `rewriteReport` (it is computed over the **first** session only — say "sample" rather than implying every session was previewed), and the memory plan.

   **`memoryPlan`** is one entry per file in the bundle's `memory/`, produced by the same function the real run executes. Read the verdicts and give the user one sentence *before* the import rather than a warning after it — that sentence is the whole defect this preview exists to prevent:
   - `copy` — absent here, will be written · `identical` — same bytes, no write
   - `index-union` — this is `MEMORY.md` and it differs; `added` lists the entries that will be appended to your index and `alreadyPresent` those already in it
   - `park` — a memory that differs on both sides; yours is kept and theirs is saved as `parkedAs` beside it
   - `keep-local` / `skip` — nothing will be written; `note` says why

   Aggregate it, e.g. *"11 memory files: 10 new, 1 index — 10 entries would be added to MEMORY.md; `notes.md` differs and would be parked as `notes.incoming.md` (you can merge it afterwards)."* Do **not** describe a `park` verdict as "would be merged": the merge is step 11, it costs tokens, and it has not been offered yet.

   `plansSkipped` is the count of plan files the bundle carries that the import will **not** write, because `plans/` is opt-in (see step 8). `planConflicts` on the dry run lists plans that already exist here with different content — only ever populated when `--include-plans` was passed. Either way the incoming plan stays in the bundle and nowhere else, so say so. `memorySkipped` is the same count for `memory/`, and it appears only when `--no-memory` was passed — that layer is on by default.

8. **Show the write set, then confirm.** Four of the six session layers land under a session id this import mints, so they can collide with nothing. Two do not — `memory/` and `plans/` — and a bundle can carry two **file payloads** besides, which land in the target *project* directory itself: `workspace/`, a copy of a whole working tree, and `carry/`, a git patch plus untracked files. The dry run has already computed what all of them will write, in `writeSet`. **Present that; do not derive it yourself and do not describe it in your own words.**

   **Say whose files these are.** A workspace or carry payload is never "the project files" — it is *someone's* project files, out of the bundle in front of you, and the provenance belongs in the same sentence as the action: *"this bundle would write 412 files from `<sourceProjectPath>` on `<sourcePlatform>` into `<target>`"*, not *"the project files would be restored"*. Before `--apply-workspace` existed, every payload this plugin applied came from the user's own other machine and travelled through a directory that user configured. This is the first one that can come from a bundle a stranger handed them, and the wording is the only place that difference shows up.

   - `writeSet.roots` — one per directory a payload can reach, reported even when the layer was declined. `scope: "project"` is the target project's own directory (`memory/`, and both file payloads); `scope: "machine"` is **shared by every project in this config dir** (`plans/`, which is why that layer is opt-in). `applied: false` means a flag declined the layer — say so, and give the count from `plansSkipped` / `memorySkipped` / `workspaceSkipped`. `enumerated: false` means this root's paths are in neither `entries` nor `total`; see below, and do not let a list that omits them read as complete. These paths, and `memoryDir` after the run, are the ones to quote: never derive either yourself, because deriving the memory path means re-implementing the project-path encoding in markdown.
   - `writeSet.entries` — one per path, each with a `layer` saying which payload it came from. `kind: "create"` is a new file; `kind: "park"` keeps the user's file and saves the incoming copy beside it under this name; **`kind: "index-append"` edits a file the user already has** — that is `MEMORY.md`, the file that decides what a future session reads, so never bury it in a list; and **`kind: "overwrite"` replaces a file the user already has, and the local copy does not survive anywhere.** Only `--force-workspace` produces one. Give every `overwrite` at least the prominence `index-append` gets, for a sharper reason: a park leaves both texts on disk and an append only adds lines, while this is the one kind in the set with nothing to go back to.
   - `writeSet.total` — the authoritative count of paths this run will write, and **it is no longer `entries.length`.** Workspace entries are capped at 200 while `total` keeps counting every path, and a `carry` root contributes to neither. So `entries` can be shorter than `total` for reasons that have nothing to do with what you chose to display.

   **Render `display`, never `path`.** Every entry carries both. `path` is the raw absolute destination and its last segment came out of the bundle, so it can carry a newline, an ANSI escape or an RTL override that restructures whatever you print it into. `display` is that same string already quoted and escaped — use it verbatim, in a code span. This holds for workspace entries too, and matters more there: every segment below the target path is bundle-chosen, and there are hundreds of them.

   **Bound the list, and take N from the field — never from a list.** Show at most 20 entries. When `writeSet.total` is larger, say *"…and N more"* with `N = writeSet.total − (how many you showed)`. **Never compute N from `entries.length`**: a bundle writing 400 project files gives you `total: 400` and 200 entries, so "and 180 more" would be wrong by exactly the amount that matters, and it would be wrong in the direction that understates. Show every `index-append` and every `overwrite` entry regardless of the bound; if the overwrites alone exceed it, say how many there are and show a sample rather than trimming to 20 in silence.

   **A root with `enumerated: false` must be disclosed as such, not rounded off.** `carry` is the only one, and its paths are absent from the list *and* from `total` — a patch's destinations are decided by git's own parse of that patch and by nothing else, so nothing here can predict them without becoming a second, worse parser. Say that, and then give the facts that stand in for the enumeration, because they are tighter than the workspace's rather than looser: applying a carry requires a **clean working tree at the exact commit it was captured against** (`carryAvailable.baseCommit`, on branch `carryAvailable.branch`), so unlike the workspace it cannot write over uncommitted work; `git checkout -- .` undoes the patch half whole; and `carryAvailable.untrackedCount` untracked files plus a `carryAvailable.patchBytes`-byte patch is its size.

   **If the workspace payload was refused, the dry run says so and nothing else ran.** `--apply-workspace` into a target project directory that already has content is an `ErrorResult` — no sessions imported, no project files written, the whole import declined before a byte moved — and it fires on the dry run too, so you see it here rather than after the sessions landed. Plugin state (`.sesh-mover-project.json` and friends) does not count as content, so a directory holding only that still reads as empty. There are exactly three remedies and all three are real: point `--target-project-path` at an empty directory; pass `--force-workspace` to unpack the payload **over** what is already there, replacing any file of the same name (it is a bootstrap copy and does not combine the two — say that, and get an explicit yes for it separately); or drop `--apply-workspace` and take the sessions only.

   Then use AskUserQuestion to confirm, and word the question as the thing it actually is:

   > "These `<writeSet.total>` paths will be written outside the imported session's own directory. Proceed?"

   When a `carry` root is present that sentence is incomplete on its own — add *"…plus whatever this bundle's git patch changes, which is not in that count."* Never fold the carry into the number to make one tidy sentence out of two true ones.

   Options: "Proceed with import" (recommended) / "Proceed and include plans" (only when `plansSkipped` is present) / "Proceed and apply the project files" (only when a `workspace` or `carry` root is present with `applied: false`) / "Cancel" — which is exactly AskUserQuestion's four, so when both extra options apply, ask the payload question as a follow-up rather than dropping "Cancel". **Any of those choices changes the write set, so re-run step 6 with the corresponding flag (`--include-plans`, `--apply-workspace`, `--apply-carry`) and show the new set before executing** — the set you displayed was computed for the flags you passed, and confirming one list while running another is the failure this gate exists to prevent.

   **What a "yes" means, and what it does not — say this plainly, and do not soften it into reassurance.** Confirming accepts these *destinations*. It is not a review of what the files contain: nothing in the CLI has read them, no path is filtered by name or extension, and none ever will be — the plugin's floor blocks names that can subvert sesh-mover itself, which is a finite set, not names that can lead to code execution, which is a property of this machine's toolchain and cannot be enumerated. A bundle with six hostile lines in path 214 of a 340-path list passes this gate exactly as an honest one does. **A bigger list is not a more thorough gate, and the file payloads must not be allowed to make it sound like one** — a 400-path workspace was read exactly as carefully as a 3-path memory layer, which is to say not at all, and the floor that stops `.sesh-mover-include` does not stop `.claude/settings.json`, `.envrc`, a `Makefile`, a `.github/workflows/*` or any ordinary source file, every one of which is an unremarkable entry in that list and every one of which runs on the next ordinary developer action. If the bundle came from someone else, this tells the user what will be touched; reading it is still theirs to do, with the same scrutiny they would give any other code that person sent them.

9. Execute the import:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" import --from "<path>" [--session-id <ids>] [--include-plans] [--no-memory] [--apply-workspace] [--apply-carry] [--force-workspace] --target-project-path "<cwd>" --target-config-dir "<config-dir>"
   ```

   Pass `--include-plans` only if the user chose it at step 8. Pass `--no-memory` only if the user asked to decline the memory layer — it is on by default and lands in this project's own memory folder.

   `--apply-workspace` and `--apply-carry` are the two file payloads, and each is its own consent: pass one only for the payload the user agreed to at step 8, never both because the bundle happened to carry both, and never either because the bundle carried it at all. There is no config key that can turn either of them on — unlike the capture side, where `export.includeWorkspace` / `export.includeCarry` exist, the apply side is flag-only on purpose, so a flag missing here means nothing is written. `--force-workspace` is a third, separate yes and only ever follows the refusal described at step 8; it unpacks the payload over a directory that already has content, replacing any file of the same name.

10. Report the result. Read what actually landed **before** offering anything to resume — `resumable` says the importer was allowed to register sessions, not that this run created any.
    - Import is idempotent by default, so check `skippedSessions` first. If it shows all requested sessions skipped (reason `duplicate` = identical content already imported into this project; reason `already-received` = already synced from this peer) and `importedSessions` is `[]`, tell the user **no new sessions** were imported and why, and offer **no** resume command — but do not call the run a no-op: the memory and plan layers are not session-scoped and are reconciled on a fully-duplicate import too, so read `memoryIndex` / `memoryConflicts` below before summarising — a fully-skipped import still reports `resumable: true`, and there is no new session id to resume. If the user actually intended a re-import, re-run the step 9 invocation with `--allow-duplicates` appended.
    - Otherwise, if `importedSessions` is non-empty and `resumable` is true: tell the user they can continue with `claude --resume <newId>`, using the `newId` of an entry in `importedSessions` — the importer assigns a fresh id, so never quote `originalId` or an id from the bundle.
    - If not resumable because of a version-mismatch or "session validation failed" error: offer to retry the step 9 invocation with `--no-register` appended. That imports the session content but skips the registry entry — the user won't get a `claude --resume` slot, but the JSONL is on disk. Note: after a `--no-register` import, a later normal import of the same bundle automatically imports a registered copy — the older unregistered copy remains on disk and can be deleted manually. `--allow-duplicates` is no longer needed for this case.
    - If not resumable and you did **not** pass `--no-register`: the registry append itself failed. A `warnings` entry says so per session — *"imported but could not be added to `<config-dir>/history.jsonl` (`<OS error>`), so it will not appear in Claude Code's resume list"* — and the sessions themselves are on disk and intact. **Do not offer `--no-register` here**: it asks for exactly the outcome the user just got. Relay the OS error and the path, since the remedy is that file (disk space, or permissions on the config dir), then offer to re-run the step 9 invocation once it is fixed — an unregistered prior copy is not counted as a duplicate, so the re-run imports a registered copy, and the unregistered one remains on disk to be deleted manually.
    - If the `--no-register` retry also fails, or if the user prefers: offer to read the imported JSONL and inject it as context into the current conversation.
    - Always relay `warnings` verbatim — that is where version adaptations, integrity problems, the idempotent-skip notice and the memory reconciliation surface.
    - **Report the memory layer from the typed fields, not from the warnings.** A session's memories are only reachable through `memory/MEMORY.md`, so a transfer that lands them and leaves the index alone lands nothing usable (that is #49, measured: ten memory files on disk, referenced by nothing, reported as `success: true`).
      - `memoryIndex.added` — link targets appended to your `MEMORY.md`. Name the count. `alreadyPresent` is how many the index already had.
      - `memoryIndex.droppedProse: true` — the sender's index carried headings or prose; only its entries were merged. One line, not a footnote.
      - `memoryIndex.unindexed` — memory files that arrived and that **no index lists**, so nothing will ever read them. They were usually already orphaned on the source machine; the union cannot fix that, because a file no line points at contributes no line. Name them and offer to add index entries if the user wants them (that is an ordinary edit to `MEMORY.md`, and it is the user's call, not the importer's).
      - `memoryConflicts` — memories that differ on both sides. **Yours was kept and nothing was overwritten**; `parkedAs` is the file the incoming copy was saved as, inside `memoryDir`. Both texts are on disk. Then go to step 11.
      - `writeSet` — the same shape step 8 previewed, now describing what this run wrote. Present on every import, including when `total` is `0`, which means nothing landed outside the session's own directory. Read `entries[].kind` rather than inferring from the paths, and render `display` here too. The same two caveats apply after the fact as before it: `total` is the count and `entries` may be shorter than it, and a `carry` root (`enumerated: false`) contributed to neither.
      - `memorySkipped` — memory files the bundle carried that were **not written**, because `--no-memory` was passed. Name the count once. Nothing was consumed by declining — every file is still in the bundle, and a re-run without the flag lands them even when every session is now a duplicate.
      - `plansSkipped` — plan files the bundle carried that were **not written**, because `--include-plans` was not passed. Name the count and the remedy once; do not push it. Nothing was consumed by declining — the plans are still in the bundle, and a re-run with `--include-plans` lands them even when every session is now a duplicate.
      - `planConflicts` — plans that already exist here with different content (only when `--include-plans` was passed). Yours was kept; the incoming plan was **not** written and is only in the bundle. If the user wants it, they must re-extract the bundle — say that, because unlike a memory nothing was parked for them. (Plans live in a directory every project on this machine shares, which is why nothing is written beside them.)
      - A memory whose parked copy could **not** be listed in `MEMORY.md` says so in `warnings` — its name cannot be written as a markdown link target. The file is on disk and named in `memoryConflicts.parkedAs`; relay both, and offer to rename it if the user wants an index entry.

    **Report the file payloads from the typed fields too**, and keep the provenance wording from step 8 — these are the bundle's files, landing in the user's project directory:
    - `workspaceUnpacked` — `{ path, fileCount }`. Present only when `--apply-workspace` was passed *and* a payload was there: `fileCount` files were written into `path`. Say the count and the directory; that directory is now a working copy of someone else's tree.
    - `workspaceRefused` — paths in the payload the `NEVER_INCLUDABLE` floor turned away (plugin state, `.git`). Nothing from them was written. Relay it without accusing the sender: an older sesh-mover on a case-insensitive filesystem legitimately produced a bundle carrying a `.GIT`.
    - `workspaceDeclaredMissing: true` — the manifest declared a workspace payload the bundle does not contain, so nothing was applied and this project's files were left alone. Report it as a bundle problem (damaged, truncated, or not produced by sesh-mover), not as a failed apply.
    - `workspaceSkipped` — the count of project files the bundle carries that were **not** written, because `--apply-workspace` was not passed. Name the count once; it is a different sentence at 1,412 than at 3. Nothing was consumed by declining — every file is still in the bundle, and a re-run with the flag reaches them even when every session is a duplicate by then.
    - `carryAvailable` — what the bundle *declares* it carries, present whether or not it was applied: `untrackedCount` untracked files and a `patchBytes`-byte patch against `baseCommit` on `branch`. A field the CLI could not read comes back as `(not recorded)`; relay that string rather than papering over it.
    - `carryApplied` — present only when `--apply-carry` was passed and the payload was there. `applied: true` gives `filesChanged` / `untrackedCopied`, and the changes are uncommitted here too, so `git status` shows them and `git checkout -- .` undoes the patch half; also relay `collisions` (yours kept, theirs written beside it), `refused` and `blocked`. `applied: false` gives a `reason` (`wrong-base`, `dirty-tree`, `in-progress`, `unsafe-payload`, `patch-damaged`, `apply-failed`, `no-git`, `not-git`), a `detail`, and a `savedTo` directory holding the whole payload — nothing reached the working tree. Two cases not to smooth over: `savedTo: null` means even that could not be written, so the bundle is the only remaining copy; and `savedCommands: false` means the saved README deliberately withholds the finish-by-hand commands, so never promise them. **Absent the flag, nothing is saved anywhere either** — deliberate, and the one place this diverges from `hub pull`, which parks an unrequested carry because a pull gets no second chance. Here the bundle is a file the user still has, so the remedy is to re-run the import with `--apply-carry`.

    **`.sesh-mover-include` and `.sesh-mover-ignore` cannot travel in a payload, and the consequence lands on the user.** Both are on the `NEVER_INCLUDABLE` floor, precisely so that a payload can never rewrite the list deciding what the next push ships — so after a bootstrap import the destination project has *neither* file, even when the source project had both. A later push or export from here therefore carries a different set of files than the source did, silently. Say so once, after a workspace or carry apply, and tell the user to copy the two files across by hand; for a git project the clone already has them, since they are meant to be committed.

    **Incremental bundles.** The import result carries no manifest, so incremental detail has to come from the bundle itself — and only when the user picked an export **directory**: for a `.tar.gz`/`.tar.zst` the CLI extracts to a private temp dir and deletes it before returning, so nothing is left to read. When `--from` was a directory and `<path>/manifest.json` has `incremental: true`, read it and add to the report:
    - Source machine: `<sourceMachineName>` (`<sourceMachineId>`)
    - What arrived, split by kind: for each entry in `importedSessions`, find the manifest session whose `sessionId` equals that entry's `originalId` and read its `type` (`"full"` or `"continuation"`). For a continuation, its manifest `slug` is the slug of the session it continues on the source machine — report it as "continues `<slug>`".
    - Duplicates skipped: `skippedSessions.filter(s => s.reason === "already-received").length`. Count the typed field, never warning text: the CLI pushes ONE aggregated warning no matter how many sessions were skipped, so matching on its wording reports at most 1.

11. **Offer to merge the conflicting memories** — only if `memoryConflicts` is non-empty and every entry you act on has a `parkedAs`. This step is yours, not the CLI's: `dist/cli.js` does pure filesystem work and never calls a model, so the semantic merge happens here, in the session the user is already paying for, where its cost is visible and it can be confirmed before it happens.

    **When there is nobody to confirm — do nothing.** A `hub pull` driven by a SessionEnd/SessionStart hook, a piped or scripted CLI run, and a `--no-register` recovery run all reach this state with no user attached. What the CLI already did (yours kept, theirs parked, both indexed) is a **complete and correct outcome**, not a fallback that failed. Never merge without asking.

    1. **Size it before offering.** For each conflict, `memoryDir` + `filename` and `memoryDir` + `parkedAs` are the two texts. Get their byte sizes and say so: *"3 memories differ (~9 KB). Merge them into one file each?"* — not *"merge memories"*. At the scale this occurs it is small (the import that produced #49 carried 11 memory files, 578–4,648 bytes each, ~16 KB in total, so merging every one is ~32 KB of reading). At 100 conflicts it is not, and the user needs the number to decline or to pick.
    2. **Offer per file, not all-or-nothing.** Conflicts are independent — merging one memory tells you nothing about another — so use AskUserQuestion with the files as options plus "All of them" and "None, leave them parked".
    3. **Read both texts, then classify every contradiction** before proposing anything. A memory is a set of claims, not a version of a string, so:
       - `superseded` — the same claim, later and more accurate. Carry the newer, drop the older.
       - `both-true-scoped` — both true, of different machines, config dirs, branches or phases. This is the *normal* case for a cross-machine tool: "the config dir is `~/.claude-nv`" and "the config dir is `~/.claude`" are both true, of two machines. Keep **both claims, each explicitly scoped**. Never pick one.
       - `unresolved` — the claims conflict and nothing in either text says which is newer or which context each belongs to.
    4. **Any `unresolved` blocks the write.** Show both claims verbatim, say which file each came from, and ask. **Presenting the contradiction instead of resolving it is a correct answer, not a degraded one.** Never merge "everything except the hard part": a merged memory that silently omits a disputed claim is the same silent partial-state loss as the defect this whole flow exists to fix.
    5. **Show the full proposed text before writing anything**, and get an explicit yes.
    6. **On acceptance, in this order:**
       1. Write the merged text to `<memoryDir>/<filename>`.
       2. Write the **pre-merge local text** to `<memoryDir>/<stem>.pre-merge.md` and delete `<memoryDir>/<parkedAs>`. Keep the *local* half, not the incoming one: the incoming text is still in the bundle (and on the hub, which deletes nothing), while the local pre-merge text existed in exactly one place — the file you just overwrote.
       3. Remove the `MEMORY.md` pointer line whose target is `<parkedAs>` — the merged memory is reachable under its own name, and a `.pre-merge.md` backup is a backup, **not a memory**: never index it. Touch no other line of `MEMORY.md`.
    7. **On decline, change nothing.** Two files, two index entries, nothing lost.

**Exit codes:** keep branching on the parsed JSON, not on `$?`. `import` exits `0` for a completed import **and for a `--dry-run`**, which changed nothing — so a zero exit is never on its own proof that sessions landed; read `importedSessions`/`skippedSessions`. `1` is a bad invocation or a failure while reading the bundle, and `2` is a refusal reported as a result — the non-empty workspace target of step 8 is one of these, and it wrote nothing at all, so correcting the flag and re-running is always safe. See "Exit Codes" in the skill doc for the full four-class table.

**Invocation:** `${CLAUDE_PLUGIN_ROOT}` is set by Claude Code inside plugin command execution — use it as-is in the bash invocations above; do not search the plugin cache. The flag set documented in this file (in both the main invocations and any conditional/retry branches, e.g. `--no-register` for the version-mismatch fallback, `--allow-duplicates` for the duplicate-skip retry, `--include-plans` for the opt-in plans layer, `--no-memory` for the opt-out memory layer, and `--apply-workspace` / `--apply-carry` / `--force-workspace` for the two file payloads) is authoritative — do not run the CLI with `--help` or with no arguments to discover its surface. None of those last three has a `--no-` form, and none of them is reachable from config: not passing one is how the payload is declined.
