name: push
description: Push this project's sessions to the cross-machine hub
---

You are running the sesh-mover push command. Follow these steps:

1. Check hub configuration and current link state first:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" hub status
   ```
   - If `hubPath` is `null`, tell the user no hub is configured yet and point them at `/sesh-mover:hub-init`. Stop.
   - If `reachable` is false, surface the `warnings` (e.g. the synced folder isn't mounted) and stop.
   - Note `project.linked` / `project.projectId` — informational only; the actual link/create decision happens in step 3 if push reports it's unlinked.
   - If `lastAutoPush` is present, that is the record of the last **automatic** (session-end) push for this project, which has no other output at all. Mention it when `ok` is `false` (the automatic pushes have been failing and nothing would have said so) or when `notes` is non-empty (those are warnings the user was never shown — the gitignored-but-tracked disclosure is one of them). Don't repeat it once the manual push below reports the same thing.

2. Ask the user which sessions to push. Default to "All sessions in this project" (omit `--session-id`). Only ask for specific sessions if the user requests narrower scope — if so, detect session IDs the same way `export` does (see "Detecting the Current Session" in the skill doc) and let them multi-select via AskUserQuestion, passing each as `--session-id <id>`.

3. Run:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" push --project-path "<cwd>" --source-config-dir "<config-dir>" [--session-id <id> ...] [--no-workspace] [--no-carry]
   ```
   For projects with **no git remote** — which includes a git repository that simply has none configured, not just a non-git directory — push bundles a workspace snapshot (the project's files) alongside the sessions by default. Offer `--no-workspace` when the user doesn't want project files uploaded to the hub (large or sensitive working directory), and carry it into any re-run in step 4. Never describe this as the "non-git" case to the user: a remote-less git repo gets its whole working tree snapshotted, and someone told otherwise would not know to ask for `--no-workspace`.

   For projects **with** a git remote, push instead carries the **uncommitted** work: a `git diff HEAD` patch plus untracked, non-gitignored files. Offer `--no-carry` when the user doesn't want work-in-progress on the hub, and carry it into any re-run. Among *untracked* files, a gitignored one is never carried unless `.sesh-mover-include` names it (see step 4). That rule does **not** extend to tracked files: the patch describes every tracked file that changed, so a gitignored-but-tracked file's changes do travel — never tell the user `.gitignore` protects them from the carry without that qualification.

   **`--full` is a recovery flag, not a tuning knob. Never offer it unprompted.** Push normally ships a *delta* for a session the hub already has, anchored on the head this machine recorded as sent. That is correct while the hub can still serve what it holds — and wrong once it cannot, because a delta with no readable base is a thread no machine can reconstruct. `--full` forgets the "the hub already has you up to entry X" ledger for this project and re-sends every session in scope whole. Reach for it only when the user describes that situation: bundles removed from the hub directory, a hub restored from an incomplete backup, or a bundle encrypted to a key that is gone. Two things to say before running it — it re-uploads every session in the project, which on a large one is slow and costs hub space, and it changes nothing locally and deletes nothing on the hub, so a wrong call costs bytes and time and no data. It combines with `--session-id` to scope the re-send. There is **no config key** for it and the session-end auto-push never does it.

   **`--force-unkeyed` is an override for one upload, not a setting. Never offer it unprompted, and never as the first answer to an `encryption-refused` result.** It applies only on a hub that has been sealed with `/sesh-mover:hub-encrypt`, where every bundle is encrypted to every registered machine. If a registered machine publishes no usable public key, push refuses rather than dropping it from the recipient list, because a bundle is encrypted once and is never re-wrapped — a machine left out can never read that thread, not after it upgrades, not after it publishes a key, not ever, and the loss would surface on *that* machine, much later, looking like corruption. `--force-unkeyed` uploads anyway and names the machines it excluded; say plainly that this is permanent for everything that push uploads. It has **no config key**, so the session-end auto-push can never take it, and it cannot override the case where *this* machine is the un-keyed one — a bundle this machine cannot read back is never the right answer, and that one refusal has a local remedy instead.

   Which of the two a project gets is decided by asking `git` for its remotes, and there is a third answer: if `git` can't be asked (not on `PATH`, or a repository it refuses to read), push includes **neither** payload and says so in a warning. That is deliberate — a workspace snapshot copies the whole directory without reading `.gitignore`, which is only safe for a project that genuinely has no remote — so relay it as a local setup problem to fix (the sessions still pushed), never as the project having no uncommitted work.

4. Parse the result and branch on its shape:
   - `reason: "unlinked"` (this project isn't linked to any hub project yet): present `linkCandidates` (name + gitRemotes) as a pick-list via AskUserQuestion, with an extra "Create a new hub project for this directory" option. Then re-run the step 3 invocation with `--project-id <picked-id>` appended (if the user picked a candidate) or `--create-project` appended (if they chose to create new). Do this once automatically as part of the flow — don't ask the user to re-invoke the command themselves.
   - `reason: "no-such-project"`: the `--project-id` you passed names no project on this hub (`requestedProjectId` echoes it back). Nothing was pushed and nothing was written — this refusal happens before any hub write, so it is safe to simply re-run. Present `linkCandidates` exactly as for `unlinked` above, plus the "create a new hub project" option, and re-run step 3 with the corrected `--project-id` / `--create-project`. If `linkCandidates` is empty the hub has no projects at all, so creating one is the only move.
   - `reason: "lock-busy"`: tell the user another sesh-mover hub operation is already running for this project (mention `holderPid`/`ageSeconds` if present), wait a few seconds, and retry the exact same invocation once. If it's still lock-busy after that retry, stop and report it to the user rather than looping.
   - `reason: "encryption-refused"`: this hub has been sealed with `/sesh-mover:hub-encrypt` and this push could not produce a bundle every registered machine can read. **Nothing was uploaded and nothing was linked** — the decision is taken right after the preflight, before the export, before any hub write and before the local link that arms the session-end auto-push, so there is nothing to roll back and re-running after a fix is always safe. There is deliberately **no plaintext fallback**: confidentiality has no lesser version to degrade to, unlike zstd→gzip. **Branch on `refusal`**, never on the prose and never on `unkeyedMachines.length` — the census is reported WHOLE, so all three shapes can carry entries and "empty" discriminates nothing. Each `unkeyedMachines` entry has a `machineId`, a `name` and a `reason` (`no-key`, `bad-key`, `unreadable-record`, `unsafe-id`); an `unsafe-id` entry's `machineId` is display-only and must never be turned back into a path. Three values, and only one of them takes the override:
     - **`refusal: "unkeyed-machines"`** — machines other than this one publish no usable key. Relay `error`/`suggestion`, say that the ordinary remedy is to run any hub command on each named machine so it publishes its key (upgrading it first if it is on an older version), or to delete a decommissioned machine's `machines/<id>.json` from the hub directory. Offer `--force-unkeyed` **second, via AskUserQuestion, never automatically**, and label it for what it does: upload anyway, permanently excluding those machines from every bundle this push writes.
     - **`refusal: "no-recipients"`** — no registered machine publishes a usable key at all, so there is nobody to encrypt to. `--force-unkeyed` does not apply and must not be offered: a bundle encrypted to an empty recipient list is readable by nobody, which is worse than the plaintext the hub is refusing.
     - **`refusal: "self-unkeyed"`** — this machine could not encrypt a bundle it is able to read back. **`--force-unkeyed` is refused here and offering it is always wrong**, because the override's premise ("I know those machines don't need this") cannot be true of the machine writing the file. Note that this is decided from the key this machine actually holds, **not** from its record on the hub — the hub keeps publishing a machine's last-known public key when its identity file becomes unreadable, so the roster can say "keyed" long after the key is gone. Two sub-cases, told apart by the `error`: *no readable key* (`~/.sesh-mover/identity.age` should exist, be readable by the user and nobody else, and hold an `AGE-SECRET-KEY-1` line — restoring from a backup comes before deleting, because a fresh identity can read nothing already on the hub), or *the hub's record for this machine publishes a different key* (usually a registration that did not land: run `/sesh-mover:hub-status` or any hub command so the record is rewritten, then push again; if the identity file was genuinely replaced, everything encrypted to the old key stays unreadable here whatever happens next).

     If this shows up on the *automatic* session-end push rather than a manual one, say so explicitly: the auto-push refuses identically at every session end, silently, and `hub status`'s `lastAutoPush` is the only place it is recorded.
   - `success: true` and `upToDate: true`: this is a successful push, not a no-op error — tell the user there was nothing new to push (`bundleId` is `null`, `pushedSessions` is empty because every session's head already matches what the hub has recorded). `bundleEncrypted` is `false` on this shape because nothing was uploaded; it is **not** a statement that the hub is unencrypted, and reporting it as one is wrong. A bare `hub encrypt` is what answers that.
   - `success: true` and `upToDate: false`: report `pushedSessions` (thread id, session id, `full` or `continuation`), whether `hasWorkspace` was included, whether `bundleEncrypted` is true (this bundle went to the hub as ciphertext, `.tar.gz.age`), and any `warnings`. `bundleEncrypted` describes **this bundle**, never the hub's policy: a hub is permanently mixed, since enabling encryption never rewrites what is already there, so the only honest thing a push can report is what it just did. A `warnings` entry saying this machine prefers encryption but the hub is not sealed is the case worth relaying verbatim — the bundle went as plaintext, nothing can change that after the fact, and the remedy is `/sesh-mover:hub-encrypt`, which is hub-wide rather than per machine. `fullResend` is present only when `--full` was passed: `forgottenSessions` is how many sessions were re-sent whole that would otherwise have gone as deltas, and `forgottenMemoryDigest` says whether the shared `memory/` layer was re-sent with them. Report the counts — they are the size of what just went back up.
   - `reason: "failed-after-link"`: the push got past the identity decision and then failed, so it may have left state behind. **Branch on the FIELDS, never on the prose in `details`** — the fields say exactly what is left: `linked` (true = this directory IS linked right now), `projectId`, `linkRolledBack` (this push created the link and removed it again), `orphanHubProjectId` (non-null = a `--create-project` push minted a hub project that nothing removes — pass `--project-id <that id>` on a later push instead of minting a second one), and `orphanBundle` (a bundle reached the hub but no index references it, so no other machine can see it yet — the next successful push republishes the index and picks it up). Report `error`/`suggestion` too, then stop. When `linked` is true, say so in plain words — this directory is linked, which means the session-end auto-push is armed for it — and offer `/sesh-mover:hub-unlink` (or deleting `.sesh-mover-project.json`) if that is not what the user wants while they sort the failure out.
   - `reason: "hub-unreachable"`: the configured `hub.path` could not be read at all. `hubState` distinguishes `"no-directory"` (nothing there — an unmounted share, a synced folder not yet present on this machine, or a typo in `hub.path`), `"not-a-hub"` (a directory exists but has no `hub.json`, so it was never `hub init`-ed or points at the wrong folder) and `"unresponsive"` (the path is mounted but a filesystem call against it timed out — a hard-mounted share whose server is gone, or a dead sync/FUSE daemon). For `"unresponsive"` do **not** offer to check or change `hub.path`: it is almost certainly correct, and the fix is to reconnect or force-unmount the filesystem. That case also takes the hub I/O timeout to detect (so the command is slow, not stuck) and exits by signal rather than with a status code — read the JSON body, which is complete, and don't report it as a crash. **Nothing was exported, written or linked** — this is checked before the identity decision and before every hub write, so re-running is always safe, and in particular the project is *not* now linked. Don't present `linkCandidates`: the hub couldn't be listed, so an empty list carries no information. Ask the user to mount/connect the share or check `hub.path` via `configure --show`, then offer to re-run. The result deliberately does **not** echo the path back.
   - Any other `success: false` (no `reason`): report `error`/`suggestion` and stop. Nothing was linked in this case: `push` defers the identity write until the export has produced a bundle, and writes the local `.sesh-mover-project.json` later still, so a failure before that point genuinely leaves the project unlinked — anything that fails *after* it reports `failed-after-link` above and says what it left. The commonest shape here is `No sessions found for this project`, which just means this directory has no Claude Code sessions yet.

   If the result carries a `carry` object, say what uncommitted work went with it: `carry.untrackedCount` untracked files plus a `carry.patchBytes`-byte patch against `carry.baseCommit` on `carry.branch`. If `carry.reIncludedCount` is above zero, name the `carry.reIncluded` paths explicitly — those are gitignored files that travelled *because* `.sesh-mover-include` lists them, and the user should be told which ones are now on the hub (`reIncluded` is capped at 10; if the count is higher, say so rather than implying the list is complete). If `carry.trackedIgnoredCount` is above zero, name `carry.trackedIgnored` too, and keep the two apart: those are gitignored files that git **tracks**, so the patch carried their changes and no `.sesh-mover-include`/`.sesh-mover-ignore` line put them there or can take them away — the remedy is `git rm --cached <path>` or `--no-carry`. A carry that was declined shows up as a `warnings` entry, not as a failure; report it verbatim rather than treating the push as broken.

   If (and only if) the result carries a non-empty `ignoredNotCarried`, mention it once after the summary — it's present only on a git project that has no `.sesh-mover-include` yet, and it lists gitignored paths this push left behind (a sample, capped at 10, spelled the way git spells them; a trailing `/` means that directory at the project root and everything under it). Tell the user these are *not* carried, and offer via AskUserQuestion to create `.sesh-mover-include` (at the project root — it is a root dotfile, not a file inside `.sesh-mover/`) listing the ones they want synced across machines. If they accept, write only the paths they picked, one per line, exactly as reported. Say plainly, before they choose:
   - `.gitignore` is also where `.env` and credential files live, so this is a security-relevant list;
   - the file is meant to be committed, so it applies on every clone and every machine;
   - listing a path means it is **uploaded on the next push** of this project (it rides the git carry described above), and a later push reports it back in `carry.reIncluded`;
   - creating the file also *stops this suggestion appearing*, since its existence is what suppresses `ignoredNotCarried`.

   Never pre-select entries, never widen one (`docs/specs/notes.md` stays that path — don't turn it into `docs/`), and never offer `.git` or any path sesh-mover owns (`.sesh-mover/`, the `.sesh-mover-*` root dotfiles): those can never be carried and a pattern naming one does nothing. If the user declines, don't ask again in this session.

5. Report a final summary: hub project id, sessions pushed (count, and full-vs-continuation breakdown), whether a workspace snapshot was included, and whether the project was newly linked or created during this run.

**Exit codes:** keep branching on the parsed JSON, not on `$?` — every branch in step 4 is decided from the body, and the codes only classify what the body already says. `0` a successful push, **including `upToDate: true`**, which pushed nothing and is not a failure. `1` a bad invocation or an unexpected failure, and also `failed-after-link` — the one shape that may have left state behind, which is why it is not grouped with the refusals. `2` `unlinked`, `no-such-project` and `encryption-refused`: refusals that wrote nothing, so re-running after correcting the flag — or after the named machine checks in — is safe. `3` `hub-unreachable` and `lock-busy`: the retryable class. See "Exit Codes" in the skill doc for the full four-class table.

**Invocation:** `${CLAUDE_PLUGIN_ROOT}` is set by Claude Code inside plugin command execution — use it as-is in the bash invocations above; do not search the plugin cache. The flag set documented in this file (in both the main invocation and the unlinked-retry branches, `--project-id`/`--create-project`, plus `--no-workspace`, `--no-carry`, `--full` and — only after an explicit confirmation on an `encryption-refused` result — `--force-unkeyed`) is authoritative — do not run the CLI with `--help` or with no arguments to discover its surface. `push` also accepts `--progress` (NDJSON progress events on stderr) — it's oriented at humans running the CLI directly; don't pass it from this command flow.
