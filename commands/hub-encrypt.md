---
name: hub-encrypt
description: Report the cross-machine hub's encryption-at-rest setting, or turn it on for every machine
---

You are running the sesh-mover hub encrypt command. It has two modes and only one of them decides anything: a bare invocation **reports** the hub's encryption setting, `--enable` seals the hub so that every machine's later pushes must be encrypted bundles. There is deliberately **no `--disable`** — see step 7.

`hub status` does not report this; a bare `hub encrypt` is the only way to ask.

Follow these steps:

1. Read the current state first:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" hub encrypt --project-path "<cwd>" --source-config-dir "<config-dir>"
   ```
   Without `--enable` this changes no setting: it does not touch `hub.json` and writes no config, so it is safe to run on any hub at any time. It is not a no-op on the hub either, and the difference is worth knowing rather than hiding: exactly as `push` and `pull` do, it refreshes **this machine's own** record under `machines/`, and that record is what publishes this machine's *public* key. So a machine that has never encrypted anything becomes a recipient of everything pushed after it asks the question — which is what makes enabling encryption a switch rather than a flag day.

2. Report what came back. The fields, and what each is actually an answer to:
   - `enabled` — the hub-wide switch **as it stands after this command**. This is `hub.json`'s own `encrypt` field, the authoritative one.
   - `changed` — this command wrote `hub.json`. `false` for a plain read, and also for an `--enable` on a hub that was already sealed.
   - `preference` — this machine's local `hub.encrypt` config value afterwards. **Not the switch.** A machine that never set it still refuses to push plaintext into a sealed hub, and a machine that sets it on an unsealed hub still pushes plaintext (the push discloses that as a warning). Never present this field as "encryption is on here".
   - `recipients` — the registered machines that publish a usable public key. Every bundle pushed to a sealed hub is encrypted to all of them.
   - `unkeyedMachines` — the registered machines that cannot be encrypted to, each with a `reason`: `no-key` (a machine on a version that predates encryption, or one whose identity file was unreadable when it last checked in), `bad-key` (it publishes something that is not an age recipient — a hand-edited or damaged record), `unreadable-record` (its `machines/<id>.json` did not parse or vanished mid-read), `unsafe-id` (its file name is not usable as a hub path component, so the record was never opened). These are what a push into a sealed hub refuses on. **`machineId` here is display only** — for `unsafe-id` it is by definition a string that must never be turned back into a path, so echo it and do nothing else with it.
   - `staleMachines` — registered machines whose last check-in was on a plugin version older than 0.10.0, or that recorded no version at all. Populated on a **read** as well as on an enable, deliberately, because the refusal in step 5 is more useful before the user asks for the change than after.
   - `warnings` — relay all of them verbatim. On a successful enable the first two are the statements in step 3 and they are the point of the command.

3. **If the user is asking to turn encryption on, say all of this before running `--enable`.** These are not caveats to append afterwards; each one is something a user will otherwise assume the opposite of.
   - **Enabling encryption does not make an existing hub private. It makes it private going forward.** Every bundle already on the hub stays readable by anyone with read access to that directory, forever. Nothing rewrites them, and that is not a shortcut: in-place re-encryption would be one machine rewriting *other machines'* files, which per-machine ownership — the invariant that makes concurrent push and pull safe without a distributed lock — forbids outright. The remedies are a fresh hub, or a per-machine re-encrypt verb that does not exist — `/sesh-mover:hub-rekey` is **not** it: that command re-addresses bundles that are already encrypted and leaves plaintext ones exactly as they are, and it reports them so the state is visible. If what is already there is the sensitive part, say plainly that this command does not help with it.
   - **The hub is therefore permanently MIXED** — plaintext and encrypted bundles side by side — and every reader branches on the bundle **file's own suffix** (`.tar.gz` versus `.tar.gz.age`), never on this setting. That is why flipping the switch cannot strand the user's own history, and why turning it off later would not make old encrypted bundles unreadable either.
   - **The authentication proves the GROUP, not the sender.** Bundles are encrypted to every machine registered on the hub, so a valid authentication tag proves the payload came from *someone* holding the file key — which is every participating machine. What is gained: a hub operator who is not one of your machines can no longer author a payload at all. What is **not** gained: any protection against a machine that is on this hub, and no attestation of what a bundle descends from. Per-machine signing is a separate, future step. Do not describe an encrypted bundle as "verified" or "signed".
   - **The key is local and is never transported.** Each machine holds an X25519 identity at `~/.sesh-mover/identity.age` (mode 0600 on POSIX; on Windows there is no 0600 and the file is protected only by the ACL it inherits). Only the **public** half is published, in that machine's hub record, on every push and pull. A machine that joins later gets every bundle pushed after it joins and **does not** retroactively gain access to older ones until each machine that pushed them runs `/sesh-mover:hub-rekey`, which re-addresses that machine's own bundles to today's roster. If one of those machines is gone, its history stays unreadable for good — nobody else can re-wrap it.
   - **The hub is not a backup, and encryption is the point at which that stops being pedantry.** Lose every copy of a key and every bundle encrypted to it is permanently unreadable — a re-wrap needs the key too, so `hub rekey` is no help here either. The *sessions* survive, because a push copies and never deletes the source, so the machine that pushed still has them; `sesh-mover push --full` is the escape hatch that re-sends whole sessions to a hub that can no longer serve what its ledger claims it holds.
   - **There is a standard-tool escape hatch, and it is the whole reason the wire format is age's:** `age -d -i ~/.sesh-mover/identity.age <bundle>.tar.gz.age` recovers a bundle with this plugin uninstalled. Key loss and plugin loss are not the same event as session loss.

4. Run the enable, once the user has said yes:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" hub encrypt --enable --scope <user|project> --project-path "<cwd>" --source-config-dir "<config-dir>"
   ```
   `--scope` (default `user`) only decides where the local `hub.encrypt` *preference* is recorded; the hub-wide switch is written either way, because it lives on the hub. Ask for `project` only if the user has a reason to keep the preference out of their user-scope config. `--scope project` writes it to `<project>/.sesh-mover/config.json` under the same directory `--project-path` names (the cwd when that flag is absent), so it lands in the scope the next command reads back.

5. Branch on the result:
   - `reason: "stale-machines"`: **refused, and nothing was changed** — not `hub.json`, not config. One or more registered machines last checked in on a plugin version that predates encryption at rest (or recorded no version at all); `staleMachines` names each, with `pluginVersion` and `lastSeenAt`. Explain why this is a refusal rather than a warning: those machines do not read the hub's encryption setting *at all*, so sealing the hub would not stop them pushing sessions to it in the clear — it would only stop the user noticing. A version field cannot stop an old plugin; it can only let a new one notice, and this is the noticing. **It is not overridable and there is no flag to ask for** — do not go looking for one. The two honest remedies are: upgrade sesh-mover to 0.10.0 or later on each named machine and run any hub command there once (which refreshes its record), or, if a machine is decommissioned, delete its `machines/<id>.json` from the hub directory by hand. Mention that the second remedy is also what stops a dead machine being carried as a recipient of every future bundle, since nothing in sesh-mover ever prunes that roster.
   - `reason: "hub-unreachable"`: the configured `hub.path` could not be read at all, so the question could not be answered — and this verb writes to the hub, so answering it from a hub this machine cannot see would be wrong rather than merely degraded. `hubState` says which case: `"no-directory"` (an unmounted share, a synced folder not yet present here, or a typo in `hub.path`), `"not-a-hub"` (a directory is there but carries no `hub.json`), `"unresponsive"` (mounted but a filesystem call against it timed out — `hub.path` is almost certainly right, so offer to reconnect or force-unmount rather than to edit config; it takes the hub I/O timeout to detect and exits by signal rather than with a status code, so read the complete JSON body and don't report it as a crash). Nothing was written. The result deliberately does not echo the path back; point at `configure --show`.
   - `success: true` with `changed: true`: the hub is now sealed. Relay the `warnings` — they carry the forward-only statement and the group-not-sender statement — and then say what happens next (step 6).
   - `success: true` with `changed: false` and `enabled: true`: it was already sealed. Nothing happened, which is the correct outcome; do not report it as a failure or re-run.
   - `success: true` with `enabled: false`: this hub is not sealed. Every push to it goes as plaintext, whatever any machine's local preference says.
   - Any other `success: false`: report `error`/`suggestion` and stop. The commonest is no hub configured at all — point at `/sesh-mover:hub-init`.

6. **Say what the next push will do**, because a sealed hub changes how push can fail. If `unkeyedMachines` is non-empty, every push to this hub — including the unattended session-end auto-push — refuses with `reason: "encryption-refused"` until those machines check in, and on the auto-push path the only place that refusal ever surfaces is `hub status`'s `lastAutoPush`. That is worth naming immediately rather than letting the user discover it as a hub that quietly stopped updating. `/sesh-mover:push` documents the refusal and the `--force-unkeyed` override, which permanently excludes the named machines from the bundles it uploads.

7. **There is no `--disable`, and it is not an omission.** Turning encryption off is a confidentiality-reducing act with no urgency attached to it: nothing breaks while it stays on, because each reader branches on a bundle's own suffix and a plaintext bundle stays readable forever. So the one-keystroke path exists only in the direction that fails safe. A user who genuinely wants it off edits `encrypt` in the hub's `hub.json` by hand — say that, rather than implying it cannot be undone, and rather than offering to do it for them unprompted.

**Exit codes:** keep branching on the parsed JSON, not on `$?` — every branch above is decided from the body. `0` a report, or an enable that succeeded (including one that found the hub already sealed). `1` a bad invocation (an unknown `--scope`), no hub configured, or an unexpected failure. `2` the `stale-machines` refusal: understood, declined, nothing written. `3` `hub-unreachable`, the retryable class. See "Exit Codes" in the skill doc for the full four-class table.

**Invocation:** `${CLAUDE_PLUGIN_ROOT}` is set by Claude Code inside plugin command execution — use it as-is in the bash invocations above; do not search the plugin cache. The flag set documented in this file (`--enable`, `--scope`, `--project-path`, `--source-config-dir`) is authoritative — do not run the CLI with `--help` or with no arguments to discover its surface.
