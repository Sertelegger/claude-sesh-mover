---
name: hub-init
description: Initialize or join a cross-machine session hub
---

You are running the sesh-mover hub init command. Follow these steps:

1. Explain briefly what the hub is: a shared directory that lets you push sessions from one machine and pull them on another (a synced folder like OneDrive/Dropbox/iCloud Drive/Syncthing, or a network share). State the trust model in one sentence: **the hub directory is a trust boundary** — by default sessions are stored there in plaintext at rest, so anyone with read access to the folder can read every pushed session. Encryption at rest exists as of 0.10.0 and is **off by default**; `/sesh-mover:hub-encrypt --enable` turns it on for the hub, and it seals what is pushed *afterwards* — it never rewrites what is already there. If the user is initializing a hub on a share other people can read, that ordering is worth one extra sentence now rather than a migration later: sealing an empty hub costs nothing, and sealing a full one leaves everything in it readable forever.

2. Ask the user for the hub directory. If you can suggest a likely candidate (an existing synced folder you can detect, e.g. `~/OneDrive`, `~/Dropbox`, `~/Library/Mobile Documents` for iCloud Drive), offer it with AskUserQuestion alongside a free-text option; otherwise just ask for the absolute path as free text. Prefer a folder that's actually synced across the user's machines — a plain local-only path only "shares" with itself. **Whatever the user picks, turn it into an absolute path yourself before step 4** — expand a leading `~` to their home directory: bash does not expand `~` inside the double quotes step 4 uses (nor in `--path=~/…`), so a `~`-spelled candidate would reach the CLI as a literal. The CLI now expands a leading `~` itself and refuses a relative path, but an absolute path is what step 5 compares against.

3. Ask for the config scope, only if it isn't obvious (e.g. skip this question if the user has never used project-level config before). Use AskUserQuestion:
   - "This machine, all projects" (recommended/default) → `--scope user`
   - "This project only" → `--scope project`

4. Run:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" hub init --path "<absolute-hub-dir>" --scope <user|project>
   ```

5. Parse the result:
   - If `success: false`, branch on `reason` first, then report `error` and `suggestion`:
     - `reason: "hub-path-not-absolute"` (exit `1`) — the path was relative (or `~user/…`, which is never expanded). Nothing was created. Ask for the absolute path and re-run.
     - `reason: "hub-content-without-identity"` (exit `3`) — the directory already holds other machines' hub files (`found` lists `machines`/`projects`) but no `hub.json`, so this machine can neither join it nor safely create one over it. **On a synced folder this is almost always the first sync still in flight**: offer to wait and re-run the same command, which then joins the existing hub. Nothing was written. Do **not** offer `--accept-new-hub-id` here unless the user tells you `hub.json` is genuinely lost — and then say what it costs before they choose it: a new hub identity for the directory, so every machine already using the hub refuses it until someone deliberately re-joins there, a machine that never joined under the old identity reads the bundles signed under it as tampering, and (if the old hub was sealed) the new `hub.json` starts with encryption off.
     - `reason: "hub-identity-changed"` (exit `2`) — this machine joined a hub at this path before, under a **different** identity (`expectedHubIds`) than the one there now (`currentHubId`). Relay `error` and `suggestion` in full. See "The hub identity" below — **never** pass `--accept-new-hub-id` on the user's behalf.
     - `reason: "hub-identity-not-present"` (exit `3`) — there is nothing at this path (no `hub.json` and no hub content, or no directory at all), yet this machine has reason to expect a hub here: with `basis: "recorded"` it joined one here before, and with `basis: "evidence"` it has no record of joining one but its own projects use this path for a hub — or might: when some project's configuration cannot be read (its directory is not there, because it sits on the same unmounted share or was deleted; or its config is unreadable or unusable), `expectedHubIds` is every hub id this machine knows and `unresolvedProjects` names each such project (`projectPath`, `syncStateFile`, `cause`). That needs only one known hub id, so it happens on a machine that has only ever used one hub too, and at ANY empty or missing path. Relay the named projects — they are what to mount, restore or fix — and note that a project deleted for good is named only by its leftover sync-state file. `expectedHubIds` names the identity it expects — more than one when its records disagree. That is what an unmounted share's mount point, or a synced folder not synced here yet, looks like. Nothing was created or written — not even the directory. Offer to wait, or to mount the share, and re-run the same command, which then joins the hub that is there. Do **not** offer `--accept-new-hub-id` unless the user tells you that hub is truly gone and they are replacing it (or, on the evidence basis, that they are starting a new hub at this path). On the recorded basis the flag carries this machine's signing-key pins over to the new hub; on the evidence basis there is no joined identity to carry them from, so it carries none — say so before they choose it, and relay the `warnings` the minting run returns.
     - no `reason` — the directory isn't writable, or an existing `hub.json` at that path couldn't be read. Report and stop.
   - If `success: true`: `created: true` means this machine just minted a new `hub.json` at that path; `created: false` means it joined a hub another machine already initialized there. Mention which case happened — it matters for whether the user should expect existing projects/threads to show up. **`created: true` does not by itself mean the directory is empty** — it means there was no `hub.json`; with `--accept-new-hub-id` it can be minted over other machines' files. Compare the returned `hubPath` with the path the user chose in step 2 and say so if they differ. If `warnings` is non-empty, relay it verbatim (it is where an accepted identity change is explained, and where a first join says it carried no signing-key pin over from the hub this machine's records name). `identity` says what this machine recorded about which hub it joined here: `recorded` (first time), `unchanged`, `accepted-change` (with `previousHubId` and `pinsCarried`), or `not-recorded` (the local record could not be written; `warnings` says why).

6. Confirm registration by running:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" hub status
   ```
   Report `hubPath`, `reachable`, `machineRegistered`, and `project.linked` from the result. If `reachable` is false or there are `warnings`, surface them — a hub that was just created should normally come back reachable and registered.

   `hub status` is a **diagnostic** and always returns `success: true`: unlike `push`, `pull` and `hub reindex`, it reports an unreachable hub instead of refusing, because reporting it is the question it was asked. `hubState` says which state, and the remedies differ:

   - `"ok"` — `reachable: true`. The normal case.
   - `"no-directory"` — nothing is at `hub.path`: an unmounted share, a synced folder that hasn't reached this machine, or a typo. **Do not offer `hub init` here** — running it at an unmounted mount point mints a *different* hub in a directory that will be shadowed the moment the real one mounts. (A machine that has joined a hub at that path before — or that has no record of joining one there but whose own projects use that path for a hub, including a project on the same unmounted share, whose configuration it cannot read — now refuses to do that, with `hub-identity-not-present`, and does not create the directory; a machine with neither would still mint one.) Offer to check the path (`configure --show`) or to mount the share.
   - `"not-a-hub"` — a directory is there but carries no usable `hub.json`. If it's a synced folder the first sync may still be in flight, so offer to wait and re-check; otherwise the path names some other directory and `hub init` (at the right path) or `configure --set hub.path=<dir>` is the fix.
   - `"identity-changed"` — `hub.json` is readable and names a **different** hub identity from the one this machine joined at this path — or, with `basis: "evidence"` and no record yet, one this machine's own records do not unambiguously tie to it (`identityChange` has `currentHubId`, `expectedHubIds` and `basis`). Every hub command here refuses until this is settled. Relay the warning verbatim — it presents both readings (a hub re-created or switched on purpose, or a rewritten `hub.json`) — and follow "The hub identity" below. **Do not offer `hub init` as a routine fix.**
   - `"unresponsive"` — the path is mounted and a filesystem call against it did not come back within the hub I/O timeout: a hard-mounted network share whose server has gone away, or a sync/FUSE daemon that has died. **Do not offer `hub init`, and do not offer to check `hub.path`** — the path is almost certainly right, and both of the remedies above are wrong for it. The fix is outside sesh-mover: reconnect or force-unmount the filesystem, then re-run. This is also the one state that takes real wall-clock time to report, because it is defined by a call that never returned.
   - `null` — no hub is configured at all (`hubPath` is also `null`). This is not a failure: point at `/sesh-mover:hub-init` and say nothing about mounts.

   `hub status` is also the one hub result that reports the configured path; the `hub-unreachable` refusals from `push`/`pull`/`hub reindex` withhold it on purpose and point here instead.

7. Report to the user: hub path, created-vs-joined, machine registration confirmed, and point them at `/sesh-mover:push` to start sharing this project's sessions through the hub (linking happens automatically on the first push/pull, not during init). On a `created: true` run **without** `--accept-new-hub-id` — a brand-new hub in a directory that held no hub content — also point at `/sesh-mover:hub-encrypt`, and say why the moment matters: enabling encryption seals only what is pushed after it, so an empty hub is the one time it costs nothing to leave behind. Do not run it for them, and do not raise it on a `created: false` join, where the decision belongs to whoever owns the existing hub.

8. State the automation consent, once, in the same breath — **linking a project is what turns it on**, so say it before the user runs their first push rather than after: linking a project enables automatic push when a session ends and a startup notice when another machine has newer work; disable with `configure --set hub.autoPush=false` / `hub.startupNotice=false` (add `--scope project` to limit either to this project). Both are inert until a project is actually linked, so `hub init` on its own changes nothing about how sessions end or start. Mention what the automatic push carries, because it is the same payload as a manual one: this project's sessions, plus — depending on the project — a workspace snapshot (no git remote) or a `git diff HEAD` patch and untracked files (git remote); `hub.noWorkspace` / `hub.carryDiff` are the opt-outs for those two, and the hook takes no flags, so config is the only place to express them.

**The hub identity, and `--accept-new-hub-id`.** This machine remembers, per hub path, which hub identity (`hubId`) it joined — in `~/.sesh-mover/joined-hubs.json`, never on the hub. Signing-key pins are kept per hub identity, so a `hub.json` whose identity changes would otherwise make every pin this machine holds stop applying; instead every hub command refuses with `reason: "hub-identity-changed"` until the user deliberately re-joins. The first `hub init` at a path (and, on a machine that upgraded from an older version, the first hub command) trusts the hub's word for its identity once, exactly as a first pin trusts a key once. There are two readings of a change and nothing local can tell them apart: the hub was re-created or `hub.path` now points at a different hub on purpose, or someone rewrote `hub.json`. So:
   - **Never pass `--accept-new-hub-id` on the user's behalf, never offer it as the first answer, and never offer it at all to a user who did not re-create or switch the hub themselves.** If they did not, the advice is the suggestion's: stop, find out who can write to that directory, and compare signing-key fingerprints out of band (`/sesh-mover:hub-trust`) with the machine that owns the hub.
   - `hub-identity-not-present` is not a changed identity at all: the directory is empty, or gone, where this machine joined a hub before (`basis: "recorded"`), or where its own projects say a hub lives or — because some project's configuration could not be read, which `unresolvedProjects` names — it cannot rule out that one does (`basis: "evidence"`) — almost always a share that is not mounted or a synced folder not synced yet. The answer is to mount it or wait, never the flag.
   - Only if the user says they re-created or switched the hub themselves (or, for an empty directory, that the old hub is truly gone and they are replacing it), offer it via AskUserQuestion, labelled for what it does: it records the new identity for this path and **carries this machine's signing-key pins forward** to it, so every machine's key stays exactly as trusted as it was (a key that differs from its pin still refuses a pull). It is a flag and nothing else — no config key, and neither session hook can pass it — the same stance as `push --force-unkeyed`.
   - When `basis` is `"evidence"` (this machine has no record for this path yet, and its own sync-state and pins do not name the hub's identity unambiguously — counting, where some project on this machine uses this path, only the ids those projects recorded, and every id it knows when some project's configuration could not be read: they name a different hub, or more than one, which is what a project that moved between hubs leaves behind, and then `expectedHubIds` may include the hub's own id), the deliberate remedy is a plain `hub init --path "<that path>"` — nothing is recorded there to override, so no flag is needed. The same "stop first" rule applies, and one more thing must be said before the user chooses it: **this is a first join, not a re-join — it carries none of this machine's signing-key pins over from another identity**, so every machine on that hub not already pinned under its identity has its key pinned afresh on first use. That is exactly what someone who rewrote `hub.json` would want, which is why it is only for a change the user made themselves. `hub init`'s own result repeats this in `warnings` when this machine's records do not name exactly the id it records.
   - Both remedy commands in the `suggestion` carry the `--scope` that supplied `hub.path` (`--scope project` when it came from a project's own config — run that one from the project directory). Keep that scope when you offer the command: `hub init` defaults to `--scope user`, which would point every other project at this hub.

**Exit codes:** keep branching on the parsed JSON, not on `$?`. `hub init` exits `0` once the hub is created or joined, `1` for a bad invocation (a missing `--path`, an unknown `--scope`, `reason: "hub-path-not-absolute"`) or an unexpected failure, `2` for a refusal it reported as a result — `reason: "hub-identity-changed"`, a path it could not create, or a directory it could not make a hub of — and `3` for `reason: "hub-content-without-identity"` and `reason: "hub-identity-not-present"`, because a sync still in flight (or a share not mounted yet) is the likeliest cause and re-running unchanged once it lands is the fix. `hub status` is a diagnostic and exits `0` **even when it reports `reachable: false`**: the whole point of that verb is to describe the state, so read `hubState`, never `$?`. See "Exit Codes" in the skill doc for the full four-class table.

**Invocation:** `${CLAUDE_PLUGIN_ROOT}` is set by Claude Code inside plugin command execution — use it as-is in the bash invocations above; do not search the plugin cache. The flag set documented in this file (`--path`, `--scope` and — only after the user has explicitly chosen it — `--accept-new-hub-id` for `hub init`; `hub status` takes no flags) is authoritative — do not run the CLI with `--help` or with no arguments to discover its surface.
