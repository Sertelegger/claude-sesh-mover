# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Names

- **npm package / GitHub repo:** `claude-sesh-mover` — the `claude-` prefix makes the scope obvious to a browser of the npm/GitHub ecosystem.
- **Plugin name (in `.claude-plugin/plugin.json`):** `sesh-mover` — this is what drives slash command prefixes (`/sesh-mover:export`, etc.), so it stays short.
- **CLI bin:** `sesh-mover` — matches the plugin name for in-session discoverability.
- **On-disk paths:** `sesh-mover`, always — a dotfile is the short name, not the package name. `~/.sesh-mover/`, `<project>/.sesh-mover/`, and the three committed root dotfiles `.sesh-mover-include` / `.sesh-mover-ignore` / `.sesh-mover-project.json`. They are declared once in `src/paths.ts`; never hand-write one of these literals elsewhere. **0.8.0 is a clean break:** no retired spelling is read, migrated, warned about, or on the `NEVER_INCLUDABLE` floor — `.claude-sesh-mover` (pre-0.7.0) and `.sesh-mover-hubinclude` / `.sesh-mover-hubignore` (0.7.0 only) are gone from the codebase entirely. Don't reintroduce them.

Don't change any of these without updating the others *and* every slash command reference in `commands/*.md`, the skill doc, and this file.

## Commands

- `npm run build` — compile TypeScript to `dist/`. **`dist/` is committed to the repo** (not gitignored) so that users installing via `/plugin install` get a working plugin without a build step. Rebuild and stage `dist/` alongside any `src/` change.
- `npm run lint` — type-check only (`tsc --noEmit`).
- `npm test` — run full vitest suite once.
- `npm run test:watch` — vitest in watch mode.
- Run a single test file: `npx vitest run tests/rewriter.test.ts`
- Filter by test name: `npx vitest run -t "translates WSL paths"`
- Invoke the built CLI directly: `node dist/cli.js <command> [options]` (every command emits a single JSON object to stdout; parse it — the two internal hook endpoints, `hub hook-session-end` / `hub hook-session-start`, are the deliberate exception and speak Claude Code's hook protocol instead).

## Architecture

claude-sesh-mover is a Claude Code **plugin** (not a standalone app) that exports, imports, and migrates Claude Code sessions across machines, OS/path conventions (macOS/Linux/Windows/WSL), config directories (e.g. `~/.claude` vs `~/.claude-tzun`), and project paths.

The design is **hybrid: deterministic Node.js core + conversational skill layer.**

- `src/` compiles to `dist/cli.js`, a Commander-based CLI with subcommands: `export`, `import`, `migrate`, `browse`, `configure`, `push`, `pull`, `whereis`, and the nested `hub init` / `hub status` / `hub reindex`. Every command returns structured JSON keyed by `success` and `command` (see `src/types.ts` for result shapes — `ExportResult`, `ImportResult`, `MigrateResult`, `BrowseResult`, `ConfigureResult`, `ErrorResult`, and the hub shapes `HubInitResult`, `HubStatusResult`, `HubPushResult`, `HubPullResult`/`HubPullListResult`, `WhereisResult`, `HubReindexResult`, plus the shared `HubUnlinkedResult`/`HubLockBusyResult`/`NotYetSyncedResult` error shapes). The two internal hook endpoints — `hub hook-session-end` and `hub hook-session-start` — are the sanctioned exception to that contract: they speak Claude Code's hook protocol instead (nothing on stdout, or for SessionStart exactly one hook-JSON object, and **always** exit 0). See "Hook registration" below.
- `commands/*.md` + `skills/session-porter/SKILL.md` are markdown-based slash commands loaded by Claude Code when the plugin is installed. They shell out to the CLI, parse the JSON, and drive UX (confirmations, path-collision handling, prune prompts, registration fallback when Claude Code rejects an imported session).
- `.claude-plugin/plugin.json` is the plugin manifest consumed by Claude Code's plugin cache — its `commands` array must list every `commands/*.md` doc (a doc not listed there never loads as a slash command, even if the file exists); `.claude-plugin/marketplace.json` sits alongside it for marketplace listing.
- `hooks/hooks.json` registers the plugin's Claude Code lifecycle hooks. See "Hook registration" below — this file is **auto-loaded by path**, so it must not also be referenced from `plugin.json`.
- `src/index.ts` is the library entrypoint — it re-exports every core module so the package can also be consumed programmatically. It deliberately does **not** export a `decodeProjectPath`: project-folder encoding (`-` for path separators) is lossy for hyphenated paths and cannot be reliably reversed. Read `cwd` from JSONL entries, or use `readProjectPathFromJsonl` in `discovery.ts`, instead of trying to decode the folder name.

### Core module responsibilities

- `platform.ts` — OS detection (including WSL1/WSL2 discrimination) and path translation between conventions. Also resolves the Claude config dir: `--*-config-dir` flag → `CLAUDE_CONFIG_DIR` env → `~/.claude`.
- `discovery.ts` — walks a config dir's project folders (`<configDir>/projects/<encoded-path>/<sessionId>.jsonl`) to find sessions matching a project path / session ID.
- `rewriter.ts` — rewrites `cwd`, tool-result content (string and text-block forms), `toolUseResult` stdout/stderr, and file-history snapshot keys via a two-stage pipeline: exact mappings (project/config/home, longest-first) with cross-family tail-separator normalization, then cross-family token translation through `translatePath`. `gitBranch` is NOT rewritten (branch names are not paths). User text and assistant text/thinking are never rewritten. Path mappings must be sorted longest-first to avoid prefix collisions (see commit 948c763).
- `manifest.ts` — reads/writes the `manifest.json` inside an export bundle (records source platform, project path, session list, Claude version, export timestamp) and owns **every hash a bundle carries**. Three layers, all damage detection and none of it attestation (see #37): per-session `integrityHash` over the JSONL; `layerDigests`, one aggregate per session per auxiliary layer (`subagents`/`tool-results`/`file-history`, over the sorted name+content-hash pairs — one per layer rather than per file because detection is identical and a real session was measured with 106 file-history entries); and `sessionsDigest`, a digest of the whole session inventory that catches a manifest which is internally self-consistent but wrong (a record dropped, a hash edited). `writeManifest` is the SINGLE place `sessionsDigest` is computed — any caller that edits the session list is restamped automatically, and a test fixture that rewrites a bundle manifest by hand must restamp it too. It deliberately covers only the session list: `hub/push.ts` patches `projectId`/`workspace`/`carry` into a staged manifest in place, and widening the digest would make every hub bundle fail its own check.
- `archiver.ts` — `tar.gz` (always available) and `tar.zst` (falls back to gzip if `zstd` binary missing; sets `actualFormat` to signal the fallback to the skill layer). zstd intermediates are written to a private temp dir (never next to the destination file), and tar entries are validated before extraction — absolute paths, `..` segments, and symlink/hardlink entries are rejected outright. **Measured, not assumed:** gzip's CRC32 makes a truncated *and* a bit-flipped `.tar.gz` throw out of node-tar, while `.tar.zst` is only equally loud because the zstd CLI defaults to an XXH64 frame checksum — with `--no-check` a flipped byte decompresses silently to different bytes. `zstdFrameHasContentChecksum` reads the 5-byte frame header instead of passing a `--check` flag an older zstd would reject; `createZstdArchive` refuses (and cli.ts falls back to gzip), extraction only warns, because the manifest hashes cover the content either way.
- `jsonl.ts` — bounded JSONL IO (first/last line, line count) — use these instead of whole-file reads for metadata. **Never derive session metadata from the literal first or last line.** Claude Code brackets a transcript with uuid-less *bookkeeping* entries (`last-prompt`, `mode`, `permission-mode`, `ai-title`, `agent-name`, `pr-link`, `queue-operation`, `file-history-snapshot`, `file-history-delta`, and whatever it ships next) that carry no `uuid`, no `timestamp` and no `cwd`; measured on real transcripts, 31% of all line boundaries (1,903 of 6,187 lines) have such an entry as the preceding line, and 7 of 7 sessions began with one. Use `readLastConversationEntry` / `readFirstConversationEntry` (and `readLastEntryUuid`, which is built on the former) — bounded backward/forward scans that stop at the first entry passing `isConversationEntry`. That predicate is structural (a non-empty string `uuid` — the chain identity `parentUuid` points at), never a type denylist, which would go stale on the next Claude Code release. Both scans read at most `MAX_ENTRY_SCAN_BYTES` and return `null` rather than a stale, earlier entry when the window runs out or an intervening line is unreadable. It answers "is this entry part of the conversation" exactly; it does **not** answer "is this the entry the next one chains onto" — a transcript is a tree, and 4.6% of consecutive conversation-entry pairs have `next.parentUuid !== prev.uuid` (sibling fans, mostly `attachment` runs), which is a separate, pre-existing source of continuation chain-mismatches.
- `exporter.ts` / `importer.ts` / `migrator.ts` — orchestrators. Export copies only; migrate is export+import+delete-source and only runs same-machine. Migrate accepts an optional `currentCwd` (wired from `process.cwd()` in `cli.ts`) and emits a "self-migration" warning when the caller is running inside the directory being moved — this is the common foot-gun when a user invokes `/sesh-mover:migrate` from the session they're trying to migrate. `--scope current` requires `--session-id`; cleanup deletes only confirmed-moved sessions (imported + skipped-as-duplicate). Import registers sessions in Claude's session index; `--no-register` skips registration (fallback for version-mismatch rejections). Imports are idempotent by default — a per-project content-hash registry in sync-state skips already-imported sessions; `--allow-duplicates` overrides.
- `version-adapters.ts` — schema migrations between Claude Code JSONL versions; called during import when source/target Claude versions differ.
- `paths.ts` — every on-disk name the plugin owns, in one place: `PROJECT_DIR_NAME`/`USER_DIR_NAME` (`.sesh-mover`), the three committed root dotfiles (`.sesh-mover-include`, `.sesh-mover-ignore`, `.sesh-mover-project.json`), and `PLUGIN_STATE_NAMES`, which `hub/workspace.ts` turns into the `NEVER_INCLUDABLE` floor by adding `.git` — so a name added here is protected on the carry side and the apply side at once. **There is exactly one copy of that list**; a second, hand-written one is how a name ends up protected on the carry side and not on the apply side. Editing it in either direction is a security change, pinned by exact-contents assertions in `tests/paths.test.ts` and *two* sites in `tests/hub-workspace.test.ts` (they move together). The split is by **lifecycle**: `.sesh-mover/` holds generated exports (gitignored), the three dotfiles hold config/identity (committed); one directory holding both is what forced the old `.gitignore` negation. `userSeshMoverDir()` is a plain `join(homedir(), ".sesh-mover")` — 0.8.0 removed the 0.7.0 rename-on-first-run along with every other legacy path check, so nothing in this file probes the filesystem and nothing warns about an old name. A pre-0.8.0 directory or list file is inert clutter, never a fallback read.
- `config.ts` — two-tier config: user (`~/.sesh-mover/config.json`) merged with project (`<cwd>/.sesh-mover/config.json`); project overrides user. `computeEffectiveConfig` is the merge site (used by `cli.ts`'s `loadEffectiveConfig` and by `hub/status.ts`) — it layers each layer's *raw, non-backfilled* file contents onto the defaults, rather than merging two independently defaults-backfilled config objects. The latter (what an earlier `mergeConfigs(readConfig(user), readConfig(project))` call did) silently reset any user-scope-only setting back to its default whenever the project-scope file was simply absent, because `readConfig` always backfills defaults even for a missing file — fixed in 57cd7b7; affects `export`, `migrate`, and `configure --show` too.
- `summary.ts` — extracts a short session summary for export names/browse listings. `--no-summary` (or `export.noSummary` in config) is functional: it skips JSONL parsing for the summary entirely and sets the manifest `summary` to the session slug, so no conversation text is copied into the manifest.
- `memory-index.ts` — the `MEMORY.md` union (#49). A memory index is a list of markdown pointer lines, and it has a well-defined union: dedup by link target, keep every local line verbatim, append incoming pointers **after the last pointer line** rather than at EOF (otherwise they land under a file's trailing prose and read as commentary). It never reorders, rewrites or deletes a local line — including a pointer whose target is missing, because a dead link beats a live file nothing points at. Matching is a two-pointer scan, never a regex (same rule as `workspace.ts`, for the same measured reason).
- `sidecar.ts` — `copyToUniqueName`, the `COPYFILE_EXCL` + numeric-suffix loop that guarantees a parked copy never eats an earlier one. **Exactly one copy of it**, shared by `hub/merge.ts`'s `writeSidecar` (`<name>.theirs-<stamp>`) and the importer's memory parking (`<stem>.incoming.md`); deleting the `COPYFILE_EXCL` fails tests in both suites, which is the check that they really share it rather than currently agreeing.
- `sync-state.ts` — per-project peer sync bookkeeping (peers, lineage, imported registry), one file per project keyed by encoded project path. **Invariant on `recordSentToPeer`:** it credits a peer's "already has it" ledger, and its only caller is hub pull, where the content demonstrably just came from the hub — so any future transfer path that moves sessions between machines *without* going through the hub must not credit the hub ledger here, or the next push ships only a delta and leaves a continuation chain on the hub with no base bundle to anchor it. Schema `v2` (additive): a `hub` block (`hubId` + `threadByLocalSession`, written by `hub/push.ts`/`hub/pull.ts` via `setThreadId`, plus `workspaceGenerations`/`lastWorkspace` written by push/pull's workspace half) is added lazily, only once a project first pushes/pulls through a hub — plain incremental-sync users never see `schemaVersion` leave `1`. A plugin version that predates the hub and encounters a `v2` file doesn't recognize it, treats it as corrupt, and renames it aside (fresh state) — that costs only peer/thread bookkeeping, never session data.

### Hub module responsibilities (`src/hub/`)

The hub is a shared directory (filesystem backend only, in Slice 1 — any path that behaves like a shared filesystem: network share or synced folder) that every participating machine points at via `hub.path` in config, holding per-project bundles plus **one index file per machine**. Two invariants hold the whole design together:

- **Per-machine ownership** — a machine only ever writes its own index file (`index/<machineId>.json`, see `layout.ts`'s `indexPath`) and its own bundles; it never touches another machine's files. This is what makes concurrent push/pull from *different* machines safe without a distributed lock — the same-machine advisory lock (`lock.ts`) only ever has to guard one machine's own writes against itself, not against other machines.
- **Derivable indexes** — everything an index file records (thread → bundle history) is reconstructible from the bundles on the hub plus this machine's local sync-state (which thread each local session belongs to). `hub reindex` (`reindex.ts`) is this invariant made executable: a repair tool for a lost/corrupt index, not a sync primitive.

Module map: `backend.ts` (the `HubBackend` interface — `read`/`writeAtomic`/`list`/`exists`/`delete` — and `createFsBackend`, the only implementation in Slice 1; it doesn't detect sync state itself — `pull-select.ts` checks whether index-referenced files exist on this machine's copy of the hub directory and returns a structured `not-yet-synced` result, rather than throwing, when they're missing) · `layout.ts` (hub-relative path builders and the on-disk schema types — `HubJson`, `HubProjectJson`, `HubBundleRecord`, `HubThreadEntry`, `HubIndexJson` — plus `assertSafeHubId`, the path-safety chokepoint every id passes through before it's used in a hub path) · `identity.ts` (project identity — `.sesh-mover-project.json` at the project root, meant to be committed, holds the project's `projectId`; `normalizeGitRemote` + matching lets a project link to the same hub project from any clone via its git remote) · `lock.ts` (the same-machine advisory lock, with stale-lock stealing after `LOCK_STALE_MS`) · `index-file.ts` (`buildIndexFile` — a pure projection of local sessions + prior index + new bundle records — plus read/write for a machine's own index and `readAllIndexes` across every machine) · `threads.ts` (`resolveThreads` — a deterministic latest-copy tiebreak across every machine's index; load-bearing for "which machine has my latest work", so it must never depend on iteration/insertion order — plus `findUnfetchableBundles`, the disclosure that a pull fetches only the resolved machine's bundle list, so a thread whose history spans two *other* machines cannot arrive whole; it is a diagnostic only — it reads no `pushedAt` and merges nothing into the source's bundle list, and its silence on the ordinary two-machine flow is structural) · `workspace.ts` (git-less project snapshot/unpack, `.sesh-mover-ignore` exclusion patterns) · `merge.ts` (repo-less 3-way workspace merge — shells out to `git merge-file`, which needs no repository; `isGitMergeFileAvailable` is the probe callers use to choose merge mode vs no-ancestor mode, and `mergeWorkspaceTrees` never deletes a file, never writes through a symlink, and degrades to "keep local, park the incoming copy beside it" whenever it cannot merge) · `carry.ts` (`captureCarry` — the git-project counterpart of `snapshotWorkspace`: `git diff HEAD --binary --relative` plus untracked files, written to `carry/` in the bundle. The two are mutually exclusive by construction, on a THREE-way `GitRemoteScan` (`identity.ts`): `remotes` takes the carry, `none` takes the workspace snapshot, and **`unknown` — git present but unable to answer — takes NEITHER**, because an unfiltered whole-tree snapshot is only safe for a project that genuinely has no remote. That third arm is the security-critical one and is what `hasGitRepoMarker` feeds (see #50). It is not a `localGitRemotes().length` check; an earlier version of this file said it was. `.sesh-mover-include` is the one rule the two builders share — every path either builder admits goes through `workspace.ts`'s `isCarriedPath`/`isReIncluded`, never a second copy of the rule. The patch is handled as BYTES end to end: a `git diff` of a text file that is not valid UTF-8 does not survive a string round trip, and git then refuses the patch) · `append.ts` (`tryAppendContinuation` / `adoptHubBranch` — the only two places that mutate a transcript the user already owns; see the guards below) · `hooks.ts` (`evaluateHookGate`, the shared consent gate for the two hook endpoints) · `init.ts` / `status.ts` / `push.ts` / `whereis.ts` / `reindex.ts` (one orchestrator per CLI verb; each of push/pull/reindex acquires the project lock before writing hub state) · and **the pull pipeline**, which is no longer one orchestrator: `pull.ts` is sequencing only (~300 lines) over eight stage modules — `pull-resolve.ts` (identity, machine registration, index read), `pull-select.ts` (thread + bundle selection, and repair — it WRITES sync-state), `pull-fetch.ts` (download, extract, both integrity guards), `pull-apply-workspace.ts` (ancestor choice, merge/unpack/skip), `pull-apply-sessions.ts` (rewrite, adapt, then append/adopt/import), `pull-apply-carry.ts`, `pull-record.ts` (thread mapping + index projection), plus `pull-apply-state.ts` (the per-pull mutable accumulators, passed by reference and never copied) and `pull-stages.ts` (the shared outcome contract: `applied`/`skipped`/`refused`/`aborted`, where `refused` is apply-safe and `aborted` stops the pull). Two stages deliberately do NOT use that shared contract — `resolve` carries structured `linkCandidates` a refusal would destroy, and `select` has seven exits including one that is `success: true`.

### Slice-2 invariants (append, merge, carry)

- **Append guards (`append.ts`).** A pulled continuation is spliced onto an existing local transcript only when all of them pass: the delta's anchor equals the base's head (chain guard — never skipped, not even by `--force-append`), the base was not modified in the last 5 minutes (liveness — this is the one `--force-append` overrides), and the bundle's content matches its manifest hash. The delta must be path-rewritten and version-adapted **before** it reaches `tryAppendContinuation` — the module does neither, so `pull.ts` builds the real source→target `RewriteContext` first. Rollback rule, and it applies to `adoptHubBranch` too: a truncate or whole-file restore is only ours to perform if the file's size is exactly what our own mutation accounts for (bytes-before + `WriteStream.bytesWritten`); otherwise **refuse and throw** rather than report a clean restore over another writer's bytes. The liveness check's self-write exemption is a heuristic (`opNowMs` is truncated to a whole ms and captured once for the whole pull), documented at the comparison site — making it exact needs a recorded write-time, not a finer clock.
- **Merge ancestor (`merge.ts` + `chooseMergeAncestor` in `pull-apply-workspace.ts`).** A 3-way workspace merge may only use a generation **common to both trees**, decided by set membership and never by a clock: ours is `SyncState.hub.workspaceGenerations` (bounded 50), theirs is `manifest.workspace.basedOn.bundleId` collected across the pull's whole bundle chain, and the newest member of the intersection wins. An empty intersection means *no ancestor* (skip), not a guess; fallback goes strictly older, because an older base fails toward "keep local + visible conflicts" while a newer one fails toward silently overwriting work. `pushedAt` is a diagnostic only — the hub stamps nothing, so it is the pushing machine's wall clock, and ordering by it reinstates a measured silent-revert bug under clock skew. Never merge into an empty/metadata-only tree (`pull-apply-workspace.ts` gates on `hasRealContent`), and never record a generation for a payload that was not applied.
- **`.sesh-mover-ignore` vs `.sesh-mover-include` (`workspace.ts`).** They deliberately disagree on a trailing slash: `.sesh-mover-ignore` matches per path *segment* (so `dir/` is decoration — it excludes `dir` at any depth), `.sesh-mover-include` matches whole *relative paths* (so any `/` in a pattern, trailing included, roots it at the project). Don't harmonize them. Glob matching is a two-pointer matcher, never a regex (the regex it replaced was a measured ReDoS). `.git` plus `PLUGIN_STATE_NAMES` (`.sesh-mover`, `.sesh-mover-include`, `.sesh-mover-ignore`, `.sesh-mover-project.json`) are the `NEVER_INCLUDABLE` floor and can't be re-included by any pattern or spelling — the load-bearing check is the per-segment **path**-side one, not the pattern-side guard. Two things about that list are permanent rather than incidental to whichever rename happened last: there is exactly ONE copy of it, so the workspace walk, the merge, the unpack, the `git` pathspecs and the patch byte scan cannot disagree; and the root dotfiles need it *more* than the directory does, since there is no directory segment between a payload and a file it can name directly. 0.8.0 removed three retired spellings from it — safe only because that release reads none of them, so a payload writing one plants inert clutter rather than a file some reader consults. Any name this plugin *does* read must be on the list. `.claude` is deliberately not on the floor: the dividing line is what a name can *do* (redirect the hub, rewrite what the next push ships, overwrite a VCS store), not what it contains. Apply side: a payload is filtered by the floor plus the *target's* own `.sesh-mover-ignore` (minus its `.sesh-mover-include`) and by nothing else — re-applying the built-in convenience excludes there silently discarded files the sender had deliberately listed.
- **Carry (`carry.ts`).** `git diff` is porcelain: the shipped invocation (`--no-ext-diff --no-textconv --no-color --src-prefix=a/ --dst-prefix=b/ -U3 --submodule=short --ignore-submodules=none --relative`) and `gitChildEnv()`'s environment scrub are each individually load-bearing against ordinary user config, including for a *security* property (`GIT_LITERAL_PATHSPECS=1` silently disables the floor's `:(exclude,…)` pathspecs). Audit any future porcelain git call on user data the same way. The safety guarantee has **two halves that differ** — every filter applies to the untracked enumeration; none of them filter the patch, so a gitignored-but-tracked file's changes travel (disclosed in the sibling field `trackedIgnored`, never folded into `reIncluded`, whose remedy would be wrong for it). On the apply side the floor is enforced from **git's own parse, and only git's** (#38): `git apply --numstat -z --summary`, read once, because git parses a patch into one entry list and then walks *that same list* to print `--numstat`, to print `--summary`, and to write the files — two invocations differing only in mode cannot disagree. `--numstat` gives every destination; `--summary` gives the rename and copy SOURCES it never prints, and is read against a **closed grammar** of git's summary shapes, so an unaccounted line refuses the whole payload rather than being skipped. That closed grammar is not fastidiousness: a destination is attacker-controlled and `--summary` interpolates it raw, so a destination containing a newline splits the only line carrying the source — measured, and it applied, deleting a floor-protected file. The older design read the patch bytes as a *second* floor source; that is gone, because it had holes git does not (it read `rename from` but never `copy from`, and a copy-out of a plugin internal applied and was then re-uploaded by the next push — also measured). The byte scan survives for exactly two jobs: **symlinks**, which stay enforcement because `--summary` prints nothing at all for a re-pointed one, and advisory README wording on a receiver with no runnable git. The write path is gated on git having answered *about the patch*, not merely about the directory — the directory probe succeeding does not mean the floor call did. A refusal is whole-payload, never partial.

### Shared layers: `memory/` and `plans/`

They land in a directory the TARGET owns, not under a session id the import minted, so they are reconciled rather than restored — and the two travel differently on purpose.

- **`memory/` ships on incremental bundles**, skipped only when the peer demonstrably already holds that exact directory (a `memoryDigest` recorded on the peer entry *after* the bundle commits, describing the bundle's own copy rather than the source's — so a copy truncated in flight fails toward re-sending). Every unknown ships: first push, `--since`, a reset state file. Before #53 the `!incremental` gate meant **no hub bundle ever carried memory at all**, while the manifest declared it — that gate was deliberate for `export --incremental` ("incremental is session-level", 2026-04-21) and was extended to the hub three months later by accident, because `hub push` passes a truthy `incremental` unconditionally.
- **`plans/` deliberately does NOT travel to the hub.** `<configDir>/plans` is config-dir-global with no project filter, so it ships *every plan on the machine*. On a plain export that is the user's own interactive call landing in their own directory; on the hub it would go out over the default-on, unattended SessionEnd auto-push, which has no channel to disclose what it just uploaded. Fix the payload's scope before widening its transport.
- **`includedLayers`/`exportedLayers` mean CONTENT, not policy** (#53): a layer is listed iff its payload is on disk in the bundle. They used to be `getAllLayers()` minus `--exclude`, stamped regardless of what the export did, which made every hub bundle declare layers it did not carry and made `--exclude jsonl` omit `jsonl` from a manifest whose bundle plainly contained it.

### Hook registration (`hooks/hooks.json`)

The hub's automation is driven by two Claude Code lifecycle hooks, registered in `hooks/hooks.json` and implemented by the internal CLI endpoints `hub hook-session-end` (auto-push) and `hub hook-session-start` (freshness notice). Neither endpoint is a slash command, so neither appears in `plugin.json`'s `commands` array.

These facts were verified against the installed Claude Code build's own embedded schema (2.1.221) and re-verified end-to-end in a real session. They are not guesses — check them again before changing this file. The three that a well-meaning edit is most likely to undo (SessionEnd `async`, SessionEnd **no** `timeout`, SessionStart sync + bounded) are pinned by tests in `tests/hub-hooks.test.ts`, because `hooks.json` itself cannot carry a warning: the loader rejects JSONC, so a `//` comment makes the file silently fail to load and the hooks never fire.

- **The file's existence *is* the registration.** Nothing else references it — no manifest entry, no code path — so if `hooks/hooks.json` is missing, renamed, or unparseable, both hooks simply never fire and no error appears anywhere. (It also means the automation ships with the *plugin* install, not with the npm package: `package.json`'s `files` is `["dist"]`, so `npx claude-sesh-mover` gets the CLI and no hooks.)
- **`hooks/hooks.json` at the plugin root is auto-loaded by path.** The `hooks` field in `.claude-plugin/plugin.json` is for *additional* hook files ("in addition to those in hooks/hooks.json, if it exists"); pointing it at `hooks/hooks.json` is rejected as a duplicate. So do **not** add a `hooks` field to the manifest. Root shape is `{"hooks": {"<Event>": [{"matcher": …, "hooks": [ … ]}]}}`.
- **`${CLAUDE_PLUGIN_ROOT}` only expands in a plugin's `hooks/hooks.json`,** never in `settings.json`. Keep the `node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" …` shell form: it works on every version that supports plugin hooks. (2.1.221 also accepts a safer exec form — `"command": "node", "args": [...]` — but an older build would drop the unknown `args` key and run bare `node`.)
- **`async: true` on the SessionEnd hook is load-bearing, not an optimization.** Claude Code gives *all* SessionEnd hooks a shared 1.5s budget (`getSessionEndHookTimeoutMs`, floor 1500ms) and then force-exits; a push routinely exceeds that. `async: true` backgrounds the hook in a detached process that survives Claude Code's exit. Conversely, **never set `timeout` on the SessionEnd hook**: that function raises the *shared* budget to the largest timeout any registered SessionEnd hook declares, so a timeout here would delay session exit for every other plugin's hooks too. The corollary is worth knowing before you debug it: because we declare no timeout and `async: true` spawns the hook *detached*, Claude Code cannot bound this hook at all — a push wedged on an unreachable network share leaves an orphaned `node` process running indefinitely. The project lock keeps a wedged push from piling up behind itself only for `LOCK_STALE_MS` (10 minutes) — `acquireProjectLock` steals a lock older than that without checking whether the holder is still alive, so a long-wedged push accrues roughly one orphan per 10-minute window, and nothing reaps any of them.
- **SessionStart must stay synchronous.** An async hook is backgrounded and its stdout is discarded, so context injection only works on a sync hook. It carries `timeout: 10` instead, so a slow or unreachable hub can never stall session start.
- **Valid SessionStart matcher values are `startup`, `resume`, `clear`, `compact`, `fork`** (matched against the payload's `source`). We register only `startup` and `resume` — `clear`/`compact` are mid-session events where a "newer work elsewhere" notice would be noise.
- **Stdin payload field names** (common to both events): `session_id`, `transcript_path`, `cwd`, plus optional `prompt_id`, `permission_mode`, `agent_id`, `agent_type`. SessionStart adds `source`; SessionEnd adds `reason`.
- **SessionStart context-injection output shape:** `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"…"}}`.

Both endpoints are the sanctioned exception to the one-JSON-result stdout contract: they print nothing (or, for SessionStart, exactly one hook-JSON object) and **always exit 0**. See `src/hub/hooks.ts` for the shared gate — linking a project IS the consent gate, so both flags default on yet stay inert for anyone who never uses the hub.

### Export storage layout

Exports land in `<homedir>/.sesh-mover/<name>/` (user scope) or `<cwd>/.sesh-mover/<name>/` (project scope) — build both from `paths.ts` (`userSeshMoverDir()` / `projectSeshMoverDir()`) rather than joining the literal name, so the user-scope migration is never bypassed. A directory export is `<name>/` with `manifest.json` + session JSONL + referenced layer files. For `--format archive`/`zstd`, the exporter writes that directory as a staging area, tars it to `<name>.tar.gz` or `<name>.tar.zst` in the parent, then removes the staging directory; the archive is the sole artifact, and `ExportResult.exportPath` is set to the archive path (equal to `archivePath`). `browse` scans both user and project directories.

### Migrate flow (self-migration hazard)

`migrate` = export + import + cleanup + optional `--rename-dir`. Because it deletes source session files and may `mv` the source project directory, running it from inside the session being migrated is unsafe:

- The running Claude Code session holds the source JSONL open and keeps appending to it; anything said after the migrate snapshot goes to the now-deleted source path and Claude Code recreates the file, orphaning the session with a stale `cwd`.
- If `--rename-dir` is passed, the shell's cwd disappears under subsequent tool calls.

`migrator.ts` **blocks actual self-migration runs by default** (returns `ErrorResult` with a recovery-step `suggestion`) whenever `currentCwd` is inside `sourceProjectPath`. Dry-run still previews (with a warning), and `--force` overrides the block for advanced use. The recommended flow for moving the active session is: exit Claude Code, `cd` to a stable outer path (`~` or similar), start a new Claude Code session there, then run `/sesh-mover:migrate`. Merging into a target project dir that already has sessions is supported, so the recovery flow is safe even when target sessions are already in place.

### Testing conventions

Vitest with fixtures under `tests/fixtures/`. Integration tests (`tests/integration.test.ts`) build full export/import round-trips against fixture config dirs — do **not** mock filesystem or archive operations; use real temp dirs (`mkdtempSync`). When adding a new JSONL entry variant, update both `src/types.ts` and the fixture JSONL; rewriter/version-adapter tests rely on realistic shapes.

### When adding a command or CLI option

1. Extend `src/cli.ts` with the Commander subcommand/option.
2. Add the matching result shape to `src/types.ts` (every CLI result is typed).
3. Update `commands/<name>.md` and (if the behavior needs explanation for the skill layer) `skills/session-porter/SKILL.md`. If the command is new (not just a new option on an existing one), add its `./commands/<name>.md` path to `.claude-plugin/plugin.json`'s `commands` array too — Claude Code only loads slash commands listed there, so a new doc file with no matching entry silently never appears as a slash command.
4. Rebuild with `npm run build` **and stage the updated `dist/`** — it's committed so installed plugins pick up the change. A commit that touches `src/` without a corresponding `dist/` update will ship a stale binary.
