# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Names

- **npm package / GitHub repo:** `claude-sesh-mover` — the `claude-` prefix makes the scope obvious to a browser of the npm/GitHub ecosystem.
- **Plugin name (in `.claude-plugin/plugin.json`):** `sesh-mover` — this is what drives slash command prefixes (`/sesh-mover:export`, etc.), so it stays short.
- **CLI bin:** `sesh-mover` — matches the plugin name for in-session discoverability.
- **On-disk paths:** `sesh-mover`, always — a dotfile is the short name, not the package name. `~/.sesh-mover/`, `<project>/.sesh-mover/`, and the three committed root dotfiles `.sesh-mover-include` / `.sesh-mover-ignore` / `.sesh-mover-project.json`. They are declared once in `src/paths.ts`; never hand-write one of these literals elsewhere. **0.8.0 is a clean break:** no retired spelling is read, migrated, warned about, or on the `NEVER_INCLUDABLE` floor — `.claude-sesh-mover` (pre-0.7.0) and `.sesh-mover-hubinclude` / `.sesh-mover-hubignore` (0.7.0 only) are gone from the codebase entirely. Don't reintroduce them.

Don't change any of these without updating the others *and* every slash command reference in `commands/*.md`, the skill doc, and this file.

## Commands

- `npm run build` — compile TypeScript to `dist/`. **`dist/` is committed to the repo** (not gitignored) so that users installing via `/plugin install` get a working plugin without a build step. Rebuild and stage `dist/` alongside any `src/` change.
- `npm run lint` — type-check only (`tsc --noEmit`).
- `npm test` — run full vitest suite once.
- `npm run test:watch` — vitest in watch mode.
- Run a single test file: `npx vitest run tests/rewriter.test.ts`
- Filter by test name: `npx vitest run -t "translates WSL paths"`
- Invoke the built CLI directly: `node dist/cli.js <command> [options]` (every command emits a single JSON object to stdout; parse it — the two internal hook endpoints, `hub hook-session-end` / `hub hook-session-start`, are the deliberate exception and speak Claude Code's hook protocol instead).

## Architecture

claude-sesh-mover is a Claude Code **plugin** (not a standalone app) that exports, imports, and migrates Claude Code sessions across machines, OS/path conventions (macOS/Linux/Windows/WSL), config directories (e.g. `~/.claude` vs `~/.claude-tzun`), and project paths.

The design is **hybrid: deterministic Node.js core + conversational skill layer.**

- `src/` compiles to `dist/cli.js`, a Commander-based CLI with subcommands: `export`, `import`, `migrate`, `browse`, `configure`, `push`, `pull`, `whereis`, and the nested `hub init` / `hub status` / `hub unlink` / `hub reindex` / `hub encrypt` / `hub rekey` / `hub trust` / `hub escrow` / `hub retire` / `hub delete` / `hub compact` (retirement is two verbs rather than one verb with a flag: the phases have opposite risk profiles and a flag puts the irreversible one a keystroke from the reversible one). Every command returns structured JSON keyed by `success` and `command` (see `src/types.ts` for result shapes — `ExportResult`, `ImportResult`, `MigrateResult`, `BrowseResult`, `ConfigureResult`, `ErrorResult`, and the hub shapes `HubInitResult`, `HubStatusResult`, `HubPushResult`, `HubPullResult`/`HubPullListResult`, `WhereisResult`, `HubReindexResult`, `HubRetireResult`/`HubDeleteResult`, `HubEncryptResult`, `HubRekeyResult`, `HubEscrowResult`/`HubEscrowRefusedResult`, `HubCompactResult`/`HubCompactPendingResult`/`HubCompactRefusedResult`, `HubTrustResultShape`/`HubTrustRefusedResultShape` — the `Shape` suffix is because `hub/trust.ts` declares its own structurally identical `HubTrustResult`/`HubTrustRefusedResult`, and the `CliResult` union member is the `types.ts` pair — plus the shared `HubUnlinkedResult`/`HubLockBusyResult`/`NotYetSyncedResult`/`HubProjectRetiredResult`/`HubRetireFailedResult`/`HubEncryptRefusedResult`/`HubEncryptionRefusedResult` error shapes). Alongside the JSON it exits with a code naming the outcome CLASS — see "CLI exit codes" below. The two internal hook endpoints — `hub hook-session-end` and `hub hook-session-start` — are the sanctioned exception to both contracts: they speak Claude Code's hook protocol instead (nothing on stdout, or for SessionStart exactly one hook-JSON object, and **always** exit 0). See "Hook registration" below.
- `commands/*.md` + `skills/session-porter/SKILL.md` are markdown-based slash commands loaded by Claude Code when the plugin is installed. They shell out to the CLI, parse the JSON, and drive UX (confirmations, path-collision handling, prune prompts, registration fallback when Claude Code rejects an imported session).
- `.claude-plugin/plugin.json` is the plugin manifest consumed by Claude Code's plugin cache — its `commands` array must list every `commands/*.md` doc (a doc not listed there never loads as a slash command, even if the file exists); `.claude-plugin/marketplace.json` sits alongside it for marketplace listing.
- `hooks/hooks.json` registers the plugin's Claude Code lifecycle hooks. See "Hook registration" below — this file is **auto-loaded by path**, so it must not also be referenced from `plugin.json`.
- `src/index.ts` is the library entrypoint — it re-exports the core modules so the package can also be consumed programmatically, and that list is public surface: `errors.ts` (`errorMessage`, #102) and `latched-write.ts` (`latchedWriteStream`, #16) are on it and are therefore public surface — a consumer catching our rejections or driving our streaming writers gets the same two primitives the CLI uses, so changing either's contract is a library change, not an internal one. As of 0.11.0 it does **not** re-export `hub/trust.ts`, `hub/compact.ts`, `hub/compact-plan.ts`, or the signing modules (`crypto/signing-key.ts`, `hub/signature.ts`, `hub/pins.ts`) — every other hub verb is exported, and `preflight.ts`'s whole argument for living in a hub module is that `hubPush`/`hubPull` have a programmatic caller — and no ruling records the omission, so treat it as unexamined rather than deliberate. It deliberately does **not** export a `decodeProjectPath`: project-folder encoding (`-` for path separators) is lossy for hyphenated paths and cannot be reliably reversed. Read `cwd` from JSONL entries, or use `readProjectPathFromJsonl` in `discovery.ts`, instead of trying to decode the folder name.
- **`export`/`import` and `push`/`pull` are the same operation with different transports** (#47), and they now carry the same FILE payload — a whole-project workspace snapshot or a git-diff carry — built and applied by the same code in `src/payload/`. What differs is **polarity, and the polarity IS the security decision** rather than a default someone picked. Capture is opt-**out** on `push` (`--no-workspace`/`--no-carry`), because linking a project is the hub's consent gate and the bundle lands in a directory the user configured; it is opt-**in** on `export` (`--include-workspace`/`--include-carry`, `export.includeWorkspace`/`export.includeCarry`, both defaulting false), because `--output` names any path and the artifact gets scp'd, emailed or handed to someone, so the destination is unknown at capture time. `export --payload-plan` is what makes an opt-in consentable: it runs the same capture in measure-only mode, reports which payload applies and what it would carry, and writes nothing, so `commands/export.md` can disclose before the bundle exists rather than after. On the **apply** side `import` is opt-in per payload (`--apply-workspace`/`--apply-carry`, and `--force-workspace` as a third, separate yes) and **no config key can turn any of the three on** — that asymmetry with the capture side is deliberate: a capture default is a decision a user makes about their own machine's outgoing bundles, while `import --apply-workspace` is the first place this plugin can write project files out of a bundle a *stranger* produced (every payload before #47 came from the user's own other machine, through a directory they configured). `pull` sits in between and is not a model for either: it applies the workspace by default and takes the carry only on `--apply-carry`. Do not "harmonize" any of these polarities.

### CLI exit codes

**One code per CLASS of outcome, and the class is a property of the result SHAPE — never of which code path printed it** (#76). The JSON body stays the contract for detail; the exit code is what a shell caller gets to branch on without parsing it.

| code | class | meaning |
|---|---|---|
| `0` | success | it happened |
| `1` | the command did not run | a bad invocation (Commander's own validation, `--on-divergence bogus`, `--set` type errors) or an unexpected failure — anything that reached a command's `catch` |
| `2` | refusal | understood and declined; nothing was done and the body says why (`unlinked`, `no-such-project`, "already up to date", the pick-required listing) |
| `3` | environment-not-ready | the invocation was fine and the machine is not (`hub-unreachable`, `lock-busy`, `not-yet-synced`). **This is exactly the retryable set** — the property that earns it a code of its own |

`exitCodeForResult` in `src/types.ts` is the single mapping, and it lives beside `CliResult` on purpose: its `Record<CliResultReason, ExitCode>` table is *exhaustive* over the union, so a new result type carrying a new `reason` fails to compile until someone assigns it a class. `src/cli.ts` has exactly two output chokepoints — `output()` (the shape decides) and `outputError()` (a throw, always 1) — and there must not be a third. The defect this replaced was precisely that the code was decided by whichever helper a site happened to call, so every typed refusal exited 0 next to every success and `sesh-mover hub pull || handle_failure` was a silent no-op for the whole refusal class.

Three things about it that look like mistakes and are not:

- **`pickRequired` is `success: true` and exits 2.** `pull` with neither `--thread` nor `--latest` pulls nothing — it lists the threads and waits to be told which. "Success means 0" is the simplification that would undo it.
- **A `success: false` result with no `reason` defaults to 2, not 1.** What reaches that default is an `ErrorResult` a command *returned* as a value, having got far enough to describe the outcome. A thrown failure never reaches it. The residual imprecision is known and stated at the function: a few of those returned `ErrorResult`s are caught exceptions (`hubInit`'s mkdir failure, `importSession`'s unreadable bundle) and are really class 1 — fixing that needs a `reason` on the producing module, not a smarter classifier, because matching on `error` text is forbidden.
- **Both helpers set `process.exitCode` rather than calling `process.exit()`.** `process.exit()` truncates a large JSON body still queued on a piped stdout and skips pending `finally` blocks — `import`'s `finally` removes its archive extract dir, which a failing import used to leak.

**The two hook endpoints are outside this scheme entirely and ALWAYS exit 0** — Claude Code's hook protocol, not a style choice. They call neither helper, which is what keeps the two schemes from meeting; `tests/hub-hooks.test.ts` pins each endpoint against a failure path that is *proved* to make the ordinary verbs exit non-zero.

### Core module responsibilities

- `platform.ts` — OS detection (including WSL1/WSL2 discrimination) and path translation between conventions. Also resolves the Claude config dir: `--*-config-dir` flag → `CLAUDE_CONFIG_DIR` env → `~/.claude`.
- `discovery.ts` — walks a config dir's project folders (`<configDir>/projects/<encoded-path>/<sessionId>.jsonl`) to find sessions matching a project path / session ID.
- `rewriter.ts` — rewrites `cwd`, tool-result content (string and text-block forms), `toolUseResult` stdout/stderr, and file-history snapshot keys via a two-stage pipeline: exact mappings (project/config/home, longest-first) with cross-family tail-separator normalization, then cross-family token translation through `translatePath`. `gitBranch` is NOT rewritten (branch names are not paths). User text and assistant text/thinking are never rewritten. Path mappings must be sorted longest-first to avoid prefix collisions (see commit 948c763).
- `manifest.ts` — reads/writes the `manifest.json` inside an export bundle (records source platform, project path, session list, Claude version, export timestamp) and owns **the trust boundary a parsed manifest crosses**, in three ordered steps that catch disjoint things: `isBundleManifestShape` (*is this a sesh-mover manifest at all* — the `plugin` marker plus an array `sessions`), then `assertSafeManifestIds` (*are its ids path-safe*), then `verifySessionsDigest` (*is this the session list the exporter wrote*). Step one exists because step two does **not** catch a wrong-shaped session list: given `sessions: "abc"` it iterates the string's *characters*, every `.sessionId` is `undefined`, every check passes, and `sessions.length` then reports a fabricated `sessionCount: 3`. There is **exactly one copy** of that predicate (#60, pinned by a structural test) — it drifted once already, with the store-directory scan not checking the marker at all until #33. Note `readManifest` itself does not apply step one, and five callers use it without one. It also owns **every hash a bundle carries**. Three layers, all damage detection and none of it attestation (see #37): per-session `integrityHash` over the JSONL; `layerDigests`, one aggregate per session per auxiliary layer (`subagents`/`tool-results`/`file-history`, over the sorted name+content-hash pairs — one per layer rather than per file because detection is identical and a real session was measured with 106 file-history entries); and `sessionsDigest`, a digest of the whole session inventory that catches a manifest which is internally self-consistent but wrong (a record dropped, a hash edited). `writeManifest` is the SINGLE place `sessionsDigest` is computed — any caller that edits the session list is restamped automatically, and a test fixture that rewrites a bundle manifest by hand must restamp it too. It deliberately covers only the session list: `hub/push.ts` patches `projectId`/`workspace`/`carry` into a staged manifest in place, and widening the digest would make every hub bundle fail its own check. `canonicalize` is exported (#86) so `hub/signature.ts` serializes the signed statement with this module's canonical form rather than a second spelling of it; the digest that statement signs is over the whole plaintext archive and lives on the index record outside it, so it is not a fourth manifest layer — see "Signing invariants (#86)".
- `archiver.ts` — `tar.gz` (always available) and `tar.zst` (falls back to gzip if `zstd` binary missing; sets `actualFormat` to signal the fallback to the skill layer). zstd intermediates are written to a private temp dir (never next to the destination file), and tar entries are validated before extraction — absolute paths, `..` segments, and symlink/hardlink entries are rejected outright. **Measured, not assumed:** gzip's CRC32 makes a truncated *and* a bit-flipped `.tar.gz` throw out of node-tar, while `.tar.zst` is only equally loud because the zstd CLI defaults to an XXH64 frame checksum — with `--no-check` a flipped byte decompresses silently to different bytes. `zstdFrameHasContentChecksum` reads the 5-byte frame header instead of passing a `--check` flag an older zstd would reject; `createZstdArchive` refuses (and cli.ts falls back to gzip), extraction only warns, because the manifest hashes cover the content either way.
- `jsonl.ts` — bounded JSONL IO (first/last line, line count) — use these instead of whole-file reads for metadata. **Never derive session metadata from the literal first or last line.** Claude Code brackets a transcript with uuid-less *bookkeeping* entries (`last-prompt`, `mode`, `permission-mode`, `ai-title`, `agent-name`, `pr-link`, `queue-operation`, `file-history-snapshot`, `file-history-delta`, and whatever it ships next) that carry no `uuid`, no `timestamp` and no `cwd`; measured on real transcripts, 31% of all line boundaries (1,903 of 6,187 lines) have such an entry as the preceding line, and 7 of 7 sessions began with one. Use `readLastConversationEntry` / `readFirstConversationEntry` (and `readLastEntryUuid`, which is built on the former) — bounded backward/forward scans that stop at the first entry passing `isConversationEntry`. That predicate is structural (a non-empty string `uuid` — the chain identity `parentUuid` points at), never a type denylist, which would go stale on the next Claude Code release. Both scans read at most `MAX_ENTRY_SCAN_BYTES` and return `null` rather than a stale, earlier entry when the window runs out or an intervening line is unreadable. It answers "is this entry part of the conversation" exactly; it does **not** answer "is this the entry the next one chains onto" — a transcript is a tree, and 4.6% of consecutive conversation-entry pairs have `next.parentUuid !== prev.uuid` (sibling fans, mostly `attachment` runs), which is a separate, pre-existing source of continuation chain-mismatches.
- `exporter.ts` / `importer.ts` / `migrator.ts` — orchestrators. Export copies only; migrate is export+import+delete-source and only runs same-machine. Migrate accepts an optional `currentCwd` (wired from `process.cwd()` in `cli.ts`) and emits a "self-migration" warning when the caller is running inside the directory being moved — this is the common foot-gun when a user invokes `/sesh-mover:migrate` from the session they're trying to migrate. `--scope current` requires `--session-id`; cleanup deletes only confirmed-moved sessions (imported + skipped-as-duplicate). Import registers sessions in Claude's session index; `--no-register` skips registration (fallback for version-mismatch rejections). Imports are idempotent by default — a per-project content-hash registry in sync-state skips already-imported sessions; `--allow-duplicates` overrides. Both ends also handle the file payload (#47), and both delegate to `src/payload/`: export calls `capturePayload` once and sets `workspace`/`carry` **in the manifest literal** before the single `writeManifest` (never patched in afterwards the way `hub/push.ts` has to, and never with a `basedOn` — an export mints no hub generation); import's `reconcilePayloadLayers` unpacks or applies, or declines and counts. Two import rules are load-bearing. A non-empty target project directory is refused as a **precondition** (step 1c, beside the step-1b integrity gate) rather than at apply time, so a refused bundle leaves the config dir byte-identical instead of landing the sessions first — and `isPluginStateName`, not a raw `readdirSync().length`, decides what counts as content, because import plants `.sesh-mover-project.json` itself. And a declined carry is **not** saved anywhere, which is the deliberate divergence from `pull-apply-carry.ts`'s `saveOnly`: a pull has no second chance, while the bundle here is a file the user still has, and the payload runs at all four shared-layer sites so a re-run with the flag reaches it even when every session is a duplicate.
- `version-adapters.ts` — schema migrations between Claude Code JSONL versions; called during import when source/target Claude versions differ.
- `paths.ts` — every on-disk name the plugin owns, in one place: `PROJECT_DIR_NAME`/`USER_DIR_NAME` (`.sesh-mover`), the three committed root dotfiles (`.sesh-mover-include`, `.sesh-mover-ignore`, `.sesh-mover-project.json`), and `PLUGIN_STATE_NAMES`, which `payload/workspace.ts` turns into the `NEVER_INCLUDABLE` floor by adding `.git` — so a name added here is protected on the carry side and the apply side at once. **There is exactly one copy of that list**; a second, hand-written one is how a name ends up protected on the carry side and not on the apply side. Editing it in either direction is a security change, pinned by exact-contents assertions in `tests/paths.test.ts` and *two* sites in `tests/hub-workspace.test.ts` (they move together). The split is by **lifecycle**: `.sesh-mover/` holds generated exports (gitignored), the three dotfiles hold config/identity (committed); one directory holding both is what forced the old `.gitignore` negation. `userSeshMoverDir()` is a plain `join(homedir(), ".sesh-mover")` — 0.8.0 removed the 0.7.0 rename-on-first-run along with every other legacy path check, so nothing in this file probes the filesystem and nothing warns about an old name. A pre-0.8.0 directory or list file is inert clutter, never a fallback read.
- `config.ts` — two-tier config: user (`~/.sesh-mover/config.json`) merged with project (`<cwd>/.sesh-mover/config.json`); project overrides user. `computeEffectiveConfig` is the merge site (used by `cli.ts`'s `loadEffectiveConfig` and by `hub/status.ts`) — it layers each layer's *raw, non-backfilled* file contents onto the defaults, rather than merging two independently defaults-backfilled config objects. The latter (what an earlier `mergeConfigs(readConfig(user), readConfig(project))` call did) silently reset any user-scope-only setting back to its default whenever the project-scope file was simply absent, because `readConfig` always backfills defaults even for a missing file — fixed in 57cd7b7; affects `export`, `migrate`, and `configure --show` too.
- `summary.ts` — extracts a short session summary for export names/browse listings. `--no-summary` (or `export.noSummary` in config) is functional: it skips JSONL parsing for the summary entirely and sets the manifest `summary` to the session slug, so no conversation text is copied into the manifest.
- `memory-index.ts` — the `MEMORY.md` union (#49). A memory index is a list of markdown pointer lines, and it has a well-defined union: dedup by link target, keep every local line verbatim, append incoming pointers **after the last pointer line** rather than at EOF (otherwise they land under a file's trailing prose and read as commentary). It never reorders, rewrites or deletes a local line — including a pointer whose target is missing, because a dead link beats a live file nothing points at. Matching is a two-pointer scan, never a regex (same rule as `payload/workspace.ts`, for the same measured reason).
- `sidecar.ts` — `copyToNewFile`, the create-only primitive, and `copyToUniqueName`, the numeric-suffix loop over it that guarantees a parked copy never eats an earlier one. **Exactly one copy of each**, shared by `hub/merge.ts`'s `writeSidecar` (`<name>.theirs-<stamp>`) and `replaceFileAtomically`, and the importer's memory parking (`<stem>.incoming.md`) and its three shared-layer destinations; breaking the primitive fails tests in both suites, which is the check that they really share it rather than currently agreeing. **The platforms are not equivalent, and the doc must not pretend they are.** `copyToNewFile` carries three guards: an `lstat` refusal of a symlink at the name, an exclusive `wx` create, and a post-open re-check before any payload byte. On POSIX the exclusive create alone is sufficient and atomic — `open(O_CREAT|O_EXCL)` is specified not to follow symlinks. On Windows it is **not**: libuv maps `O_CREAT|O_EXCL` to `CREATE_NEW` without `FILE_FLAG_OPEN_REPARSE_POINT` and calls `CopyFile` with `bFailIfExists`, which Microsoft documents as failing "only if the target of the symbolic link exists" — so a *dangling* link is followed and the payload lands at the far end. This is exactly CVE-2025-0913, which Go fixed and Rust avoids; libuv never took the fix and Node exposes no way to pass the flag, so it is not fixable by spelling. The `lstat` is therefore the load-bearing guard on Windows, and what remains is a check-then-write with a residual race that guard 3 reduces from "payload escapes" to "empty file appears". **Linux cannot prove any of this** — measured: removing the `lstat` guard leaves all 97 importer+merge tests green, as does reverting the whole helper to `copyFileSync(..., COPYFILE_EXCL)`. Only the Windows CI job settles it. Note `tests/hub-merge.test.ts`'s symlink tests are `skipIf(isWindows)`, so merge has no Windows symlink coverage of its own.
- `sync-state.ts` — per-project peer sync bookkeeping (peers, lineage, imported registry), one file per project keyed by encoded project path. **Invariant on `recordSentToPeer`:** it credits a peer's "already has it" ledger, and its only caller is hub pull, where the content demonstrably just came from the hub — so any future transfer path that moves sessions between machines *without* going through the hub must not credit the hub ledger here, or the next push ships only a delta and leaves a continuation chain on the hub with no base bundle to anchor it. Schema `v2` (additive): a `hub` block (`hubId` + `threadByLocalSession`, written by `hub/push.ts`/`hub/pull.ts` via `setThreadId`, plus `workspaceGenerations`/`lastWorkspace` written by push/pull's workspace half, each carrying an optional `digest` since #110 — additive inside the already-v2 `hub` block, so no schema bump, and `parseSyncState` never shape-checks that block) is added lazily, only once a project first pushes/pulls through a hub — plain incremental-sync users never see `schemaVersion` leave `1`. A plugin version that predates the hub and encounters a `v2` file doesn't recognize it, treats it as corrupt, and renames it aside (fresh state) — that costs only peer/thread bookkeeping, never session data.
- `errors.ts` — `errorMessage`, the ONE way a thrown value becomes text (#102). It replaced the whole `(e as Error).message` class, several sites of which sat on contracts where a throw is not cosmetic — both hook endpoints (always exit 0) and `pull-fetch.ts`'s stage aborts — because `catch` binds `unknown` and a `null` rejection made the cast itself a TypeError inside the catch. It decides nothing: every caller keeps its own discrimination on the value's class or `code`, and matching on the string it returns is forbidden, as for every message in this codebase. Exactly one copy, for the usual reason: a second spelling is how a site ends up with the unguarded version again.
- `latched-write.ts` — `latchedWriteStream`, the write-side error latch every streaming writer sits on (#16): `rewriteJsonlStream`, `buildContinuationStream`, `copyFileWithHash`, `stripHeader`. A `Writable` fails asynchronously and at most once, and a bare `once(stream, "drain")` hangs forever on a stream that errored *before* the wait began; the latch races a stays-rejected promise at every await. Two of the four writers are module-private, so before it they could not be pinned at all — `tests/latched-write.test.ts` pins the protocol once. It is a latch, not a supervisor: first error only, it bounds nothing (the bound is `hub/io-timeout.ts`'s, on the syscall), and `destroy()` in the caller's `catch` is an obligation for failures the stream did not raise.

### Payload module responsibilities (`src/payload/`)

The FILE payload — the project's own files, travelling beside the sessions. It is **transport-neutral by construction, and the dependency runs one way**: `payload/` imports `../config.js`, `../paths.js`, `../types.js` and `../manifest.js` — that last one deliberately, so the carry's `patchDigest` is computed by the module that owns every hash a bundle carries rather than by a private sha256 (`manifest.ts` imports only a type back, so the cycle is type-only) — and nothing from `src/hub/`, while `src/hub/` is a *consumer* of it alongside `exporter.ts` and `importer.ts`. That direction is what the module move was for (#47) — these files never imported anything hub-specific, they just lived in that directory, and leaving them there meant a second copy of the decision below whenever a non-hub transport wanted one. Keep it one-way.

- `git-scan.ts` — `scanGitRemotes` / `GitRemoteScan` / `normalizeGitRemote` / `localGitRemotes`, moved out of `hub/identity.ts` because the answer decides which payload a project may send and both transports need it. **The three-way answer is a security boundary, not a diagnostic nicety**: `remotes` takes the carry, `none` takes the workspace snapshot, and `unknown` — a `.git` exists and git could not be asked — takes **NEITHER**, because an unfiltered whole-tree copy is only safe for a project that genuinely has no remote. The kind comes from `git remote` (bare names), never from `git remote -v`: a remote configured with only a `pushurl` prints no `(fetch)` line, and counting those read a real git project as remote-less and shipped its `.gitignore`d secrets — measured. The repository-marker walk (`findGitRepoMarker`, private here; it was `hasGitRepoMarker` before the move) is what feeds the `unknown` arm and is deliberately a *filesystem* fact, since it is the one thing still knowable when `git` cannot run — `existsSync` is not the test (#50: an empty stray `.git` satisfies it and git would not recognize it). `localGitRemotes` still collapses all three into `[]` and is for hub-project *identity matching only*.
- `workspace.ts` — git-less project snapshot/unpack, the `.sesh-mover-ignore`/`.sesh-mover-include` rules, and the `NEVER_INCLUDABLE` floor.
- `carry.ts` — the git-diff carry: `captureCarry` and `applyCarry`.
- `capture.ts` — `capturePayload`, the ONE shared decision-and-disclosure block `hub/push.ts` and `src/exporter.ts` both call, plus `listTopLevelIgnored` (moved out of `push.ts`). It owns five things together, and together is the point: one git-remote scan per operation; the `unknown` arm building neither payload and saying why; the snapshot only on `none`; the carry only on `remotes`, *contained* so no git failure can cost the sessions that are the point of the operation; and `reIncluded`/`trackedIgnored`/`inProgress`/a non-capture turned into prose a user can act on, with the export wording louder than the push wording and a `measureOnly` tense that does not claim a past write. It deliberately does **not** own `workspace.basedOn` (a hub generation id, so `hub/push.ts` stamps it and an export mints none), where the fields land in the manifest, or the git scan itself — that arrives as a value, so this module has no opinion about caching it and the dependency stays one-way.

Two invariants live here rather than under "Slice-2 invariants", because they are properties of the **payload** and not of the transport — they held for `push`/`pull` before #47 and hold unchanged for `export`/`import` now:

- **`.sesh-mover-ignore` vs `.sesh-mover-include` (`workspace.ts`).** They deliberately disagree on a trailing slash: `.sesh-mover-ignore` matches per path *segment* (so `dir/` is decoration — it excludes `dir` at any depth), `.sesh-mover-include` matches whole *relative paths* (so any `/` in a pattern, trailing included, roots it at the project). Don't harmonize them. Glob matching is a two-pointer matcher, never a regex (the regex it replaced was a measured ReDoS). `.git` plus `PLUGIN_STATE_NAMES` (`.sesh-mover`, `.sesh-mover-include`, `.sesh-mover-ignore`, `.sesh-mover-project.json`) are the `NEVER_INCLUDABLE` floor and can't be re-included by any pattern or spelling — the load-bearing check is the per-segment **path**-side one, not the pattern-side guard. Two things about that list are permanent rather than incidental to whichever rename happened last: there is exactly ONE copy of it, so the workspace walk, the merge, the unpack, the `git` pathspecs and the patch byte scan cannot disagree; and the root dotfiles need it *more* than the directory does, since there is no directory segment between a payload and a file it can name directly. 0.8.0 removed three retired spellings from it — safe only because that release reads none of them, so a payload writing one plants inert clutter rather than a file some reader consults. Any name this plugin *does* read must be on the list. `.claude` is deliberately not on the floor: the dividing line is what a name can *do* (redirect the hub, rewrite what the next push ships, overwrite a VCS store), not what it contains. Apply side, and **the three apply paths do NOT agree — this sentence used to claim they did**: only `hub/merge.ts`'s `mergeWorkspaceTrees` filters by the floor plus the *target's* own `.sesh-mover-ignore` (minus its `.sesh-mover-include`), and for it the rule holds as stated — re-applying the built-in convenience excludes there silently discarded files the sender had deliberately listed. `unpackWorkspace` takes `{force}` and **never reads the target's ignore file at all**; `applyCarry` reads neither carry rule and is filtered by git's own parse instead (#38). `readIgnorePatterns` has exactly two call sites — `snapshotWorkspace` (capture) and `mergeWorkspaceTrees` — which is the cheapest way to check this claim has not drifted again. The floor is the only filter common to all three, which is precisely why it is the floor and why the "exactly ONE copy" rule above is load-bearing rather than tidy. A consequence #47 makes visible: **the two rule files cannot travel in a payload**, so after an `export`→`import` bootstrap the destination project has neither, and a later push or export from there carries a different set than the source did. Disclosed in `commands/import.md` rather than fixed by weakening the floor — a payload that could write `.sesh-mover-include` into an empty directory is the same exfiltration primitive one push later.
- **Carry (`carry.ts`).** `captureCarry` is the git-project counterpart of `snapshotWorkspace`: `git diff HEAD --binary --relative` plus untracked files, written to `carry/` in the bundle. The two are mutually exclusive by construction, on the three-way `GitRemoteScan` above — it is *not* a `localGitRemotes().length` check; an earlier version of this file said it was. `.sesh-mover-include` is the one rule the two builders share — every path either builder admits goes through `workspace.ts`'s `isCarriedPath`/`isReIncluded`, never a second copy of the rule. The patch is handled as BYTES end to end: a `git diff` of a text file that is not valid UTF-8 does not survive a string round trip, and git then refuses the patch. `git diff` is porcelain: the shipped invocation (`--no-ext-diff --no-textconv --no-color --src-prefix=a/ --dst-prefix=b/ -U3 --submodule=short --ignore-submodules=none --relative`) and `gitChildEnv()`'s environment scrub are each individually load-bearing against ordinary user config, including for a *security* property (`GIT_LITERAL_PATHSPECS=1` silently disables the floor's `:(exclude,…)` pathspecs). Audit any future porcelain git call on user data the same way. The safety guarantee has **two halves that differ** — every filter applies to the untracked enumeration; none of them filter the patch, so a gitignored-but-tracked file's changes travel (disclosed in the sibling field `trackedIgnored`, never folded into `reIncluded`, whose remedy would be wrong for it). On the apply side the floor is enforced from **git's own parse, and only git's** (#38): `git apply --numstat -z --summary`, read once, because git parses a patch into one entry list and then walks *that same list* to print `--numstat`, to print `--summary`, and to write the files — two invocations differing only in mode cannot disagree. `--numstat` gives every destination; `--summary` gives the rename and copy SOURCES it never prints, and is read against a **closed grammar** of git's summary shapes, so an unaccounted line refuses the whole payload rather than being skipped. That closed grammar is not fastidiousness: a destination is attacker-controlled and `--summary` interpolates it raw, so a destination containing a newline splits the only line carrying the source — measured, and it applied, deleting a floor-protected file. The older design read the patch bytes as a *second* floor source; that is gone, because it had holes git does not (it read `rename from` but never `copy from`, and a copy-out of a plugin internal applied and was then re-uploaded by the next push — also measured). The byte scan survives for exactly two jobs: **symlinks**, which stay enforcement because `--summary` prints nothing at all for a re-pointed one, and advisory README wording on a receiver with no runnable git. The write path is gated on git having answered *about the patch*, not merely about the directory — the directory probe succeeding does not mean the floor call did. A refusal is whole-payload, never partial. That the destinations are knowable only from git's parse is also why `WriteSetRoot.enumerated` is `false` for `carry` alone: an import's consent gate cannot list them, and says so rather than rounding it off.

- `crypto/` — the primitives, deliberately kept out of `hub/`. `age.ts` is a from-scratch **age v1** implementation over `node:crypto` (X25519 recipient stanzas, ChaCha20-Poly1305 STREAM payload) exposed as `AgeEncryptStream`/`AgeDecryptStream`. Three things about it are permanent rather than incidental. **(1) They are `Transform`s and there is no whole-buffer helper**, because a whole-buffer helper is how the streaming constraint gets undone — the bundle path is a pipeline at both ends and the largest writer in this codebase is the unattended session-end auto-push. **(2) A self-round-trip test is worthless here.** Measured: a frozen STREAM chunk counter encrypts *and* decrypts back to the plaintext byte for byte while every chunk reuses one nonce — four such defects round-trip perfectly through our own code. The differential test against the real `age`/`rage` binaries (`tests/crypto-age.test.ts`, `tests/crypto-age-mutations.test.ts`) is the gate, its absence is announced through `process.stderr.write` because vitest swallows `console.error` from a passing file, and `SESH_MOVER_REQUIRE_AGE=1` makes absence a failure. Nonce reuse is only observable at **≥2 chunks**, and the `>` vs `>=` hold-back only at an **exact multiple of 64 KiB**, so the 65536/131072 cases are load-bearing and no randomly-sized payload replaces them. **(3) The format is age's for one reason:** `age -d -i ~/.sesh-mover/identity.age <bundle>.tar.gz.age` recovers a bundle with this plugin uninstalled, so losing the plugin and losing the sessions are not the same event. `identity-file.ts` owns `~/.sesh-mover/identity.age` (0600) with a three-valued read — `absent` / `unreadable` (`io` vs `malformed`, different remedies) / `present` — and never overwrites a present-but-unreadable file, because minting a new identity is a decision with consequences the user has to make. It re-derives the recipient from the secret rather than trusting the file's `# public key:` comment. `signing-key.ts` is the SECOND keypair — Ed25519, for the statement `hub push` signs — and why it is a second one rather than the X25519 identity reused, and why it alone of the two is never escrowed, is under "Signing invariants (#86)".

### Hub module responsibilities (`src/hub/`)

The hub is a shared directory (filesystem backend only, in Slice 1 — any path that behaves like a shared filesystem: network share or synced folder) that every participating machine points at via `hub.path` in config, holding per-project bundles, per-project **workspace artifacts**, plus **one index file per machine**. Two invariants hold the whole design together:

- **Per-machine ownership** — a machine only ever writes its own index file (`index/<machineId>.json`, see `layout.ts`'s `indexPath`) and its own bundles; it never touches another machine's files. This is what makes concurrent push/pull from *different* machines safe without a distributed lock — the same-machine advisory lock (`lock.ts`) only ever has to guard one machine's own writes against itself, not against other machines.
- **Derivable indexes** — everything an index file records (thread → bundle history) is reconstructible from the bundles on the hub plus this machine's local sync-state (which thread each local session belongs to). `hub reindex` (`reindex.ts`) is this invariant made executable: a repair tool for a lost/corrupt index, not a sync primitive.

`src/hub/` is a **consumer of `src/payload/`**, not its owner: the two payload builders (`workspace.ts`, `carry.ts`), the git-remote scan (`git-scan.ts`) and the shared capture block (`capture.ts`) are not hub modules and are documented in the section above. Nothing below may be imported from there.

### Slice-2 invariants (append, merge)

Both are hub-only: they are about reconciling two machines that have drifted, which no other transport does. The carry and the two rule files were listed here until #47 moved them to "Payload module responsibilities" above — they were never hub-specific, and an `export`/`import` round trip exercises them with no hub involved.

- **Append guards (`append.ts`).** A pulled continuation is spliced onto an existing local transcript only when all of them pass: the delta's anchor equals the base's head (chain guard — never skipped, not even by `--force-append`), the base was not modified in the last 5 minutes (liveness — this is the one `--force-append` overrides), and the bundle's content matches its manifest hash. The delta must be path-rewritten and version-adapted **before** it reaches `tryAppendContinuation` — the module does neither, so `pull.ts` builds the real source→target `RewriteContext` first. Rollback rule, and it applies to `adoptHubBranch` too: a truncate or whole-file restore is only ours to perform if the file's size is exactly what our own mutation accounts for (bytes-before + `WriteStream.bytesWritten`); otherwise **refuse and throw** rather than report a clean restore over another writer's bytes. The liveness check's self-write exemption is a heuristic (`opNowMs` is truncated to a whole ms and captured once for the whole pull), documented at the comparison site — making it exact needs a recorded write-time, not a finer clock.
- **Merge ancestor (`merge.ts` + `chooseMergeAncestor` in `pull-apply-workspace.ts`).** A 3-way workspace merge may only use a generation **common to both trees**, decided by set membership and never by a clock: ours is `SyncState.hub.workspaceGenerations` (bounded 50), theirs is `manifest.workspace.basedOn.bundleId` collected across the pull's bundle chain **and filtered to the machine whose payload is being applied**, and the newest member of the intersection wins. That filter is the whole of the `ChainWorkspaceBase` machine stamp, and it is load-bearing rather than tidy: `basedOn` is a self-report about ONE machine's own generation history, so walking back over several bases is only sound while they are linear. That held for free until #35, when `planThreadPull`/`assembleChain` began ordering `needed` by session-continuation links **across machines** — links say nothing about workspace generations, so an *earlier* bundle in the assembled order can declare a base newer in our list than the one the applied payload declares, and taking the chain-wide minimum then merges one machine's tree against another machine's generation. Measured: our tree reads as unchanged against it, every file the peer differs on is scored `taken`, and the local copy is atomically overwritten with no sidecar and no backup, reported as a clean merge (`tests/hub-pull-cross-machine-workspace.test.ts`). Reading another machine's bases off the assembled chain is not a fix for the three-machine skip either — it trades a loud skip for that silent overwrite. An empty intersection means *no ancestor* (skip), not a guess; fallback goes strictly older, because an older base fails toward "keep local + visible conflicts" while a newer one fails toward silently overwriting work. `pushedAt` is a diagnostic only — the hub stamps nothing, so it is the pushing machine's wall clock, and ordering by it reinstates a measured silent-revert bug under clock skew. Since #110 a generation also records `WorkspaceGenerationRef.digest`, the sha256 of the plaintext archive the tree came out of, as THIS machine computed it when it pushed or applied the generation — a self-attestation that needs no peer to sign anything, checked before the ancestor archive is unpacked. A mismatch means the ancestor is NOT used and the merge degrades to no-ancestor, which is the existing safe direction; it is never an abort, and the message names damage beside substitution because a hub is often a synced folder and a half-written archive lands on that branch as an ordinary state. Absent means no check, permanently: every ref written before #110 has none, `MAX_WORKSPACE_GENERATIONS` is 50, and an inline (pre-#91) generation's `file` is a bundle no pull ever hashed. Never backfill it from what the hub currently holds — that pins an attacker-supplied value as the trusted one. Never merge into an empty/metadata-only tree (`pull-apply-workspace.ts` gates on `hasRealContent`), and never record a generation for a payload that was not applied.
- **The workspace payload is its own hub file (#91), and that changed the generation's LOCATION, not its IDENTITY.** A generation is still `bundleId` on both sides of the intersection — `manifest.workspace.basedOn.bundleId` and `SyncState.hub.workspaceGenerations[].bundleId` — because one push mints one bundle id and writes at most one snapshot under it, so the set membership test is untouched and the silent-revert class is not reopened. What did change is `WorkspaceGenerationRef.file`, which now names the ARTIFACT rather than the bundle: `fetchAncestorWorkspace` opens exactly that file, and a bundle no longer holds a tree for it to find, so recording the bundle path degrades every future merge to no-ancestor — safe, silent and permanently wrong. Both writers of that field (push after upload, pull after apply) must name the file the tree actually came from, and the pull's is the one to watch, since the incoming payload may have arrived in EITHER shape. `basedOn.file` stays diagnostic-only and must never become a path, for the reason it always was: a generation's identity must not be steerable by a self-report. The split's own pointer, `manifest.workspace.file`, is the ONE workspace field that does become a path, and it is contained to `workspaceDir(projectId, machineId)` for the machine whose index listed the bundle.
- **The split is a permanent TWO-SHAPE read, decided from the artifact.** `manifest.workspace.file` present means a separate hub file; absent means the tree is inside the bundle at `workspace/`, which is what every pre-#91 bundle says and will go on saying. Never decide it from local config, from `hub.json`, or from a version — same rule and same reason as the `.age` suffix. An artifact that cannot be retrieved is a SKIP with `workspaceDeclaredMissing`, never an abort: the transcripts are the point of a pull and the tree is the optional half. Conversely an older plugin meeting a split bundle finds no `workspace/`, takes the already-shipped "declares a payload the bundle does not contain" branch, and imports the sessions normally — that graceful degradation is why the pointer was added to the existing `workspace` block instead of replacing it with a new key.

### Encryption-at-rest invariants (#91)

Four rules, and every one of them is a place this has already been got wrong in design review.

- **All three manifest hash layers stay exactly where they are, over PLAINTEXT.** `integrityHash`, `layerDigests` and `sessionsDigest` are computed by the exporter inside the staging directory, long before `createArchive` and therefore long before any encryption. Their question is "is this the file the exporter wrote"; a ciphertext hash answers "is this the ciphertext the pusher uploaded", which the AEAD tag already answers per chunk and better — and it would have nowhere to live, since `manifest.json` is inside the archive and so inside the ciphertext. Do not move them and do not add a fourth. The #86 signature's `bundleDigest` is not that fourth: it is over the whole plaintext archive, so it cannot live inside it, and it sits on the signer's own index record — a different question (*who wrote this*) answered outside the archive. Nothing in `signature.ts` reads the three layers.
- **New bundles only; never rewrite an existing bundle in place — except your OWN, and only the header.** In-place re-encryption would be one machine rewriting *other machines'* files, which per-machine ownership forbids outright — and that invariant is what makes concurrent push/pull safe with no distributed lock. So the hub is **permanently mixed**, plaintext and ciphertext side by side, and that is the design rather than a transitional state. `hub rekey` (`rekey.ts`) is the one rewrite there is, and it composes with the rule rather than bending it: a machine re-addresses its own bundles and nobody else's, keeps the file NAME (so no index anywhere learns that it ran), and never touches the payload. Its two residuals are structural and get named rather than worked around — **a decommissioned machine can never re-wrap its bundles**, and a machine that lost or replaced its key cannot re-wrap its own either, because a re-wrap has to unwrap the file key first. A re-wrap therefore GRANTS access and can never revoke it: the file key does not change.
- **The reader branches on the FILE SUFFIX, never on local config or on `hub.json`.** `.tar.gz` vs `.tar.gz.age`. This is the rule that keeps flipping the switch from stranding your own history, and it is easy to undo by reaching for `resolveHubEncryption` in a read path — which fails in BOTH directions: on a freshly sealed hub it strands every earlier bundle, and on a machine that has not noticed the flip it tries to gunzip ciphertext. Neither shows up on the machine that made the change. THREE readers must obey it — `pull-fetch.ts`, `pull-apply-workspace.ts` (both its merge-ancestor fetch and, since #91, its incoming-payload fetch, which share one retriever), and `reindex.ts` — which is exactly why they share `bundle-io.ts` rather than each carrying the branch. **No `backend.readStream` outside `bundle-io.ts`** — that is the enforceable rule, and it is the correct spelling of a claim this file made wrongly for two releases ("`fetchBundleArchive` is the ONLY appearance"): there are two, `fetchBundleArchive` and `rewrapBundleFile`, both in that module. A new artifact class that needs bytes off the hub takes that seam or it is a plaintext hole in a hub the user believes is sealed. The workspace split is the worked example — it added a second hub artifact and no second reader, by giving it `bundleFileName`'s naming and wrapping its tree at `workspace/` so one extractor serves both shapes.
- **`hub.encrypt` is authoritative in `hub.json`; the config key is a local preference.** A local-only flag has a silent failure: one machine that never set it keeps pushing plaintext into a hub the user believes is sealed. A malformed value in `hub.json` resolves toward `required: true`, because a hand-edited `"true"` read as `false` is exactly the loss the field exists to prevent while the other direction is a surprise on bundles you hold the keys to. Absent stays `false` — that is every hub in existence and must not become encrypted by inference.

**No plaintext fallback, ever.** The `zstd`→gzip and `git merge-file`→no-ancestor degradations work because the weaker mode satisfies the *same* property; the only thing a failed encryptor could fall back to is plaintext, which is not a lesser confidentiality but its absence, and invisible to everyone except the machine that pushed. So push fails, and on the read side an undecryptable bundle aborts that bundle and therefore the chain.

**The un-keyed decision, and why it is a refusal with a flag override ON PUSH ONLY.** A machine dropped from a push's recipient list cannot read that bundle — not after it upgrades, not after it publishes a key — until the machine that WROTE it runs `hub rekey`, and never at all if that machine is gone; the loss surfaces on the *other* machine much later as what looks like corruption. So push refuses by default. **`hub rekey` decides the same census differently, deliberately**: it discloses an un-keyed machine and continues, with no flag at all, because a re-wrap is idempotent and re-runnable — the machine left out of this one is picked up by the next, so refusing would block a strictly widening operation to prevent a loss that does not occur. The two callers share `checkSelfIsRecipient` (the self/empty-set half, where they cannot disagree) and stop there; that split is the whole reason the half was extracted. `--force-unkeyed` exists because nothing in this codebase ever deletes a `machines/<id>.json` (`hub retire` deletes a project's files, never a machine record), so one decommissioned machine would otherwise block every encrypted push forever. It is a FLAG and never a config key — same rule as `push --full` — so the unattended SessionEnd auto-push can never make that choice; the cost, stated rather than discovered, is that a sealed hub with one un-keyed machine makes the auto-push refuse at every session end, visible only in `hub status`'s `lastAutoPush`. The **self** case is not overridable: "I know those machines do not need this" is definitionally false about the machine writing the file.

**The claim not to overstate, in code and in docs.** An AEAD tag proves the ciphertext was produced by someone holding the file key — which, under a shared-recipient design, is **every participating machine**. It authenticates the **group, not the sender**. Gained, and real: a hub operator who is not a recipient can no longer author a payload at all, which partially discharges #36 for the host-and-transport threat. Not gained by encryption: #37 in any form, and #36 with respect to a *peer*, because a peer is a recipient. Per-machine signing (#86) shipped in 0.11.0 and moved both by a bounded amount — it authenticates the SENDER, which is the one thing the tag cannot — and its limits are set out under "Signing invariants (#86)" below rather than restated here. And the statement that must reach the user: **enabling encryption does not make an existing hub private; it makes it private going forward** — everything already there stays readable by anyone with read access, forever.

**`MIN_ENCRYPTION_PLUGIN_VERSION` is a fact about the FEATURE, not about the release.** `hub encrypt --enable` refuses while a registered machine's `pluginVersion` predates it, naming the machine — because that machine does not read `hub.json.encrypt` at all, so sealing the hub would not stop it uploading in the clear, only stop you noticing. Compare against this constant and never against `PLUGIN_VERSION`, which would make every release declare every not-yet-upgraded machine "too old for encryption". The machine running the gate is exempt tautologically: it is the build that implements the feature.

**`hub escrow` escrows the IDENTITY, because the design the spec asked for cannot be built.** §2.3/§6 Q2's "an scrypt stanza alongside the X25519 ones" on every bundle is forbidden by the age spec with a MUST, and the failure mode is the reason it must never be re-attempted: measured against age 1.2.1 with a hand-built header the CLI cannot produce, a mixed file reads fine with `-i` and is REJECTED with a passphrase — so it would read correctly on every ordinary pull, on every machine, forever, and fail at exactly one moment, the recovery that by definition happens after the key is already lost. Block #4 in `crypto/age.ts` therefore enforces "exactly one stanza" on the **read** side as well as the write side, which is what makes a passphrase-addressed bundle unproducible *and* unopenable here rather than merely un-written — age gives the reason itself: a mixed file lets a key holder author a payload the passphrase holder decrypts believing their passphrase authenticated it. What ships instead is a passphrase-wrapped copy of this machine's own `~/.sesh-mover/identity.age` at a path the user names, default off, written 0600 with `wx` and then read back through the real reader and compared (a check that cannot catch a defect symmetric in our own code — that is what the differential test against the real `age` binary is for) and deleted if it does not match. It changes **nothing** on the bundle path: `push`, `pull`, `rekey`, `retire` and `reindex` do not know the file exists, and it takes no project lock and needs no configured hub. It is **RECOVERY ONLY and is not a backfill mechanism** — restoring it on a rebuilt machine restores THAT machine's own identity and moves no key, while handing it to a *different* machine collapses two machines into one identity and destroys the per-machine revocation the identities are per-machine for; `hub rekey` is the tool for that job, and every doc points at it by name. The work factor is age 1.2.1's own logN 18 and is deliberately not an option, because there is no MINIMUM work factor (logN 1 decrypts cleanly under age, measured), so a silently weak escrow is accepted by every tool and the writer's choice is the only protection there is; the read side caps at 22, matching age, since a file claiming logN 30 is a 1 TiB allocation request. The passphrase is **stdin-only** — a flag lands in shell history, a config key sits in plaintext beside what it protects, and an environment variable leaks through `/proc/<pid>/environ` *and* is inherited by every subprocess, including the `git` this repo runs on user data, since `gitChildEnv()` scrubs `GIT_*` and would pass anything else straight through to git, its credential helper and its hooks — and specifically **not collected in-chat**, because a passphrase typed into a Claude Code session is written into the JSONL that the default-on SessionEnd auto-push then uploads, encrypted to a key that very passphrase unwraps; `commands/hub-escrow.md` prints a `read -rs … | sesh-mover hub escrow --enable --passphrase-stdin` line for the user's own shell instead, and `browse --prune` delegating its prompt to the skill layer is not a precedent, because nothing it collects is a secret. The `--out` refusal (inside the hub, inside a sesh-mover project, inside a git work tree, under a sync-client directory name or marker, no parent directory, a file already there; the parent is realpath'd first and there is no override flag) is a guard against the **obvious mistake** and nothing more: it cannot see that a home directory — or any parent of it — is itself a synced folder, a network mount, a backup target or a shared volume. That is why `ESCROW_DESTINATION_LIMITS` is returned on every result including successes: a refusal that fires makes the check look more capable than it is, and that is exactly the moment a user concludes the destination they pick next must be safe.

### Signing invariants (#86)

Every push signs ONE statement and stamps it on every index record it mints; a pull verifies it between retrieval and unpack; the first key seen for a machine is pinned locally and a change refuses the pull; `hub trust` turns a hub-supplied key into a human-confirmed one. Four modules, in order of importance — which is the reverse of how a design review reads them: the pin store is the feature, and the signature is what it gives the pin to check.

- **`crypto/signing-key.ts` — a SECOND keypair, and reusing the X25519 identity is not possible, not merely unwise.** `node:crypto` accepts the X25519 secret's 32 bytes as an Ed25519 JWK `d`, which looks exactly like reuse working. It is not: Ed25519's `d` is a SEED, expanded through SHA-512 into the scalar, where X25519's is the scalar itself, so the same 32 bytes yield two unrelated keypairs — measured on Node 22.23.1 by deriving both public halves. An XEdDSA-style conversion needs the Edwards-curve arithmetic `age.ts` was written to avoid, and unlike `age.ts` there is no reference binary to check it against. It would be wrong even if it worked: one scalar in two protocols is cross-protocol key reuse with no composed security argument, and it welds the two keys' lifecycles — the age identity is escrowable, so an escrow passphrase would become a signature-forgery capability. That is why the signing key is **not escrowed** (owner ruling), and the asymmetry is the design: losing `identity.age` is permanent, losing `signing.key` costs a new keypair and one re-pin round with peers (old bundles stay verifiable against the old key wherever it is pinned), so escrowing it would widen `hub escrow`'s blast radius from "can read this machine's bundles" to "can also forge its signatures" to buy back a loss that costs a re-pin. `~/.sesh-mover/signing.key`, PKCS#8 PEM — what `node:crypto` exports natively, so nothing is hand-built — beside `identity.age` and never inside it (that file must stay a valid age identity so `age -d -i` keeps working with the plugin uninstalled), and never in `machine-id.json` (published verbatim). It gets `identity-file.ts`'s file discipline in full — 0600, `wx`, a three-valued `absent`/`unreadable` (`io` | `malformed`)/`present` read, never overwrite a present-but-unreadable file — even though re-minting is survivable, because a key silently replaced during a transient read failure invalidates nothing but fires every peer's pin alarm for no reason, which trains users to click through the one alarm that matters. `loadOrCreateSigningKey` returns a result and never throws, because `registerMachine` calls it on every push and pull including the detached SessionEnd auto-push, and **an unreadable key WARNS AND PUSHES UNSIGNED** — owner ruling; no flag and no config key reopens it, so the warning names the file and nothing to pass. `keyFingerprint` (first 10 bytes, hex, grouped in fours) exists for a person comparing two screens and is never what verification compares: that uses the full key, because a truncated fingerprint is a smaller search space and no automated check may settle for one.
- **`hub/signature.ts` — the statement signs a digest of the PLAINTEXT archive, and it is bound to where the bundle lives.** Plaintext rather than the uploaded bytes because `hub rekey` replaces a bundle's age header in place under the same name: a ciphertext signature would die at every rekey, and re-signing after one would make validity depend on an operation whose entire point is that no index learns it ran. Not over any of the three manifest layers either: `sessionsDigest` deliberately excludes `workspace`/`carry`/`projectId` (push patches those in afterwards), so a signature over it would attest the transcripts and say nothing about the file payload — the surface #86 exists for. And because #91 moved the workspace tree into a hub file no existing digest reached, the statement carries a second digest, `workspaceDigest`, absent together with `workspaceFile` when no artifact went up — absent, not empty: `canonicalize` drops `undefined`, so the two shapes sign differently and a verifier cannot be talked into reading a missing artifact as a matching one. The context binding (`domain`, `hubId`, `projectId`, `machineId`, `bundleId`, `pushedAt`, `bundleFile`) is there because a bare `{digest, signature}` pair is forgeable by MOVING it: whoever can write the hub re-files a validly signed bundle under another project, another thread's chain slot or another name, and every byte still verifies. `verifyStatement` checks cryptographic validity first, then each context field against the record the pull actually resolved (never anything echoed from the statement), then the pin — and `context-mismatch` is the loudest arm, because everything cryptographic about it checks out, which damage cannot produce. `statementBytes` is ONE function used by both sides, since a signer and a verifier that serialize differently produce a mismatch that reads as tampering. One statement per push, not per record: every record of one push shares the whole context, and `bundleFile` is the exact `hubFile` string each record's `file` gets, so a mismatch there is self-inflicted and indistinguishable from an attacker's. `bundleDigest` is computed in push's `uploadArchive` after `createArchive` and before the stream that may encrypt — the one moment the plaintext bytes are provably in hand. The statement lives on `HubBundleRecord.signature`, in the signer's own index file (per-machine ownership holds trivially; zero extra hub reads at the verification point), which puts an assertion into a file the "derivable indexes" invariant calls a projection — the reconciliation is WHO: the one machine allowed to write that index holds the key, so `hub reindex` re-signs what it rebuilds from the plaintext archive `fetchBundleArchive` just produced, and it must, because rebuilt-unsigned records would read on every peer as a DOWNGRADE, making a repair look exactly like the tamper the feature detects. It returns unsigned rather than sign a statement it cannot make true: no key, or a declared workspace artifact that is not on the hub (indistinguishable there from a pre-#91 in-bundle tree, and the same answer serves both). **That re-sign path has no test** — `tests/hub-reindex.test.ts` never mentions a signature and neither signing suite calls `hubReindex` — so it is currently a characterization of the code, not a guard.
- **`hub/pins.ts` — the pin carries the security property; the signature does not.** Read this before deciding the pin store is an optimization. Verification against a hub-published key (`HubMachineJson.signingPublicKey`, written by `registerMachine` on every push and pull, carried forward rather than retracted when the file is unreadable) detects exactly one adversary: a tamperer who edits a bundle and then declines to re-sign it. Anyone else who can write the hub rewrites the victim's `machines/<id>.json`, substitutes a key, and signs whatever they like — the codebase already says this about the recipient list, and on the filesystem backend "peer" and "hub operator" are not distinct adversaries, since per-machine ownership is a convention and not an enforcement. So the first key seen for a machine is pinned in `~/.sesh-mover/key-pins.json`, keyed by `(hubId, machineId)` because the same machine id on two hubs is two trust decisions, and never ON the hub, which would be circular. After that a change is loud: `recordPin` with a `tofu` origin against a different key returns `conflict` and writes NOTHING — the load-bearing refusal, because nothing local can tell a machine that re-minted from an attacker, and a silent re-pin would make the whole mechanism decorative. A TOFU pin is written only AFTER the digest matched, so a bundle that fails its own statement can never be the thing that installs a pin; and it is only ever written after a signed bundle verified, so its existence IS the "this machine has signed before" fact. What TOFU covers is the realistic timeline — hub honest when the fleet was set up, compromised or migrated later — and what it does not cover is an attacker already there before this machine ever pulled; that residue is `hub trust`'s. An unreadable pin store reads as EMPTY, a deliberate weakening with a stated reason: refusing every pull over a local file turns a file problem into total loss of function, and the attacker it would protect against (delete the pin file to force re-TOFU) already has local write access and can edit the pins instead; write-then-rename, because a torn file would silently re-TOFU every machine. **An absent signature applies exactly as before #86, permanently** — that is every bundle on every hub — and the branch is the absent field on the record, never local config, `hub.json` or a version, for the suffix rule's reason: a policy bit fails in both directions, invisibly to the machine that flipped it. What keeps "absent" from being a tamperer's free pass is the **downgrade ratchet**: once this machine holds a pin for a signer, an unsigned bundle from it is worth a sentence — a warning, not a refusal, because push legitimately falls back to unsigned when its key is unreadable and a refusal would strand every machine that does.
- **`hub/trust.ts` — the out-of-band fingerprint ceremony, the ONLY step in signing that does not depend on trusting the hub.** It lists every machine's fingerprint and pin state — `tofu`, `confirmed` or `null`, three different facts and not a boolean, since only the first is independent of the hub — and `--machine <id> --fingerprint <fp>` records `confirmed`, which a TOFU write never overwrites and which may replace a conflicting pin (that is what it is for after a legitimate re-mint; the old key stays in `previousKey`). It **refuses a missing or mismatched fingerprint**, and that refusal is what makes the ceremony real: confirming without checking would be the user typing yes to whatever the hub published — TOFU with extra steps and a false sense of having verified — which is why `commands/hub-trust.md` must never read a fingerprint off the hub to feed back in. It takes no project lock and writes nothing on the hub (only this machine's pin file), but unlike `hub escrow` it needs a configured, reachable hub, since the roster is what it fingerprints. It never asks a machine to trust itself. Optional by owner ruling — a single-owner fleet may decline, and the report counts the unconfirmed without nagging — but without the option #86's "does not depend on trusting the hub" would simply be false rather than satisfied-after-first-contact.

**What it buys, and the claims not to overstate.** A verified signature proves the bundle was written by a holder of the key pinned for that machine, for this exact hub slot — the SENDER, which is the one thing the AEAD tag cannot say. That moves #36 and #37 by a bounded amount, and #37's amendment records exactly how far: a signed bundle's `basedOn` can no longer be edited on the hub or re-filed under another machine, and a false one is attributable to a specific key; what is not gained is TRUTH — a compromised or buggy peer signs a false claim perfectly, holds a key, and after one pull holds a pin, so against a hostile peer signing raises the cost of forging from *editing a file* to *using your own key* and no further. Four limits that must reach the user rather than be discovered: **(1)** an unsigned bundle still applies, permanently, with a warning once a pin exists and never a refusal — there is no strict require-signed mode. That is #107, deferred, and when it is built it must be a LOCAL receiver policy and never a `hub.json` field, for the suffix rule's reason. **(2)** The statement's `workspaceDigest` **is** verified on pull as of #110, and what remains uncovered is worth stating precisely. `pull-fetch.ts`'s signature gate mints a `WorkspaceAttestation` — `unsigned` / `signed-no-artifact` / `attested` — only after the statement verified, its context matched and the archive's own digest matched, and forwards it on `FetchStageResult`; `pull-apply-workspace.ts` compares it against the artifact it downloads, BEFORE the unpack, so on an attested artifact node-tar never parses a byte that failed attribution. A mismatch is a **skip** with `workspaceUnverified`, never an abort: `pull.ts` returns a workspace abort terminally while earlier bundles are already applied and credited, which `pull-record.ts` names as one of three hard returns that strand a chain — so an abort would add a route into a documented hazard on an input an attacker chooses, and would hand a hub-writing attacker a transcript denial of service. The merge ANCESTOR is covered separately and needs no signature at all: `WorkspaceGenerationRef.digest` is this machine's own note about a tree it applied, so the check holds on a fleet that has never signed a bundle. Four residues, all deliberate: **stripping** a signature still works (an index file carries no integrity of its own, and on the filesystem backend writing the artifact and writing the record are one capability) — that is #107's; **`hub reindex` launders a substitution**, because `rebuildSignature` signs whatever is at the derived artifact path, which is why no message ever offers a reindex as the remedy; a key holder signs anything (limit 3); and generations recorded before #110, or inline pre-#91 ones, carry no digest and are never checked — absent means no check, permanently. **(3)** A signature proves authorship, never that contents are safe: a valid signature from a compromised machine authenticates hostile content perfectly, so #36's consent gate around applying project files is unchanged and stays. **(4)** TOFU trusts the hub once per machine; only `hub trust` removes that, and it is optional.

### Shared layers: `memory/` and `plans/`

They land in a directory the TARGET owns, not under a session id the import minted, so they are reconciled rather than restored — and the two travel differently on purpose.

- **`memory/` ships on incremental bundles**, skipped only when the peer demonstrably already holds that exact directory (a `memoryDigest` recorded on the peer entry *after* the bundle commits, describing the bundle's own copy rather than the source's — so a copy truncated in flight fails toward re-sending). Every unknown ships: first push, `--since`, a reset state file. Before #53 the `!incremental` gate meant **no hub bundle ever carried memory at all**, while the manifest declared it — that gate was deliberate for `export --incremental` ("incremental is session-level", 2026-04-21) and was extended to the hub three months later by accident, because `hub push` passes a truthy `incremental` unconditionally.
- **`plans/` deliberately does NOT travel to the hub.** `<configDir>/plans` is config-dir-global with no project filter, so it ships *every plan on the machine*. On a plain export that is the user's own interactive call landing in their own directory; on the hub it would go out over the default-on, unattended SessionEnd auto-push, which has no channel to disclose what it just uploaded. Fix the payload's scope before widening its transport.
- **`includedLayers`/`exportedLayers` mean CONTENT, not policy** (#53): a layer is listed iff its payload is on disk in the bundle. They used to be `getAllLayers()` minus `--exclude`, stamped regardless of what the export did, which made every hub bundle declare layers it did not carry and made `--exclude jsonl` omit `jsonl` from a manifest whose bundle plainly contained it.

### Hook registration (`hooks/hooks.json`)

The hub's automation is driven by two Claude Code lifecycle hooks, registered in `hooks/hooks.json` and implemented by the internal CLI endpoints `hub hook-session-end` (auto-push) and `hub hook-session-start` (freshness notice). Neither endpoint is a slash command, so neither appears in `plugin.json`'s `commands` array.

These facts were verified against the installed Claude Code build's own embedded schema (2.1.221) and re-verified end-to-end in a real session. They are not guesses — check them again before changing this file. The three that a well-meaning edit is most likely to undo (SessionEnd `async`, SessionEnd **no** `timeout`, SessionStart sync + bounded) are pinned by tests in `tests/hub-hooks.test.ts`, because `hooks.json` itself cannot carry a warning: the loader rejects JSONC, so a `//` comment makes the file silently fail to load and the hooks never fire.

- **The file's existence *is* the registration.** Nothing else references it — no manifest entry, no code path — so if `hooks/hooks.json` is missing, renamed, or unparseable, both hooks simply never fire and no error appears anywhere. (It also means the automation ships with the *plugin* install, not with the npm package: `package.json`'s `files` is `["dist"]`, so `npx claude-sesh-mover` gets the CLI and no hooks.)
- **`hooks/hooks.json` at the plugin root is auto-loaded by path.** The `hooks` field in `.claude-plugin/plugin.json` is for *additional* hook files ("in addition to those in hooks/hooks.json, if it exists"); pointing it at `hooks/hooks.json` is rejected as a duplicate. So do **not** add a `hooks` field to the manifest. Root shape is `{"hooks": {"<Event>": [{"matcher": …, "hooks": [ … ]}]}}`.
- **`${CLAUDE_PLUGIN_ROOT}` only expands in a plugin's `hooks/hooks.json`,** never in `settings.json`. Keep the `node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" …` shell form: it works on every version that supports plugin hooks. (2.1.221 also accepts a safer exec form — `"command": "node", "args": [...]` — but an older build would drop the unknown `args` key and run bare `node`.)
- **`async: true` on the SessionEnd hook is load-bearing, not an optimization.** Claude Code gives *all* SessionEnd hooks a shared 1.5s budget (`getSessionEndHookTimeoutMs`, floor 1500ms) and then force-exits; a push routinely exceeds that. `async: true` backgrounds the hook in a detached process that survives Claude Code's exit. Conversely, **never set `timeout` on the SessionEnd hook**: that function raises the *shared* budget to the largest timeout any registered SessionEnd hook declares, so a timeout here would delay session exit for every other plugin's hooks too. The corollary is worth knowing before you debug it: because we declare no timeout and `async: true` spawns the hook *detached*, **Claude Code cannot bound this hook at all** — so whatever bounds it has to come from inside, which is what #71 is. That fix has two halves and the second is the surprising one. Making `hub/backend.ts` async and bounded (`hub/io-timeout.ts`) is what lets a push on a hung mount refuse, release its project lock and reap its staging directory instead of parking in its own critical section forever. It does **not** let the process exit: the abandoned `open()` is still running on a libuv threadpool thread, and measured 3/3 on Node 22.23.1 (identically for the callback API, so it is the libuv request and not a JS promise) neither a natural exit nor `process.exit(0)` nor `process.reallyExit(0)` returns — only a signal does. `cli.ts`'s `leaveEvenIfHubIoWedged` is that signal, ordered behind a stdio flush barrier, and it is why a wedged run exits by SIGKILL rather than with a code. Delete it and the fix silently degrades from "no orphans" to "one inert 50 MB orphan per session end" — which `tests/hub-lock-orphan.test.ts` pins by mutation, not by reading. **The steal that #71 left behind is closed by #84**, and the two are worth reading together: #71 removed the common TRIGGER (a wedge holding a lock for hours), #84 removed the MECHANISM. A push that legitimately outruns 10 minutes — a large bundle over a slow-but-working share, deliberately unbounded because bounding throughput would fail the shares this plugin exists to serve — now keeps its lock until the 60-minute ceiling instead of losing it silently at 10. What remains is bounded and disclosed rather than silent: a genuinely stuck holder still loses its lock at the ceiling, and when it does, both sides say so and `<lock>.steal.json` records it.
- **SessionStart must stay synchronous.** An async hook is backgrounded and its stdout is discarded, so context injection only works on a sync hook. It carries `timeout: 10` instead, so a slow or unreachable hub can never stall session start.
- **Valid SessionStart matcher values are `startup`, `resume`, `clear`, `compact`, `fork`** (matched against the payload's `source`). We register only `startup` and `resume` — `clear`/`compact` are mid-session events where a "newer work elsewhere" notice would be noise.
- **Stdin payload field names** (common to both events): `session_id`, `transcript_path`, `cwd`, plus optional `prompt_id`, `permission_mode`, `agent_id`, `agent_type`. SessionStart adds `source`; SessionEnd adds `reason`.
- **SessionStart context-injection output shape:** `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"…"}}`.

Both endpoints are the sanctioned exception to the one-JSON-result stdout contract: they print nothing (or, for SessionStart, exactly one hook-JSON object) and **always exit 0**. See `src/hub/hooks.ts` for the shared gate — linking a project IS the consent gate, so both flags default on yet stay inert for anyone who never uses the hub.

### Export storage layout

Exports land in `<homedir>/.sesh-mover/<name>/` (user scope) or `<cwd>/.sesh-mover/<name>/` (project scope) — build both from `paths.ts` (`userSeshMoverDir()` / `projectSeshMoverDir()`) rather than joining the literal name, so the user-scope migration is never bypassed. A directory export is `<name>/` with `manifest.json` + session JSONL + referenced layer files. For `--format archive`/`zstd`, the exporter writes that directory as a staging area, tars it to `<name>.tar.gz` or `<name>.tar.zst` in the parent, then removes the staging directory; the archive is the sole artifact, and `ExportResult.exportPath` is set to the archive path (equal to `archivePath`). `browse` scans both user and project directories.

### Migrate flow (self-migration hazard)

`migrate` = export + import + cleanup + optional `--rename-dir`. Because it deletes source session files and may `mv` the source project directory, running it from inside the session being migrated is unsafe:

- The running Claude Code session holds the source JSONL open and keeps appending to it; anything said after the migrate snapshot goes to the now-deleted source path and Claude Code recreates the file, orphaning the session with a stale `cwd`.
- If `--rename-dir` is passed, the shell's cwd disappears under subsequent tool calls.

`migrator.ts` **blocks actual self-migration runs by default** (returns `ErrorResult` with a recovery-step `suggestion`) whenever `currentCwd` is inside `sourceProjectPath`. Dry-run still previews (with a warning), and `--force` overrides the block for advanced use. The recommended flow for moving the active session is: exit Claude Code, `cd` to a stable outer path (`~` or similar), start a new Claude Code session there, then run `/sesh-mover:migrate`. Merging into a target project dir that already has sessions is supported, so the recovery flow is safe even when target sessions are already in place.

### Testing conventions

Vitest with fixtures under `tests/fixtures/`. Integration tests (`tests/integration.test.ts`) build full export/import round-trips against fixture config dirs — do **not** mock filesystem or archive operations; use real temp dirs (`mkdtempSync`). When adding a new JSONL entry variant, update both `src/types.ts` and the fixture JSONL; rewriter/version-adapter tests rely on realistic shapes.

**A green suite is not evidence that a guard guards.** Seven separate guards in this repo have been found passing for reasons unrelated to what they claimed to check — a `retry-works` classification nothing re-ran, a "never map an unapplied bundle" rule whose gate could be swapped for the wrong one with every pull suite still green, a double-run check whose fixture made one run and two runs byte-identical, and eight `whereis` tests built against a hub shape `hub init` cannot produce. Every one was found by mutation or a fixture audit; none by reading. So: **break the thing on purpose and watch the test fail** before believing it, and when a test passes against unfixed code, say so and label it a characterization test rather than shipping it as a guard.

**A test that writes into the un-overridden home is a WINDOWS-ONLY failure amplifier, and the amplification lands somewhere else entirely.** `overrideHome` sets `HOME` *and* `USERPROFILE` (a POSIX-only override is a silent no-op on Windows), but a test that never calls it writes to the real profile — and on Windows the temp root lives UNDER that profile, so a stray `~/.sesh-mover` becomes an ancestor of every other test's fixtures. Measured: one such write in `tests/cli.test.ts` made 18 `hub escrow` destination assertions fail on the Windows runner and nowhere else, because the ancestor walk read every temp path as "inside a sesh-mover project". The detector is cheap and worth re-running after adding any `--storage user` test — `chmod a-w` a fake home, point `TMPDIR` inside it, and the offending test names itself with `EACCES`. The same nesting is why `checkEscrowDestination` exempts **both** `homedir()` and `userInfo().homedir`: only the latter survives an override, and a fake profile staged through `$HOME` cannot exercise it, so a repro harness built that way tests the unfixed path and reports the fix as broken.

**You can run the Windows CRLF class locally, and should.** `GIT_CONFIG_GLOBAL=<a config with `core.autocrlf = true`> npm test` reproduces on Linux what Windows does to any file `git` materialises — verified by reverting a fix under it and getting the identical CI failure (`expected 'v2\r\n' to be 'v2\n'`). Use it before pushing anything that asserts on file contents after a `git apply` or checkout; it has cost this PR two CI round-trips. It does **not** cover the other platform classes (case-insensitive filesystems, `COPYFILE_EXCL` semantics, resolved tmpdir paths) — those still need the matrix.

Two traps in doing that here. **A CLI-level test cannot be mutation-tested by editing `src/` alone** — `runCli` spawns `dist/cli.js`, so a mutation is invisible until `npm run build` runs (this is why `pretest` exists; `npx vitest run` on its own does not rebuild). And **a mutation that is Windows-only or macOS-only cannot be disproved locally**: removing `sidecar.ts`'s `lstat` symlink guard leaves all 97 importer+merge tests green on Linux, and so does reverting the whole helper — only the Windows job settles it. State which platform a guard's proof lives on when it is not this one.

### When adding a command or CLI option

1. Extend `src/cli.ts` with the Commander subcommand/option.
2. Add the matching result shape to `src/types.ts` (every CLI result is typed).
3. Update `commands/<name>.md` and (if the behavior needs explanation for the skill layer) `skills/session-porter/SKILL.md`. If the command is new (not just a new option on an existing one), add its `./commands/<name>.md` path to `.claude-plugin/plugin.json`'s `commands` array too — Claude Code only loads slash commands listed there, so a new doc file with no matching entry silently never appears as a slash command.
4. If the new result shape carries a `reason`, `exitCodeForResult`'s table in `src/types.ts` will not compile until you assign it an exit class — do that deliberately (see "CLI exit codes"), and state the code in `commands/<name>.md`. A shape with no `reason` compiles either way and silently takes the default, so check it lands in the class you meant.
5. Rebuild with `npm run build` **and stage the updated `dist/`** — it's committed so installed plugins pick up the change. A commit that touches `src/` without a corresponding `dist/` update will ship a stale binary.
