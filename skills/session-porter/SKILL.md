# sesh-mover Session Porter Skill

This skill provides background knowledge for all sesh-mover slash commands. It is not invoked directly by users — the individual commands (export, import, migrate, browse, configure, hub-init, push, pull, whereis, hub-unlink) reference this knowledge.

## CLI Location

The sesh-mover CLI is at `${CLAUDE_PLUGIN_ROOT}/dist/cli.js`. Claude Code sets `CLAUDE_PLUGIN_ROOT` automatically inside plugin command execution, so **no plugin-cache discovery is needed** — invoke directly:
```bash
node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" <command> [options]
```
Do not run `find` over `~/.claude*/plugins/cache` to locate the plugin; the env var is authoritative.

All commands output structured JSON to stdout. Parse it with JSON.parse(). (The two internal hook endpoints, `hub hook-session-end` and `hub hook-session-start`, are the deliberate exception — they speak Claude Code's hook protocol and are never invoked from this skill layer. See "Hub automation" below.)

## Exit Codes

**Keep branching on the parsed JSON, not on the exit code** — the body is what carries `reason`, `linkCandidates`, `warnings` and everything else a command flow needs. But the codes exist and mean something specific, so know them: a non-zero exit is *never* a reason to discard the JSON, and a zero exit is not by itself proof of success (a `--dry-run`, a `collision: true` export and an `upToDate: true` push all exit 0 and all need their body read).

| code | class | what it means |
|---|---|---|
| `0` | success | it happened |
| `1` | the command did not run | a bad invocation, or an unexpected failure. Commander's own argument validation is here, and it prints its message on **stderr with an empty stdout** — the one case where there is no JSON to parse |
| `2` | refusal | understood and declined; nothing was done. `unlinked`, `no-such-project`, "already up to date", and `pull`'s pick-required listing |
| `3` | environment-not-ready | the invocation was fine and the machine is not: `hub-unreachable`, `lock-busy`, `not-yet-synced`. **The retryable class** — the same invocation is expected to work once the share is mounted, the lock is released, or the sync finishes |

Two shapes worth knowing because they contradict the obvious reading:

- `pull`'s **pick-required listing is `success: true` and exits 2**. Nothing was pulled; the body carries `threads` for the user to choose from. Treat it as the pick-list branch the pull command file already describes, never as a failed pull.
- A **`success: false` result on exit 2 is often routine**, not an error to escalate — a second identical `pull` answering "already up to date" is the everyday case. Report it as the state it is.

The two hook endpoints are outside all of this and always exit 0 (see "Hub automation" below).

## Do Not Probe the CLI

Each command file (`commands/*.md`) lists the exact CLI invocation it should produce, with every flag spelled out. **Do not run the CLI with `--help`, with no arguments, or with `-h` to discover its surface** — the command file is the authoritative reference. If a flag you need isn't listed there, the command file is wrong; fix it rather than working around it at runtime.

## Sensitive Data Warning

Exported sessions may contain API keys, tokens, passwords, or other sensitive data from the conversation or tool results. Always warn the user:
- When exporting to a project-level directory (it might get committed to git)
- When creating archives for transfer (the archive contains raw conversation data)
- Recommend adding `.sesh-mover/` to `.gitignore` for project-level exports — a plain line with no negation, since the three files a project is meant to commit (`.sesh-mover-include`, `.sesh-mover-ignore`, `.sesh-mover-project.json`) are root dotfiles outside that directory

## Detecting the Current Session

The current session ID can be found by:
1. Looking at the `sessionId` field in any recent tool result in the current conversation (fastest; always available mid-session)
2. Listing `<configDir>/projects/<encoded-project-path>/*.jsonl` — each filename (minus `.jsonl`) is a session ID for that project

Do **not** use `sesh-mover browse` to find live session IDs — `browse` only lists previously-exported bundles, not live sessions. There is no `--project` flag on `browse`.

## Browse Metadata (archives included)

Every `BrowseResult.exports[]` entry — directory bundle or `.tar.gz`/`.tar.zst` archive — reports `exportedAt`, `sourcePlatform`, `sourceProjectPath`, and `sessionCount` read from that bundle's own `manifest.json`. They describe the machine the bundle was **exported from**, so an archive carried from WSL to a Mac lists as `wsl2` with its WSL path. Never substitute the local platform for an archive's.

Those four fields are **nullable**, and each entry carries `metadataAvailable: boolean` (plus `metadataError: string` iff it's false):

- `metadataAvailable: true` — the four fields hold real manifest values and `sessions[]` is the manifest's session list.
- `metadataAvailable: false` — all four are `null` and `sessions` is `[]`. `null` means **"not read"**, never "not applicable" and never "zero": don't render it as `0`, an empty string, or the local platform. Show the bundle name and `metadataError` instead, and keep listing the other exports — one unreadable bundle degrades only its own row.

Causes of `metadataAvailable: false`: no `zstd` binary on *this* machine (`.tar.zst` only), a corrupt/unrecognized archive, no bundle-root `manifest.json`, unparseable or unsafe manifest content — and, for a **directory** export, a `manifest.json` that is present but unreadable, structurally not a sesh-mover bundle, or missing the `plugin: "sesh-mover"` marker. Degradation is kind-agnostic: don't assume a degraded row is an archive, and don't offer to read `<path>/manifest.json` for a degraded directory — that read is exactly what failed.

**Two omissions that are not degradations, and must not be reported as bugs.** A directory with no `manifest.json` at all never appears in any listing — only something that *claims* to be an export can degrade. And a directory in the **cwd** whose manifest is unreadable is skipped silently rather than degraded: that same read is what tells `browse` whether a stray directory is even one of ours, so degrading there would list every unrelated folder the user happens to be standing next to. A missing cwd entry is therefore ambiguous by design; a missing store entry is not.

**Identify the zstd case by the entry's name, not by the error text:** a degraded entry whose `name` ends in `.tar.zst` is the missing-`zstd` case. `metadataError` is the free-text `detail` of the underlying failure — it normally mentions zstd and corroborates the name, but it is not a stable enum and must not be the trigger (the typed `reason` never reaches the JSON). **Offer to install it** rather than just reporting the degradation — `brew install zstd` (macOS) or `sudo apt-get install -y zstd` (Debian/Ubuntu/WSL) — then re-run `browse`. Do this *before* the user picks a bundle to import: zstd is required to import a `.tar.zst` bundle too, not just to read its metadata, so an entry degraded for this reason will also fail to import until it's installed. Degraded entries stay selectable; just say the import will likely fail until the cause is fixed.

Cost note: reading a `.tar.zst` manifest decompresses the **whole** bundle to a temp file before the manifest can be pulled out, so `browse` is IO-bound in total archive size when zstd bundles are present. `.tar.gz` bundles are streamed instead of copied, but are still read end to end. Archive reads run 8 at a time, so a directory of many bundles is slower than one of a few — expect seconds, not a hang.

## Config Directory Detection

The Claude config directory is resolved in order:
1. `--source-config-dir` / `--target-config-dir` flags
2. `CLAUDE_CONFIG_DIR` environment variable
3. `~/.claude/` default

The user may have multiple config dirs (e.g., `~/.claude` and `~/.claude-tzun`). Always detect or ask rather than assuming.

## Where sesh-mover Keeps Its Own Files

Distinct from the Claude config dir above, and renamed in 0.7.0 — a dotfile spells the *plugin* name (`sesh-mover`), not the npm package name (`claude-sesh-mover`):

- `~/.sesh-mover/` — machine identity (`machine-id.json`), sync state, hub locks, user-scope exports and config.
- `<project>/.sesh-mover/` — generated only: project-scope exports, project-scope `config.json`, parked carry payloads (`carry-<ts>/`). Gitignored with a plain `.sesh-mover/` line.
- `<project>/.sesh-mover-include`, `.sesh-mover-ignore`, `.sesh-mover-project.json` — root dotfiles, **meant to be committed**, and outside the ignored directory precisely so they can be. Never tell a user to look for these inside `.sesh-mover/`.

**0.8.0 is a clean break, and nothing warns about it.** The paths above are the only ones sesh-mover reads or writes. It does not read, migrate, or notice anything a previous version wrote — no fallback read, no rename-on-first-run, no stale-name warning in `warnings` — so don't tell a user to expect one. If a user mentions a `~/.claude-sesh-mover/` directory, a `<project>/.claude-sesh-mover/` directory, or a `.sesh-mover-hubinclude` / `.sesh-mover-hubignore` file, that state is inert: nothing reads it, and it can simply be deleted. What they do instead is short — recreate `.sesh-mover-include` and `.sesh-mover-ignore` at the project root with the old contents, and either copy the old `project.json` across verbatim as `.sesh-mover-project.json` to keep that project's hub link or let the next push re-link by git remote. A project holding only an old name behaves as if it had no list at all: silent, harmless, and deliberately preferred to a list read in part.

## Error Handling

When a CLI command returns `{"success": false, ...}`:
- Read the `error` and `details` fields
- If `suggestion` is present, offer it to the user
- Common errors:
  - "No sessions found" — wrong project path or config dir
  - "Session validation failed" — version mismatch, suggest `--no-register`
  - "Integrity check failed" — data corruption during transfer

Common warnings (result is still `success: true`):
- Sessions already imported — reported in `skippedSessions` with reason `duplicate` (identical content already in this project) or `already-received` (already synced from this peer), not as an error. `importedSessions` will be empty if every requested session was skipped this way. If the user actually intended a fresh re-import, offer to retry with `--allow-duplicates`.

When import registration fails (session not resumable):
- Offer to read the imported JSONL and inject the conversation as context into a new session
- This is the fallback for when Claude Code's internal validation rejects the imported session

## Platform Notes

- WSL paths: `/home/user/...` and `/mnt/c/...`
- Windows paths: `C:\Users\user\...`
- macOS paths: `/Users/user/...`
- Linux paths: `/home/user/...`

The CLI auto-detects the current platform and translates paths during import. For WSL <-> Windows, it shows the mapping and asks for confirmation.

Rewriting is two-stage: stage 1 always replaces the exact project-path/config-dir/home-dir prefixes it's given (longest-first); stage 2 runs only cross-family (e.g. WSL ↔ Windows) and additionally scans tool-result content, `toolUseResult` stdout/stderr, and file-history snapshot keys for other path-shaped tokens (`/mnt/<drive>/...`, `/tmp`, `/home/<user>/...`, `/Users/<user>/...`). `gitBranch` is never rewritten (it's a branch name, not a path), and user text / assistant text and thinking blocks are never rewritten. Stage 2's token scan stops at the first whitespace, so a path containing a space only translates reliably when it falls under one of stage 1's exact mappings.

## Memory and Plans (the shared layers)

Four of the six layers a bundle carries — the transcript, subagents, tool-results, file-history — are written under a session id the import mints on the spot, so they can never collide with anything. Two are not: `memory/` lands in the target project's memory directory and `plans/` in a directory **every project on the machine shares**. Those two are the only place an import touches files the user already owns, and they have a stated rule rather than a copy-if-absent accident:

- **`MEMORY.md` is an index, and it is unioned — always, with no flag and no confirmation.** It is a list of pointer lines and it is the *only* thing that makes a sibling memory reachable, so keeping the local copy on a conflict strands everything that arrived beside it (#49: ten memory files landed, correct and complete, referenced by nothing, reported as `success: true`). The union keeps your file verbatim — every line, in its original order, nothing reordered, nothing rewritten, nothing deleted — and appends incoming entries whose **link target** your index does not already name, after its last pointer line. Deduping is by target, never by title or description, because the same memory gets retitled and re-described on every machine. Incoming headings and prose are dropped (reported as `droppedProse`): the union merges entries, not documents. It is idempotent, so re-running an import is safe and — since 0.8.x — actually does something: the shared layers are reconciled even when every session in the bundle is a duplicate.
- **A conflicting prose memory is kept and the incoming copy is parked beside it** as `<stem>.incoming.md` (uniquified, so a second unresolved import never eats the first), then indexed by the union so it is reachable. Reported in `memoryConflicts` with both hashes, `parkedAs`, and `memoryDir` — the absolute directory both files live in. **Nothing is ever overwritten.** The index line is *built* rather than copied, so every string in it (the parked name, the sender's machine name) is bundle-supplied and passes through one chokepoint that guarantees a single line: display text is sanitised, and a parked name that cannot be written as a markdown link target gets no line at all and a warning saying so, rather than a line that points somewhere else.
- **Those five fields (`memoryConflicts`, `memoryIndex`, `memoryDir`, `planConflicts`, `plansSkipped`) are on `import`, `pull` AND `migrate` results alike** — one declaration (`SharedLayerFindings`), mixed into all three shapes. Until 0.8.x only the *warnings* crossed into pull and migrate, so those two paths described a parked memory in prose and gave the skill layer no `parkedAs` to act on; the merge below could not be offered there at all. On a pull they are **aggregated over the whole bundle chain** rather than reported per session, because neither layer is session-scoped: a five-bundle pull that parks a memory file per bundle names every one.
- **Then, and only in a session with a user attached, `/sesh-mover:import` step 11 offers a semantic merge** (`/sesh-mover:pull` step 7 and `/sesh-mover:migrate` step 12 offer the same one, by reference to it) of the two texts — one memory, correct, with contradictions classified as superseded / both-true-in-different-scopes / unresolved, and any unresolved one shown to the user instead of being decided. The CLI never does this: it makes no model call, has no way to ask a question, and runs from detached hooks and scripts. **Parked-and-indexed is a complete outcome, not a fallback** — it is what a hook-driven `hub pull` leaves behind, and it is correct.
- **`plans/` is opt-in, and even then reported rather than merged or parked.** An import writes no plan at all unless `--include-plans` is passed: the destination is `<config-dir>/plans`, which has no project filter, so applying the layer writes files every project on this machine shares on the say-so of a bundle that may have come from anywhere. That is the receive-side half of the rule that already keeps `plans/` off the hub — fix the payload's scope before widening its transport. A skipped layer is disclosed, never silent: `plansSkipped` counts the files, and the bundle still holds every one of them, so a re-run with the flag loses nothing. With the flag on, a colliding plan keeps the local file and appears in `planConflicts`; the incoming one stays in the bundle. It has no index to make a parked copy reachable, so nothing is written beside it either. Before all this it was discarded in complete silence.
- **Memory files are never path-rewritten**, deliberately. A memory is prose a model wrote; "the config dir is `/Users/x/.claude-nv`" is a statement *about a machine*, and translating it to this machine's path would make it false rather than portable.

## Incremental Sync

sesh-mover supports incremental export/import between machines. Key concepts:

- **Machine identity:** each machine has a persistent ID in `~/.sesh-mover/machine-id.json`, auto-created on first incremental op. The human-readable name defaults to the hostname and can be overridden with `sesh-mover configure --set machine.name=<label>`.
- **Per-project sync state:** `~/.sesh-mover/sync-state/<encoded-project-path>.json` tracks, per peer machine, what's been sent and received.
- **Incremental export:** `export --incremental --to <peer>` emits only new sessions + continuation sessions for sessions with new messages since the last sync. `--since <path>` is a stateless fallback when no peer state exists (e.g. the user received an export bundle from a new machine).
- **Continuation session:** a new session whose first entry is a synthetic user message explaining the lineage. The body is the sliced remainder of the source session. This avoids merge conflicts entirely and lets Claude see the lineage directly in the transcript.
- **Idempotent import:** import is idempotent by default for every export, not just incremental ones — a per-project content-hash registry recognizes sessions whose exact content was already imported into this project and skips them (`skippedSessions` reason `duplicate`). Peer-tracked incremental syncs additionally skip sessions already recorded as received from that specific peer (reason `already-received`). Pass `--allow-duplicates` to force a re-import.

When users ask "why are there two sessions that look like the same conversation?" — check `~/.sesh-mover/sync-state/<encoded>.json`'s `lineage` map. The continuation header in the JSONL also spells out the origin session.

## Hub

The hub is a shared directory (synced folder or network share) that lets sessions move between machines without a manual export/import round-trip: `/sesh-mover:hub-init` sets it up once, `/sesh-mover:push` publishes this project's sessions to it, `/sesh-mover:pull` brings a thread from another machine down onto this one, `/sesh-mover:whereis` is a read-only view of which machines have which threads, and `/sesh-mover:hub-unlink` undoes the link for one directory — it removes `<project>/.sesh-mover-project.json` and nothing else, writes nothing to the hub, and is the one hub verb that works with no hub configured or reachable (it is the disarm path for the default-on hooks, so it must not depend on the thing it is disarming from). It is idempotent, takes the same per-project lock push/pull take (`--force` skips it), and keeps this machine's sync bookkeeping deliberately, returning the `projectId` so `push --project-id <id>` re-links to the same hub project instead of re-uploading everything. There's also a CLI-only repair verb, `hub reindex` — it rebuilds this machine's own hub index for the current project from its own pushed bundles (no dedicated command doc; run it directly if a machine's index looks stale or corrupted, e.g. `node "${CLAUDE_PLUGIN_ROOT}/dist/cli.js" hub reindex --project-path "<path>"`). Its failures are typed like the rest: `reason: "unlinked"` (this project was never pushed, so there is nothing to rebuild from — push first), `reason: "hub-unreachable"` (the shared shape push and pull return; reindex is on their side of the line because it writes), and the shared `reason: "lock-busy"`. `unlinked` is checked first and wins when both are true — it reads a local file, so unlike push's `--project-id` check its answer does not depend on the hub being mounted, and "you have never pushed this project" is the more useful of the two things to hear. On success it can carry two fields that a plain `warnings` scan would miss, and only when non-empty: `unrecognizedBundleFiles` (files in this machine's bundle directory whose names did not parse — a sync client's conflict copy is the usual one) and `droppedBundles`, which is **data loss to report rather than an aside**: those bundles are not referenced by the rebuilt index, so no other machine can see them, and the cause is this machine's sync-state having no thread mapping for the session they carry.

A **thread** is the hub's cross-machine identity for a logical conversation — one thread can have a different local session id (and even different JSONL content, if machines are out of sync) on each machine. `push`/`pull`/`whereis` all resolve threads before doing anything else.

**JSON result classes the skill must branch on:**
- `reason: "unlinked"` (push, pull — a `success: false` result instead of their normal shape) — this project directory isn't linked to a hub project yet. Comes with `linkCandidates` (matched by git remote) to present as a pick-list, plus a "create new" option for push (`--create-project`) or pick-and-relink for either (`--project-id <id>`). `whereis` reports the equivalent state differently: it always returns `success: true`, with `linked: false` and the same `linkCandidates` shape embedded in its normal result — there's no separate error case to catch there. Check `reachable` first all the same: on an unreachable hub `linked: false` is a local fact only and `linkCandidates` is absent, so neither branch below applies.
- `reason: "no-such-project"` (push, pull) — a `--project-id` was passed and the hub has no project with that id. Distinct from `unlinked` on purpose: this directory may already be linked and only the *flag* is wrong, so the remedy is to correct the id rather than to link. `requestedProjectId` echoes what was passed and `linkCandidates` is the same pick-list shape (empty when the hub lists no projects at all, which for push means `--create-project` and for pull means the other machine has to push first). It is refused at the CLI boundary before the verb runs, so **nothing was written** — no hub file, no link, no local state — and re-running with a corrected id is always safe.
- `reason: "lock-busy"` (push, pull, `hub unlink`, `hub reindex`) — another sesh-mover hub operation is already running for this project **on this machine** (see the lock caveat below). Wait briefly and retry once; don't loop. For `hub unlink` there is a second way out that push and pull don't have — `--force` skips the lock, because a wedged push holds it for up to 10 minutes and disarming must not be blocked by the thing being disarmed; the result then warns that a still-running operation could write the link file again.
- `reason: "failed-after-link"` (push) — the push got past the identity decision and then failed, so state may be left behind. Branch on the **fields**, never on `details`: `linked` (true = this directory is linked right now, so the session-end auto-push is armed for it — offer `hub unlink`), `linkRolledBack` (this push made the link and removed it again), `orphanHubProjectId` (a `--create-project` push minted a hub project nothing removes; a later push should pass `--project-id <it>` rather than mint a second), `orphanBundle` (a bundle reached the hub that no index references yet — the next successful push republishes the index). This is also the only failure shape the unattended session-end push can record, so it is what a later `hub status` shows in `lastAutoPush`.
- `reason: "hub-unreachable"` (push, pull, `hub reindex`) — the configured `hub.path` could not be read at all, so nothing could be attempted. `hubState` says which: `"no-directory"` (an unmounted share, a synced folder not yet present here, or a typo in `hub.path`), `"not-a-hub"` (a directory exists but carries no `hub.json` — never `hub init`-ed, or pointing at the wrong folder), or `"unresponsive"` (#71 — the path is mounted but a single filesystem call against it timed out: a hard mount whose server is gone, a dead sync/FUSE daemon). Treat the third as its own case rather than a variant of the first two: `hub.path` is almost certainly correct, so never send the user to check it, and the remedy is to reconnect or force-unmount the filesystem. It is also the only `hubState` whose detection costs wall-clock time, so a push or pull that returns it took the hub I/O timeout to do so — that delay is the diagnosis working, not a hang. One process-level consequence not to misread: a command that hit `"unresponsive"` exits **by signal (137), not with a status code**, because a Node process still holding the abandoned filesystem call cannot exit normally — measured, and `process.exit()` blocks too. The JSON on stdout is complete and is still the thing to read; treat a non-zero shell status accompanied by a parseable `hub-unreachable` body as that refusal, never as a crash. Refused before any hub write, any export and any link, so **re-running is always safe** and a failed push has definitely not armed the auto-push for that directory. For `hub reindex` the refusal is what stops it rebuilding an index into a directory it could not read — and stops the rebuild's own `registerMachine` write from *creating* a plausible-looking hub at a mistyped path. Two things not to do with it: don't present `linkCandidates` (the hub couldn't be listed, so empty means "unknown", not "none"), and don't tell the user the path — the result withholds it on purpose; point them at `configure --show` instead. Distinct from `not-yet-synced` by construction: that one presupposes a *fully readable* hub whose indexes already resolved a thread and names the specific bundle files still in flight, and it is only reachable after this gate passes — so the two can never both be true.
- **The same condition is REPORTED, not refused, by the three verbs that are not about to write, and the split is deliberate rather than partial.** `hub status` and `whereis` both answer `success: true` carrying `reachable: boolean` and the same `hubState` enum (`whereis` also uses `hubState: "ok"`; `hub status` additionally uses `hubState: null` for "no hub configured at all", which pairs with its `hubPath: null`; both also report `"unresponsive"`, and for them it is the state most worth surfacing verbatim, since a diagnostic verb is exactly what a user runs when the share has gone quiet). Refusing there would answer a different question than the one asked — `hub status` exists to say what state things are in, and would take `hubPath`, `machineRegistered`, `project.linked` and `lastAutoPush` down with it, the last of which is the *only* record of the unattended push that unreachable hub just broke. On `whereis` read `reachable` before anything else: `threads: []` then means unknown rather than none, `linked` is a purely local fact about `<project>/.sesh-mover-project.json`, and `linkCandidates` is **absent** rather than empty (empty is documented to mean "the hub lists no projects", and the projects listing is exactly what failed). `hub unlink` never asks at all — it is the disarm path and works with no hub configured or reachable, which is a guarantee, not an oversight.
- `reason: "not-yet-synced"` (pull) — the hub folder's own sync client (OneDrive/Dropbox/Syncthing/etc.) hasn't finished copying the needed bundle files to this machine yet. Lists `missing` files; offer a retry.
- `pickRequired: true` (pull, when run without `--thread`/`--latest`) — presents the same thread list shape as `whereis` (`threads: WhereisThread[]`); ask the user to pick one, or offer `--latest`.

**Continuation append (pull):** when a pulled bundle continues a session this machine already has, `pull` splices the new entries onto the end of that local session instead of creating a second, truncated "continuation" session — so the thread stays one resumable transcript. Successful splices appear in `appended: [{ threadId, baseSessionId, entriesAppended }]`; those sessions are **not** in `importedSessions` (nothing new was created). The splice is refused, with a warning and a normal fragment import as the fallback, when (a) the local file was written in the last 5 minutes — a live Claude Code session may still be appending to it, and so may an earlier sesh-mover pull that imported or spliced that same session (the self-write exemption covers only the pull doing the asking), so relay the age and both possibilities rather than asserting a live session; (b) no local session's entry chain lines up with the continuation, or (c) the bundle's content fails its manifest integrity check. `--force-append` overrides **only** case (a) — it never skips the chain guard, so suggesting it for (b) or (c) is always wrong. Case (a) is foreclosed for the bundle it happened to (it was imported and recorded, so no re-run reaches it) but not for the thread: `--force-append` on the *next* pull of that thread does splice that pull's continuation, so scope the advice rather than withholding the flag. `--no-append` (or `hub.pullAppend: false`) disables the whole path. Content always arrives either way — the only difference is one session or two.

Which local session a continuation splices onto is decided by its **anchor** (the entry it follows), not by which session was mapped to the thread first: a thread routinely maps to several local sessions, because every refused splice forks a fragment that is also mapped to it. That is also what makes a forked thread self-healing — the next continuation finds the fragment carrying its anchor and rejoins there.

**Divergence (pull, `--on-divergence`):** case (b) above has a special shape worth naming — both machines extended the thread from the *same* entry, so neither branch continues the other. The pull then returns a `divergence` object (anchor uuid, the diverged local session id, entry counts and last-active times for both sides, `adoptAvailable`, and the `resolution` that was actually applied) and the mode decides what happens: `fragment` (the config default) imports the hub's branch as a separate session and leaves the local one alone; `adopt-hub` makes the hub's branch canonical in the local session and preserves the local branch **in full** — shared history included — as a new registered session named in `divergence.preservedSessionId`; `skip` applies and records nothing **for the diverged bundle and everything behind it in the chain**, so the same pull can be re-run with a different answer. `adoptAvailable: false` means the shared anchor isn't in the local session at all (compacted or unrelated history), and adopt-hub is then refused with a warning and falls back to a fragment import. Two things to always tell the user about an adoption: the preserved session has **no thread mapping**, so the next push publishes it as its own thread, and a Claude Code session left open on the adopted transcript will keep appending to the hub's branch. Because adoption **truncates** a transcript the user owns, it is refused outright when the local session was modified in the last 5 minutes (`divergence.localLastActiveAt`) unless `--force-append` is passed — the same flag, but here it means "I have closed that session and accept the cut", not the live-base override it means on a plain append. That refusal reports `resolution: "skip"` and stops the **whole chain**, not just the bundle it was refusing: the next bundle is anchored on the head the refused one would have installed, so letting the loop carry on fragment-imported it, recorded it, and silently overwrote `divergence.resolution` with `"fragment"`. Because the chain stops, the re-run it asks for genuinely reaches the fork: a refusal never forecloses the choice it is refusing. The same is true of a user-chosen `skip`; both say in a warning how many later bundles they left unfetched. **"Nothing was applied" is a claim about the diverged bundle and the ones behind it, never about the whole pull.** A chain is walked in order, so bundles *before* the fork have already been spliced or imported and recorded — read `appended` and `importedSessions` before you tell the user the pull was a no-op, and expect `carryApplied` to be present when a payload rode one of those earlier bundles. The CLI's own warning names what landed and says the re-run resumes at the diverged bundle rather than replaying the chain; relay that, and never generalize it to "nothing happened". An adoption also surfaces in `appended`, so check `divergence.resolution` before describing an `appended` entry as a continuation: an adopted session no longer holds the entries the user wrote locally. `/sesh-mover:pull` runs with `--on-divergence skip` so the choice can be offered before anything is applied; the default for a direct CLI invocation is `fragment` (`hub.onDivergence` in config).

**Workspace payloads (pull — `workspaceUnpacked`, `workspaceMerge`, `workspaceRefused`, `workspaceDeclaredMissing`):** a bundle from a project with **no** git remote carries a copy of the project's files. How it is applied depends on whether the two machines share a workspace generation — a snapshot both trees are known to have passed through, identified by bundle id (never by a timestamp; the hub stamps nothing and `pushedAt` is the pushing machine's own clock). With one, `pull` merges 3-way against it and reports `workspaceMerge`; the payload is applied, so never describe that as "skipped". Without one — a first pull into a directory that already has content — the payload is left alone entirely and the warning names `--force-workspace` (overwrite, not merge) and `--target-path <fresh-dir>` (unpack elsewhere, destroys nothing); offer those as attempts rather than guarantees, because this pull recorded its bundles and a repeat can answer "already up to date" before reaching the payload — they apply reliably only to the *next* payload from that machine. **The two are not interchangeable.** Only `--force-workspace` ends the repetition for *this* directory: every piece of local bookkeeping is keyed off the effective project path, which IS `--target-path` when one is given, so the generation an unpack there records belongs to the fresh directory and pulls into the original keep skipping identically. **Whenever you offer `--target-path <fresh-dir>`, say what it plants there:** a pull that delivers a payload into that directory also writes `.sesh-mover-project.json` into it, which *links* the throwaway directory to the hub project — and linking is the consent gate for the default-on session-end auto-push, so a Claude Code session later started *in* that directory would push its contents to the hub when it exits. `/sesh-mover:hub-unlink` (`hub unlink --project-path <that-dir>`) is the supported way to undo that, and deleting the root dotfile by hand is the same act; nothing else un-links it — the `.sesh-mover/` directory beside it holds parked carry payloads and exports, so removing that discards those but leaves the link intact. Never present the flag as leaving nothing behind. Into an empty directory, or with `--force-workspace`, it is unpacked wholesale and only `workspaceUnpacked` is set. The merge never deletes: a file gone locally but untouched upstream stays gone (`localDeleted`, which is *not* proof the user deleted it — an earlier merge that could not write there lands in the same list), a file gone locally but changed upstream comes back (`restored`), and anything it cannot merge is kept as-is with the incoming copy parked beside it as `*.theirs-<ts>` (`sidecars`). `conflicted` files contain real `<<<<<<<`/`>>>>>>>` markers and are the user's to resolve. Branch on the fields, never on the warning: a warning naming `--force-workspace` is emitted in *both* directions now (successful merges name it as the remedy for a withheld file). `workspaceRefused` lists payload paths that can never be applied (`.git`, or a path sesh-mover owns — `.sesh-mover/` and the `.sesh-mover-*` root dotfiles — at any depth, any casing); `workspaceDeclaredMissing: true` means the manifest declared a payload the bundle does not contain — field-identical to the no-generation skip otherwise, but with no remedy on this machine, since re-running is foreclosed and the payload was never in the bundle.

**Gitignored paths a push left behind (push — `ignoredNotCarried`):** present only on a **git** project that has no `.sesh-mover-include` yet; it is a capped sample of gitignored paths the carry did not take, offered so the user can create that file. Its existence is what suppresses the suggestion. It is a security-relevant list (`.gitignore` is where `.env` lives), it is meant to be **committed** so it applies on every clone, and listing a path really does upload it on the next push — a later push names it back in `carry.reIncluded`. Never pre-select, never widen a path, never offer `.git` or any path sesh-mover owns.

**Carried uncommitted work (pull, `--apply-carry`):** a bundle from a git project can carry that machine's *uncommitted* work — a `git diff HEAD` patch plus untracked files. It is **never** applied on its own: `pull` reports `carryAvailable` (the sender's own description) and `carryApplied` (what happened), and only `--apply-carry` writes into the working tree. Every guard runs before any mutation — a git repository whose `HEAD` is the exact captured commit, no merge/rebase/cherry-pick in progress, no uncommitted changes to tracked files in the project subtree, `git apply --check` clean — and the payload itself is refused whole if it names `.git` or a path sesh-mover owns (`.sesh-mover/`, the `.sesh-mover-*` root dotfiles) at any depth — as a write, a rename source or a copy source — or would create a symlink (`reason: "unsafe-payload"`). That reason is only ever about the payload: a receiver whose own `git` cannot run or cannot read its repository comes back as `no-git`/`not-git` with git's words in `detail`, and a bundle whose patch no git can parse comes back as `apply-failed` — so never relay either as a security finding. Untracked files never overwrite: identical content is a no-op, different content is kept and the incoming copy lands beside it as `<name>.incoming-<ts>` (reported in `collisions`). Any decline — including the routine `reason: "not-requested"` — writes the whole payload to `carryApplied.savedTo` (`.sesh-mover/carry-<ts>/`, self-ignoring, with a README of the exact commands whenever `carryApplied.savedCommands` is `true` — it is `false` for the two declines that withhold them on purpose, `unsafe-payload` and an unparseable `apply-failed`). Branch on `carryApplied.reason`, never on warning text, and never suggest re-running the pull with `--apply-carry`: the bundle is recorded as received by then, so that re-run reports "already up to date" — the saved directory is the remedy.

**A thread whose history is split across machines (pull, whereis — `unfetchableBundles`):** each machine's hub index lists only the bundles *it* pushed, so a conversation written on A, continued on B and pulled back to A has half its bundles in A's index and half in B's. **A pull assembles that chain across every machine's list**, following the entry each bundle records itself as continuing from, and fetches the whole thread in order whichever machine listed which part — so a third machine gets the conversation entire. Order comes from those links alone, never from `pushedAt` (the hub stamps nothing, so that is the pushing machine's own clock). **What assembly still cannot deliver, it names — and each condition is its own typed field, so you never have to read the wording to know which one it is.** `unfetchableBundles` says which **machines** hold what this pull did not fetch; the field beside it says **why**, and the five are five different answers: `chainGaps` (a bundle's recorded link points at an entry no bundle on the hub carries — the chain is applied up to that point and stops there, never resuming past it; `strandedBundleIds` is what one gap holds back); `parkedBranches` (the thread forks on the hub and this pull followed one side — not the local-vs-hub `divergence`, which is about the user's own transcript and has a policy flag); `unplaceableBundles` with `preAssembly: true` (pushed before this release recorded links at all — unlinkable by construction, *not* missing, and it re-links the next time the machine holding that session pushes it) or `preAssembly: false` (an index declaring a continuation of nothing, i.e. damaged or hand-edited); `unwalkedRoots` (the thread has more than one independent starting point and this pull walked one — ordinary rather than damage, since a compacted or truncated session is re-pushed whole under the same thread id, and two starting points can never be joined because a compaction rewrites the uuids a link would need); and `advertisedUnshipped` (a machine advertises a head it never pushed — that work is not on the hub at all, so no pull of any kind reaches it, and the answer is for that machine to push, which its SessionEnd auto-push does by default). Every one of those fields is emitted together with the warning that explains it, so branch on the field and use the warning as the wording, never the other way round. `unfetchableBundles` can appear *alone* — the residual case where the walk could not account for those bundles at all — and the honest report there is exactly that, not a guess at which condition it was. Nothing is ever lost in any of them: every bundle stays on the hub. A pull that assembles a thread, hits one of these and correctly applies nothing comes back **`success: true`** with `nothingToApply: { reason }` and no `error` — do not present that as a failure or offer a retry; the reason is the answer. **One shape has a remedy and it needs no flag:** if the thread's newest copy is *this* machine's own (`whereis`: `latest.machineId` is the machine of the copy matching `localCopy.localSessionId`) while another machine still lists bundles that never arrived here, a plain `pull` of that thread falls back to that machine and fetches them, warning that it did, instead of stopping at "the latest copy of this thread is already local" — a statement about heads that was answering a question about bundles, which the default-on auto-push separates routinely. Offer that pull. `pullNeeded` answers one question and it is the pull's own: *would a pull fetch a bundle that never arrived here?* It reads receipts, not heads, and since assembly it reads them across the whole assembled chain — so it is true whenever a pull would fetch, including on a thread whose local head already matches the newest one the hub knows, and including on a thread whose remaining bundles sit on a machine this pull does not resolve to. Wholeness is still `unfetchableBundles`' question, never this field's: `pullNeeded: false` means "a pull would fetch nothing", and a thread can be complete-as-the-hub-allows while one of the conditions above still holds. Do not relay an empty `warnings`, a successful import, `whereis`'s `current: true` or `pullNeeded: false` as "you now have the whole thing" when `unfetchableBundles` is present.

**Same-machine lock caveat:** the push/pull lock (`~/.sesh-mover/locks/<encoded-project-path>.lock`) only guards against two hub operations racing on the **same machine** for the same project. It is not a distributed lock — two different machines can still push or pull concurrently, and the hub's append-only bundle/index design is what keeps that safe, not the lock.

**Hub automation (hooks — never invoked by this skill layer):** the plugin registers two Claude Code lifecycle hooks in `hooks/hooks.json`, backed by two internal CLI endpoints, `hub hook-session-end` (pushes this project when a session ends) and `hub hook-session-start` (injects a one-line notice when another machine holds newer work for this project). **Never run either endpoint yourself, and never treat them as commands** — they are the one exception to the "all commands output structured JSON" rule above: they speak Claude Code's hook protocol (nothing on stdout, or exactly one hook-JSON object) and always exit 0, so their output cannot be parsed as a result. They are not slash commands and are absent from `plugin.json`'s `commands` array.

What matters for user questions: **linking a project to a hub project is the consent gate.** Both hooks default on, and both are inert until a hub is configured *and* this project is linked — so a user who never touches the hub never has either one do anything. Once linked, they are live with no further action, including for projects linked under an earlier version. Opt out per machine or per project with `configure --set hub.autoPush=false` / `hub.startupNotice=false`; the auto-push carries the same payload a manual push does, so `hub.noWorkspace` and `hub.carryDiff` govern it too (the hook takes no flags). If no auto-push seems to be happening, check `hub status`'s `project.linked` first — an unlinked project is silent by design. The gate is undone the way it was made: `/sesh-mover:hub-unlink` removes exactly that one file (`<project>/.sesh-mover-project.json`) and deleting it by hand is the same act, so both hooks go inert for that directory. It writes nothing to the hub — sessions already pushed stay there, other machines are unaffected — and it needs no configured or reachable hub, so it still works when `hub.path` is gone or the share is unmounted. Two things not to conflate: it is per *directory* (a scratch directory a `pull --target-path` linked has to be unlinked on its own), and it is not a config change — `configure --set hub.autoPush=false` silences the push while leaving the project linked, unlinking disarms both hooks for one directory while leaving config alone, and neither removes anything from the hub. The auto-push is also **silent about what it did**: its stdout is closed and a clean session exit never surfaces its stderr, so every warning a manual push prints — including the `carry.trackedIgnored` disclosure naming gitignored-but-*tracked* files whose contents its patch carried off the machine — is recorded in sync-state instead and reported by `hub status` as `lastAutoPush` (`{ at, ok, notes, noteCount }`). That field is the answer to "what has been leaving my machine automatically?" and to "why does the hub look stale?" (a failed push records its error there); never claim the automatic push warned the user about something, because it has no one to warn. **It has one known blind spot, so don't read its absence as "no auto-push has failed":** the breadcrumb is only written for a project whose sync-state already carries a hub block, i.e. one that has completed a push through a hub at least once, and an auto-push refused for an unreachable hub is refused *before* the step that creates that block. So a project that has never pushed successfully records nothing at all when its auto-push is refused. `hub status`'s own `reachable` / `hubState` is what answers there instead. The notice fires on `pullNeeded`, which asks exactly what a pull asks — *is any bundle in this thread's assembled chain still unreceived here?* — so it is silent for a thread a pull would fetch nothing for. Since chain assembly that question spans every machine's bundle list, so the notice no longer nags indefinitely about a split thread no pull could complete. Read the silence narrowly all the same: it means "a pull would fetch nothing", never "this machine holds the whole conversation", and `whereis`'s `unfetchableBundles` is still the field that says which. Conversely the notice can name a thread whose local head already matches the hub's newest, because a head arriving is not a bundle arriving; that is a real fetch, not a stale index. `hub.startupNotice=false` remains the way to silence the notice per machine or per project.

**Trust model:** the hub directory is a trust boundary — sessions are stored there in plaintext at rest until a future encryption slice ships. Anyone with read access to the hub folder can read every pushed session.
